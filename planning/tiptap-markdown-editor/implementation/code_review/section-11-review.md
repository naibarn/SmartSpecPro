| HIGH | `SafeMarkdown.tsx:214` | `extractAttr` regex does not escape `name` before interpolating into `RegExp`. For attribute names containing regex metacharacters (specifically hyphens in `data-asset-id`), the hyphen is a literal in most positions but the `\b` word-boundary assertion preceding `name` already breaks for hyphenated names — see MEDIUM below. More critically: if `name` ever contained `(`, `)`, `.`, or `*` (caller-controlled), the regex would be silently malformed or exploitable. The function is currently called with three hard-coded string literals, so no immediate exploit exists, but the function has no guard. | Escape the `name` parameter before interpolating: `const escaped = name.replace(/[.*+?^${}()|[\]\\]/g, "\\$&");` then use `escaped` in the `RegExp` constructor. |
| HIGH | `SafeMarkdown.tsx:214` | `extractAttr` uses a `\b` word-boundary before the attribute name. `\b` requires a word character (`[A-Za-z0-9_]`) on one side and a non-word character on the other. A space (` `) before `data-poster` satisfies this. However the `-` in `data-asset-id` is a non-word character, so `\b` before `data` matches correctly at the start of the token. The real failure case is a tag like `<video xdata-poster="..." data-poster="good">` — the `\b` before `data` also matches inside `xdata-poster`, so `extractAttr(attrStr, "data-poster")` would return the value from `xdata-poster`. In practice Tiptap serialization will not produce such attributes, but SafeMarkdown renders arbitrary user/LLM-generated HTML. | Replace `\b` with `(?:^|\\s)` in the constructed regex: `` const re = new RegExp(`(?:^|\\s)${escaped}=["']([^"']*)["']`); `` |
| MEDIUM | `SafeMarkdown.tsx:219-226` | `isUrlSafe` allows `http://` (plain HTTP). The section plan specifies "reject `javascript:`, `data:`, etc." and `sanitizeUrls` in the same file does NOT allow bare `http://` links without further scrutiny. More importantly, the canonical URL validator in `mediaSerializationRules.ts:sanitizeMediaSrc` (the shared security utility for all Tiptap media nodes) uses the same allowlist (`https://`, `http://`, `/`), so this is consistent with the rest of the codebase. However, the `isUrlSafe` implementation diverges from the canonical helper in one important respect: `sanitizeMediaSrc` checks a blocklist of dangerous schemes (`data:text/html`, `data:application`, `data:image/svg+xml`, `blob:`, `file:`) before the allowlist, while `isUrlSafe` uses an allowlist-only approach. Both arrive at the same result for the poster URL specifically — `data:image/svg+xml` is NOT in the `isUrlSafe` allowlist, so it would be blocked. But the divergence creates a maintenance risk: a future change to `BLOCKED_PROTOCOLS` in `mediaSerializationRules.ts` will not propagate to `isUrlSafe`. | Replace `isUrlSafe` with an import of `sanitizeMediaSrc` from `../../editor/extensions/mediaSerializationRules` and use `sanitizeMediaSrc(poster) || undefined` in the `splitByMedia` push. This eliminates duplication and keeps URL policy in one place. If the import path is awkward, at minimum document the link. |
| MEDIUM | `SafeMarkdown.tsx:313` | When a caption is present, `videoEl` is constructed with `key={undefined}` (line 313: `key={part.caption ? undefined : i}`). The `<figure>` wrapper then uses `key={i}`. This means the internal `<video>` element has no key, which is fine when it is a direct child of `<figure>`, but if React ever reconciles the `mediaParts` list when a caption is added/removed, the `<video>` element will be remounted unexpectedly (user loses play position). The same pattern applies to `<audio>` at line 340. | Give the inner `videoEl` / `audioEl` a stable key regardless of caption presence: always use `key={i}` on both the figure wrapper and the inner element. Since the inner element is not a direct child of the array (it is a child of `<figure>`), the `key` prop on the inner element is not required by React — remove it entirely from `videoEl`/`audioEl` and keep the `key` only on the outermost returned element (`<figure>` or the bare element). |
| MEDIUM | `SafeMarkdown.tsx` (general) | `data-alignment` is one of the four attributes in `MEDIA_DATA_ATTRS` (the canonical allowlist defined in `mediaSerializationRules.ts:7`). Section 11 adds `data-poster`, `data-caption`, and `data-asset-id` to `ADD_ATTR` in `sanitizeContent`, but `data-alignment` is omitted. Section 06 review (previously filed) already flagged `MEDIA_DATA_ATTRS` missing `data-alignment` as a HIGH issue. Regardless of that finding's resolution status, if Section 06 serializes `data-alignment` onto image nodes and SafeMarkdown later renders those images, the attribute will be stripped by DOMPurify. | Add `"data-alignment"` to the `ADD_ATTR` array in `sanitizeContent` alongside the three attributes added in this section. |
| MEDIUM | `SafeMarkdown.test.tsx:91-98` | The mixed-content test (test 9) asserts that "Some text before" and "Some text after" are NOT present — it never calls `screen.getByText` for them; it only checks that `"Cap"` and a `<video>` element exist. If the text-part Streamdown rendering is broken (e.g., text parts are silently dropped), this test still passes. The plan specifies: "Assert 'Some text before' text is present" and "Assert 'Some text after' text is present". | Add `expect(screen.getByText(/Some text before/)).toBeTruthy()` and `expect(screen.getByText(/Some text after/)).toBeTruthy()` to the mixed-content test. |
| LOW | `SafeMarkdown.tsx:211` | The new `MEDIA_TAG_REGEX` pattern `/<(video|audio)\b([^>]*)>(?:<\/\1>)?/g` does not handle self-closing XHTML-style tags (`<video ... />`). A `<video src="..." />` will not be matched; instead the tag leaks into the text part and is passed to Streamdown, which will strip it. | Extend the regex: `/<(video|audio)\b([^>]*?)\/?>(?:<\/\1>)?/g`. ### Summary

The four planned changes are correctly implemented: the DOMPurify `ADD_ATTR` whitelist is extended, `MediaPart` is widened, `splitByMedia` extracts all three new attributes via a two-step regex approach, and the render path propagates `poster`, `caption`, and `assetId` to the DOM with a `<figure>` wrapper. The `javascript:` XSS vector in `data-poster` is blocked.

Two issues warrant fixes before merge: (1) `extractAttr` interpolates the `name` parameter into a `RegExp` constructor without escaping it, and the `\b` word-boundary can match inside longer attribute names like `xdata-poster`; both are low-risk with current callers but are correctness bugs in a security-adjacent function. (2) `data-alignment` — the fourth member of the canonical `MEDIA_DATA_ATTRS` constant — is absent from the `ADD_ATTR` whitelist, meaning images with that attribute rendered via the DOMPurify path will silently lose their alignment. The recommendation to consolidate `isUrlSafe` into the shared `sanitizeMediaSrc` utility is worth doing now to prevent URL policy divergence between SafeMarkdown and the Tiptap extensions.
