### Findings

| Severity | File:Line | Issue | Recommended Fix |

| HIGH | `DocumentManagement.tsx:770` | **Conflict detection still uses fragile string-match in parent**. The plan explicitly forbids `error.message.toLowerCase().includes("version conflict")` and requires either `error.data?.httpStatus === 409` or an error-code check. This is the code path that is supposed to hand off to the dialog, but the existing `DocumentManagement.tsx` save handler at line 770 still silently retries on conflict — it never calls `triggerConflict` and never opens the dialog. The new `triggerConflict` callback defined in `UnifiedDocumentSurface` at line 201 is entirely dead code: it is neither passed as a prop to `UnifiedDocumentSurfaceProps`, nor forwarded via a ref, nor wired into any parent save handler. The dialog will therefore never be shown in practice. | Add `onConflict?: () => void` to `UnifiedDocumentSurfaceProps`. Call `props.onConflict?.()` inside the surface's `doSave` error path (or expose `triggerConflict` via a ref). In `DocumentManagement.tsx` replace the string-match with `error.data?.httpStatus === 409` and call the new callback instead of the silent retry. |
| HIGH | `UnifiedDocumentSurface.tsx:182–186` | **`handleConflictOverwrite` calls `doSave` but `doSave` is fire-and-forget and cannot propagate a conflict trigger back**. The overwrite attempt re-invokes `onSave?.(md)` (line 74), which is a void callback. If the overwrite itself fails (e.g. a network error), `conflictDetected` has already been set to `false` (line 184) before `doSave` is called (line 185). The user loses the conflict state with no way to re-enter it. `dirty` is also set to `false` inside `doSave` regardless of whether the underlying save mutation succeeds. | Move `setConflictDetected(false)` to the success path rather than before the save attempt. Because `doSave` is fire-and-forget by design (plan §S10 comment on line 71), the overwrite handler must wait for a success/error signal from the parent (e.g. via an `onSaveSuccess`/`onSaveError` callback, or by tracking `isSaving` and `errorMessage` transitions) before clearing the conflict flag. |

This creates a gap if the rendering pattern changes in the future. | Either remove the conditional wrapper and pass `open={conflictDetected}` always (allowing Radix to animate open/close), or remove the `open` prop from the interface entirely and always render `<AlertDialog open={true}>` knowing the conditional handles visibility. The test fires a `keydown` event directly on the title text node (which is not the `AlertDialogContent` element), not on the element where `onEscapeKeyDown={(e) => e.preventDefault()}` is registered. Radix forwards its synthetic Escape event to the `AlertDialogContent` via its own internal event system — a raw `fireEvent.keyDown` on an inner text node bypasses this entirely. The assertion that the dialog is still visible passes trivially because nothing in the test environment causes it to close (the `open` state is controlled by the parent and was never changed). The test proves nothing about the `e.preventDefault()` guard. | To meaningfully test the Escape prevention, render `<AlertDialog>` with an `onOpenChange` spy and verify the spy is NOT called when Escape is pressed. Alternatively, move this behavior to an integration test that renders `UnifiedDocumentSurface` and verifies the dialog persists after the global Escape handler fires. |

The plan (§Step 3, bullet 3) and the component interface both support a `documentTitle` prop that shows users which document has a conflict. `UnifiedDocumentSurfaceProps` exposes nothing equivalent, and the call site passes no `documentTitle`. ### Summary

The `ConflictResolutionDialog` component itself is well-built: Escape and outside-click prevention are correctly implemented, XSS is not possible through `documentTitle` because it is rendered as a React text node, and the i18n keys are present in both locales. However, the integration has a critical gap — the `triggerConflict` function defined in `UnifiedDocumentSurface` is dead code because it is never forwarded to the parent and `DocumentManagement.tsx` still silently overwrites on conflict using the pattern the plan explicitly forbade. Additionally, the overwrite handler clears the conflict flag before confirming save success, which can leave the document in an inconsistent state if the overwrite mutation fails. These two wiring issues must be resolved before the conflict dialog provides any user-visible protection.
