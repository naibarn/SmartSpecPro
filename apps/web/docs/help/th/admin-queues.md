# ตรวจสอบคิว

## ภาพรวม

Queue Monitoring Dashboard ให้ผู้ดูแลระบบมองเห็นการประมวลผล Background ทั้งหมดบนแพลตฟอร์มแบบ Real-time คำขอ LLM Inference และงานสร้างสื่อทำงานแบบ Asynchronous ผ่านคิวแยกกัน — หน้านี้คือที่ที่คุณวินิจฉัยการทำงานช้า ตรวจสอบข้อผิดพลาด และแทรกแซงด้วยตนเองเมื่อจำเป็น

## Queue Dashboard

Dashboard ระดับบนแสดงการ์ดสรุปสำหรับแต่ละคิว:

- **Active** — งานที่กำลังประมวลผลอยู่
- **Waiting** — งานที่อยู่ในคิวและรอ Worker
- **Completed** — งานที่เสร็จสำเร็จในชั่วโมงที่ผ่านมา
- **Failed** — งานที่เกิดข้อผิดพลาดและต้องดูแล

ตัวบ่งชี้สุขภาพใช้การเข้ารหัสสี: สีเขียว (ปกติ), สีเหลือง (เวลารอสูงหรืออัตราข้อผิดพลาดสูง), สีแดง (คิวหยุดหรืออัตราความล้มเหลวสูง)

## LLM Queue

LLM Queue จัดการคำขอ Language Model Inference ทั้งหมด — ข้อความ Chat การรัน Skill การปรับปรุง Prompt และการเรียก Brainstorm Mode

- **กรอง** ตามสถานะ ผู้ใช้ โมเดล หรือช่วงเวลา
- แต่ละแถวงานแสดง: ผู้ใช้ โมเดลที่ขอ ประมาณ Token ขาเข้า สถานะ เวลารอ และเวลาประมวลผล
- **รายละเอียดงาน** — คลิกงานเพื่อดู Request Payload ครบถ้วน, Response Payload, Provider ที่เลือก, Token จริงที่ใช้, ต้นทุนเป็น USD และเครดิต และข้อความข้อผิดพลาด
- **Trace ID** — แต่ละงานมี Trace ID ใช้เพื่อเชื่อมกับรายการ Audit Log

## Media Queue

Media Queue จัดการงานสร้างรูปภาพ วิดีโอ และเสียงที่ประมวลผลโดย Celery Workers

- กรองตามประเภทสื่อ (รูปภาพ วิดีโอ เสียง) สถานะ ผู้ใช้ หรือ Provider
- แต่ละงานแสดง: ผู้ใช้ ประเภทสื่อ โมเดล/Provider ระยะเวลาโดยประมาณ สถานะ และเวลาสร้าง
- **รายละเอียดงาน** — แสดง Prompt การสร้าง รูปอ้างอิง (ถ้ามี) การตอบกลับของ Provider URL ไฟล์ผลลัพธ์ และการแบ่งเวลา
- งานสร้างวิดีโอที่ใช้เวลานานจะแสดง **เปอร์เซ็นต์ความคืบหน้า** เมื่อ Provider รองรับ

## รายละเอียดงาน

แผงรายละเอียดทุกงานประกอบด้วย:

- **Request Payload** — สิ่งที่ส่งไปยัง Provider จริงๆ
- **Response Payload** — สิ่งที่ Provider ส่งกลับมา รวมถึงข้อความข้อผิดพลาดดิบสำหรับงานที่ล้มเหลว
- **Timing** — เวลารอในคิว เวลาประมวลผล เวลารวม
- **Cost** — เครดิตที่หักและต้นทุน USD ในอัตรา Provider
- **Error** — ข้อความข้อผิดพลาดและ Stack Trace ครบถ้วนสำหรับงานที่ล้มเหลว

## การลองใหม่งานที่ล้มเหลว

- คลิก **Retry** บนงานที่ล้มเหลวเพื่อส่งใหม่ด้วยพารามิเตอร์เดิม
- งานที่ลองใหม่จะถือเป็นงานใหม่ — ได้รับ Job ID ใหม่ แต่รักษา Trace ID เดิมสำหรับการเชื่อมโยง Audit
- **Auto-retry** — กำหนดค่าจำนวนการลองซ้ำอัตโนมัติและช่วง Backoff ใน **Admin → System Settings → Queue**
- งานที่เกินขีดจำกัดการลองใหม่จะย้ายไปสถานะ **Dead Letter** แต่ยังสามารถลองใหม่ด้วยตนเองได้

## ตัวบ่งชี้สุขภาพ

Queue Dashboard คำนวณ:

- **Throughput** — งานที่เสร็จต่อนาที (LLM และสื่อแยกกัน)
- **P50 / P95 Latency** — เวลาประมวลผลค่ากลางและหาง
- **Error Rate** — เปอร์เซ็นต์งานที่ล้มเหลวใน 15 นาทีที่ผ่านมา
- **Worker Count** — Celery Workers ที่ใช้งานอยู่และโหลดปัจจุบัน

ตั้งค่าเกณฑ์การแจ้งเตือนใน **Admin → System Settings → Monitoring** เพื่อรับการแจ้งเตือนเมื่อตัวชี้วัดใดๆ เกินขีดจำกัดที่กำหนด
