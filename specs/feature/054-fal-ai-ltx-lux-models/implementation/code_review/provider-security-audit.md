## Findings

| ID  | Severity | File:Line | Anti-Pattern | Description | Recommended Fix |
|-----|----------|-----------|--------------|-------------|-----------------|
| F01 | HIGH | `fal_ai_provider.py:79` | SSRF — redirect following on main calls | `_check_video_size` correctly sets `follow_redirects=False`, but the four main outbound calls (`client.post` at lines 137, 161, 182; `client.get` at lines 196, 209) do **not** set `follow_redirects=False`. `httpx.AsyncClient` defaults to `follow_redirects=False` for GET but **True** for POST in some versions — more importantly the explicit omission leaves the door open if the default is changed or the client is reconfigured. If fal.ai ever returns a `3xx` to an internal redirect target, the client will silently follow it. | Pass `follow_redirects=False` explicitly on every `client.post` and `client.get` call in the provider. |
| F02 | HIGH | `fal_ai_provider.py:133,156,178` | URL path injection via `model_id` | `model_id` is interpolated directly into URLs: `f"{self.base_url}/{model_id}"` and `f"{self.QUEUE_BASE_URL}/{model_id}"`. No validation is applied. A caller passing `model_id = "fal-ai/ltx-2.3/../../admin"` or a value containing `?` / `#` / `%2f..%2f` could redirect the request to an unintended fal.ai endpoint. The gateway normalises model IDs with `_normalize_model_id` before routing decisions (gateway_unified.py:955) but passes the **original** `request.model` string directly to `fal_client.generate_video(request.model, ...)` (gateway_unified.py:975) — normalisation does not happen before URL construction. | Add an allowlist check inside each public method of `FalAIProvider`: validate `model_id` against `VIDEO_MODELS | AUDIO_MODELS | IMAGE_MODELS` and raise `ValueError` if it is not present. This is a one-liner using the existing frozensets. |
| F03 | HIGH | `fal_ai_provider.py:192,205` | URL path injection via `request_id` | `request_id` is also interpolated directly into URLs without any validation: `f"…/requests/{request_id}/status"`. The value comes from the fal.ai API response (`data["request_id"]`, line 188), so it is attacker-influenced in a supply-chain sense, but more critically it is stored in `MediaTask.task_id` and then passed back from the database via the recovery loop in `media_tasks.py:1481`. If a malformed request ID (e.g. containing `/../` or `?injected=`) were stored, it would be replayed as part of a URL on every recovery cycle. | Validate `request_id` with a strict allowlist regex such as `^[a-zA-Z0-9_\-]{8,128}$` before constructing any URL that contains it. Apply the check both when storing the value (line 188) and when consuming it in `get_queue_status` / `get_queue_result`. |
| F04 | HIGH | `media_job_validators.py:87–88` | SSRF bypass — `host.docker.internal` explicitly whitelisted | `_is_internal_hostname` returns `False` for `host.docker.internal`, meaning `validate_uri_no_ssrf` skips the private-IP check for that hostname. The comment explains this is intentional for Docker-to-host asset downloads. However, `FalAIProvider._validate_urls` explicitly **blocks** `host.docker.internal` (line 63) then calls `validate_uri_no_ssrf` which would allow it through if that first guard were bypassed or removed. The two validators are inconsistent: the provider guard fires first (line 64), but it operates only on the parsed `hostname`, not on the raw URL. A URL such as `http://HOST.DOCKER.INTERNAL/secret` (upper-case) would not match the provider's lowercase comparison only if `urlparse` normalises the hostname — which it does, so this specific case is safe — but the layered architecture creates confusion and the whitelist in the shared validator silently undermines SSRF protection for any other caller that uses `validate_uri_no_ssrf` directly. | Remove `host.docker.internal` from the whitelist in `validate_uri_no_ssrf` (or add a separate, narrowly-scoped `validate_internal_asset_uri` for the Docker worker case). At minimum, document the security implication with a `# SECURITY:` comment on the whitelist and add a unit test that verifies fal.ai URLs for `host.docker.internal` are rejected. |
| F05 | MEDIUM | `fal_ai_provider.py:91–93` | Insufficient prompt sanitisation | `_sanitize_prompt` strips only `<tag>` and `</tag>` patterns using `re.sub(r"<[^>]+>", "", prompt)`. This does not address: (a) prompt injection via instruction-style text (e.g. `"Ignore previous instructions and …"`), (b) null bytes, (c) very long prompts that can cause provider-side abuse or denial of service, (d) zero-width Unicode characters used to bypass content filters. The docstring says "Strip HTML/XML tags" — this is accurate but the function name `_sanitize_prompt` implies broader safety. Callers likely rely on it for more than HTML stripping. | The HTML stripping is appropriate for its stated purpose. Rename it to `_strip_html_from_prompt` for accuracy, or add explicit limits (e.g. `prompt[:10_000]`) and a `\x00` null byte strip. Add a length cap at the call site (the caller controls this after sanitisation). Prompt-injection defence against instruction override is out of scope at the transport layer but should be handled at the gateway layer via role-separated messages. |
| F06 | MEDIUM | `fal_ai_provider.py:76–88` | SSRF via video URL redirect — `_check_video_size` is best-effort | `_check_video_size` suppresses all `httpx.RequestError` and `httpx.HTTPStatusError` exceptions (`pass` at line 87). This means a 301/302 redirect response from the HEAD request is caught by `raise_for_status()` and silently ignored, allowing a redirect to an internal host to go undetected for the size check. More critically, the `pass` on request errors means DNS-resolution failures (including for private hostnames that `validate_uri_no_ssrf` might miss) are silently allowed through. The function is correctly labelled "best-effort" in its docstring, but the interaction with the SSRF checks above means a determined attacker who can cause the initial HEAD to fail will bypass the size gate entirely. | This is acceptable as a size check only if the SSRF check has already blocked internal URLs before `_check_video_size` is called. Verify the call order is always `validate_uri_no_ssrf` → `_check_video_size` (it is today at line 69 then 74). Add an explicit comment to `_check_video_size` stating that SSRF validation must have already run before this function is called. Change the bare `pass` to `logger.debug("fal_ai_video_size_check_skipped", url=url)` so the skip is observable. |
| F07 | MEDIUM | `fal_ai_provider.py:46` | Single shared `httpx.AsyncClient` with 300-second timeout | The client is instantiated once in `__init__` with `timeout=300.0` and is shared across all operations (queue submit, status polls, result fetches, and the HEAD size check). Three problems: (1) A single slow request to fal.ai during the HEAD check (`_check_video_size`) ties up the shared connection slot for up to 5 minutes, potentially stalling concurrent generation calls. (2) There is no `connect` timeout distinct from the read timeout — a TCP SYN to a slow host would block for 300 s. (3) The HEAD check should have a much shorter timeout (e.g. 10 s) than a generation submission (300 s). | Use `httpx.Timeout(connect=10.0, read=300.0, write=30.0, pool=5.0)` for generation calls. Pass a separate short timeout to the HEAD request in `_check_video_size` via `self.client.head(url, timeout=10.0, follow_redirects=False)`. |
| F08 | MEDIUM | `fal_ai_provider.py:99–109` | Incomplete HTTP error coverage in `_handle_http_error` | The error handler covers 401, 422, and 429. It does not handle: (a) 403 Forbidden (user quota exceeded or account suspended — currently surfaces as the generic `fal.ai error (HTTP 403)` message, which is fine, but the caller can't distinguish quota-exceeded from auth failure), (b) 5xx errors (returned as `fal.ai error (HTTP 5xx)`) — this is acceptable but callers in `gateway_unified.py` catch the resulting `ValueError` and re-raise as HTTP 500 with the string `"fal.ai video generation failed"` leaking that a downstream call failed, (c) the `data["request_id"]` access at line 188 is unguarded — if fal.ai returns a 200 with a body that lacks `request_id` (possible during provider outage or schema change), a raw `KeyError` propagates uncaught, bypassing `_handle_http_error` entirely. | Add a guard at line 188: `request_id = data.get("request_id") or raise ValueError("fal.ai queue response missing request_id")`. Add handling for 403 with a distinct error message. Ensure all callers of `_submit_queue` / `get_queue_result` are prepared for `ValueError`. |
| F09 | MEDIUM | `gateway_unified.py:990,1045` | Internal error detail leakage in HTTP 500 responses | At line 1045, the audio generation error handler raises `HTTPException(detail=f"Video generation failed: {str(e)}")` — the stringified exception is sent to the client. For fal.ai errors, `str(e)` will be one of the controlled `ValueError` messages from `_handle_http_error`, so it is safe there. However, line 990 and 1045 catch `Exception` broadly and use `str(e)` in the detail string, meaning a database error, import error, or unexpected exception could expose an internal message. Lines 697 and 1280 correctly suppress the exception string: `detail="fal.ai image generation failed"` — this is the correct pattern and should be applied consistently to video and audio. | Audit all catch-all `except Exception as e` blocks in the fal.ai routing sections. Use a fixed error string in `HTTPException.detail` and log `error=str(e)` to the structured logger only. |
| F10 | LOW | `fal_ai_provider.py:47` | API key stored in `_headers` dict — risk of accidental logging | `self._headers` contains `"Authorization": f"Key {api_key}"`. If any code path ever passes `self._headers` to a structured log call (e.g. `logger.debug("request_headers", headers=self._headers)`), the full API key will appear in the log. No current call site does this, but the risk surface exists whenever a developer adds debug logging. | Store the API key only at construction time, never retain it in a dict that could be accidentally spread into logs. A safer pattern is to pass the `Authorization` header only at the point of each `client.post` / `client.get` call via `headers={**self._headers}` where the dict is assembled from a private `_api_key` attribute just-in-time, or mark `_headers` with a comment: `# SECURITY: never log this dict`. |
| F11 | LOW | `fal_ai_provider.py:228–234` | `_derive_resolution` does not validate negative or zero pixel values | `_derive_resolution` receives `width` and `height` from the fal.ai API response JSON (line 217). No bounds checking is performed. A fal.ai response with `"width": -1` would return `"1080p"` (falls through all comparisons), which is benign. A width of `9999999` also returns `"2160p"`. The concern is that `width` and `height` are used as-is without type checking — if the API returns a string (e.g. `"3840"`) the comparisons `width >= 3840` will raise `TypeError` at runtime, propagating an unhandled exception through `get_queue_result`. | Add `if not isinstance(width, (int, float)) or width <= 0:` guard before the comparisons and return a default of `"1080p"`. The same pattern is duplicated in `media_tasks.py:_derive_fal_resolution` — fix both. |

## Summary

| Severity | Count |
|----------|-------|
| HIGH     | 3 (F01, F02, F03) |
| HIGH (architectural/layered) | 1 (F04) |
| MEDIUM   | 5 (F05, F06, F07, F08, F09) |
| LOW      | 2 (F10, F11) |

**Critical path to fix before merge:**

1. **F02 (model_id injection)** — add allowlist check at the top of each public method in `FalAIProvider`. One-liner using existing frozensets.
2. **F03 (request_id injection)** — add regex validation before URL construction in `get_queue_status` / `get_queue_result`.
3. **F01 (redirect following)** — add `follow_redirects=False` to all outbound `client.post` and `client.get` calls.
4. **F08 (unguarded KeyError on request_id)** — add a `.get("request_id")` guard in `_submit_queue`.

F04, F06, F07, F09, F10, F11 are defensible-in-depth improvements that should be addressed in a follow-up hardening pass.

No findings were identified in the six mandatory audit categories for:
- **SQL injection via raw SQLAlchemy** — none in this provider.
- **Missing `Depends(get_current_user)`** — authentication is enforced at the gateway layer before `FalAIProvider` is instantiated; the provider itself has no endpoint signature.
- **LLM prompt injection via system-prompt interpolation** — the provider does not call an LLM; prompts are forwarded as JSON body fields, not as LangChain system messages.
- **Celery task arguments containing secrets** — the recovery loop in `media_tasks.py:1469` correctly fetches the API key from the database inside the task body rather than accepting it as a task argument.
- **`print()` logging sensitive data** — no `print()` calls found in the provider or its call sites.
- **`os.environ` serialisation in responses** — no `os.environ` serialisation found.
