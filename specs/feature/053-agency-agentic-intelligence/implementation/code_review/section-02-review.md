## Review Report

### Verdict: APPROVE_WITH_FIXES

### Findings

| Severity | File:Line | Issue | Recommended Fix |
|---|---|---|---|
| HIGH | `agency_orchestrator.py:602` | **Guardrails bypassed in agentic mode.** The dispatch branch `if execution_mode == "agentic": return await self._execute_agent_node_agentic(...)` fires before the input/output guardrail checks at lines 612–639 and 809–836 in `_execute_agent_node()`. Agents with configured guardrails silently run without any input sanitisation, blocking, or redaction, and without output guardrail validation on the final answer. The spec (§ Implementation Details §5) explicitly states: "This check goes at the very top of `_execute_agent_node()`" but does NOT say guardrails should be skipped. Design Decision 5 in the spec says: "Input guardrails run once before the loop starts. Output guardrails run on the final answer." Neither path is implemented. | Move the guardrail checkpoint logic out of the agentic branch: (1) run input guardrails in `_execute_agent_node()` before dispatching to `_execute_agent_node_agentic()`; pass the (possibly redacted) `augmented_message` into the agentic method; (2) run output guardrails on `final_answer` after `_execute_agent_node_agentic()` returns, still inside `_execute_agent_node()`. |
| HIGH | `agency_orchestrator.py:519` | **`get_planning_prompt()` raises `ValueError` for unknown strategy — unhandled in agentic loop.** The spec supports three strategies: `"basic"`, `"cot"`, `"react"`. A node configured with any other string (e.g. a future extension or a typo) causes `get_planning_prompt()` to raise `ValueError`. The `try/except Exception` at line 586 would catch this and return an error string, but only after the agent-creation block is entered. The planning prompt call at line 519 is *outside* the `try` block, so the exception propagates uncaught and terminates the entire agency run. | Wrap line 519 in a try/except or add a fallback: `planning_prompt = get_planning_prompt(strategy if strategy in ("basic", "cot", "react") else "basic", max_cycles)` with a `logger.warning` for unknown strategies. |
| HIGH | `agency_orchestrator.py:526` | **Inline import inside hot loop.** `from app.services.agency_swarm_adapter import AgentConfig, AgencyConfig as SwarmAgencyConfig` is executed on every cycle of the reflection loop. Python caches module imports so this is not a correctness bug, but it triggers the module-lookup overhead on every iteration and would silently become a performance hazard if the import machinery ever changes. More critically, it means the import is not visible at module level for static analysis tools (mypy will not type-check it). | Move the imports to the top of `_execute_agent_node_agentic()` (before the loop), or better to module level with the other service imports. |
| MEDIUM | `agency_orchestrator.py:100` | **`showReasoning` field read in spec but never read in implementation.** The spec §4 lists `showReasoning: bool (default False)` as a config field that should control emission of reasoning trace SSE events. The implementation reads `planningStrategy` and `maxReflectionCycles` but never reads `showReasoning`. The spec says "Optionally emit reasoning trace if `showReasoning` is True" in step 6g. The field is a no-op today, which is acceptable if documented, but there is no comment to that effect and the field is listed as a spec deliverable. | Either implement the `showReasoning` gate (emit reasoning trace when `True`), or add a comment `# showReasoning: reserved for future use (section-05)` and document the deferral explicitly. The latter is acceptable since this is Level 1. |
| MEDIUM | `agency_orchestrator.py:560-561` | **Growing message size across cycles: no truncation cap.** On cycle N > 1, the message sent to the adapter is `augmented_message + "\n\nPrevious attempt (cycle N-1):\n" + last_response`. Over many cycles (up to `MAX_REFLECTION_CYCLES = 10` by default) this message grows to include the full text of every prior response, potentially far exceeding the model's context window. There is no check against `MAX_TOKENS_BUDGET` (which exists in `agentic_limits.py` at 100,000 tokens) and no truncation logic. A 3-cycle run on a large task could easily produce 30,000+ tokens in the final message. | Cap the `last_response` text injected from prior cycles (e.g., only include the last response, not accumulate all prior responses — which the current code already does correctly for single prior response). However, add a character/token length guard on `last_response` before injecting it. Consider truncating to `MAX_TOKENS_PER_ITERATION * 4` chars (a rough char-to-token heuristic) with a `[truncated]` marker. |
| MEDIUM | `test_completion_detection.py:407-411` | **`test_max_cycles_zero_returns_immediately` is misplaced and vacuous.** This test is in `test_completion_detection.py` but tests `clamp_to_limit()` from `agentic_limits`, not `_parse_completion`. It does not test orchestrator behaviour (that the agentic method returns immediately when cycles are 0); it only checks that `clamp_to_limit(0, 10) == 0`, which is already covered by `test_agentic_limits.py`. The behaviour of "returns immediately when max_cycles == 0" — which is an actual orchestrator invariant — has no test in `test_agentic_orchestrator.py`. | Move this assertion to `test_agentic_limits.py` (or remove the duplicate). Add a test in `test_agentic_orchestrator.py`: when `maxReflectionCycles=0`, `_execute_agent_node()` returns `""` immediately without calling `adapter.run()`. |
| MEDIUM | `test_agentic_orchestrator.py:299` | **`test_single_shot_mode_unchanged` sets `orch.db = None` as a side-channel workaround.** The comment says "Set db=None to skip tool resolution in single-shot path." Nullifying the db forces the test to avoid the tool-resolution path rather than mocking it properly. If the single-shot path ever requires the db for something other than tool resolution, this test silently stops exercising production behaviour. | Use `AsyncMock` for `db` and add a `mock_resolve_tools_for_agent` patch at the test level so the db-dependent path can run. Alternatively, document why `db=None` is acceptable in this test. |
| LOW | `agency_orchestrator.py:76` | **`_FENCED_JSON_RE` does not use `re.MULTILINE`; `$` anchors to end of entire string with `re.DOTALL`.** In Python regex, `$` with `re.DOTALL` but without `re.MULTILINE` still matches at the end of the string (or before a trailing newline). This is correct and intentional, but the regex `\s*$` would also match if the agent appended several trailing newlines after the fenced block. This is acceptable, but combining `re.DOTALL` and the `.*?` lazy quantifier means the regex could theoretically match the first `{...}` in a multi-block response if it appears before a closing ` ``` `. | No code change required. Add a comment explaining that `re.DOTALL` is needed for `.*?` to span newlines within the JSON block, and that `$` anchors to end-of-string to prevent matching mid-response blocks. |
| LOW | `test_completion_detection.py` | **Missing test: nested JSON in response body should not trigger false positive.** The `_RAW_JSON_RE` pattern `(\{[^{}]*"complete"[^{}]*\})\s*$` uses `[^{}]*` which intentionally prevents nested objects. But there is no test for a response containing `{"complete": true, "answer": "..."}` mid-text (not at the end) — verifying the `\s*$` anchor correctly rejects it. This is a distinct scenario from the current `test_parse_completion_marker_in_tool_output` test. | Add a test: response is `'Early {"complete": true, "answer": "done"} then more text'` — verify `_parse_completion()` returns `None` (completion signal not at end). |
| LOW | `test_agentic_orchestrator.py:251` | **`test_agentic_mode_calls_planning_prompt` uses fragile `call_args` introspection.** The assertion `call_args.kwargs.get("config") or call_args[1].get("config") if call_args[1] else call_args[0][0]` is brittle — it silently evaluates to `call_args[0][0]` if kwargs is empty, which would be the `user_token` string, not the config. The test could pass vacuously if the conditional short-circuits. | Simplify to `assert adapter.create_agent.call_args.kwargs["config"].instructions` contains the expected text, or use `call_args[1]["config"]`. Also assert on `"You have up to"` and the cycle count specifically rather than `or "cycles"`. |

### Summary

The core logic of this section is sound: the reflection loop, `CompletionSignal` detection, cycle SSE events, and `delegation_depth` scaffolding are all correctly implemented and match the spec. The two blocking issues are the guardrail bypass (the agentic dispatch fires before the input/output guardrail checkpoints in `_execute_agent_node()`, directly contradicting Design Decision 5 in the spec) and the uncaught `ValueError` from `get_planning_prompt()` for unrecognised strategy strings (the call is outside the `try` block). Both are required fixes before this section can be considered safe for merge. The remaining findings are correctness nits or test-quality issues that should be addressed in the same PR to avoid accumulating technical debt in the reflection loop path.
