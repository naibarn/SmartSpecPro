## Findings

| FE01 | HIGH     | apps/web/client/src/components/agency/MemoryViewer.tsx:131-132, server/routers/agency.ts:4368-4391    | CSRF / missing auth  | `deleteAgentMemory` is called with no per-row confirmation dialog. A single mis-click on the `<Trash2>` icon button permanently soft-deletes a memory entry with no undo path. More critically, the `resetAgentMemories` mutation is called without sending `agencyId`-scoped ownership to the server — the server correctly re-derives tenant/userId from `ctx`, but the client is also passing a `userId` prop (MemoryViewer line 17) that it **never uses in any mutation call**. For a domain_admin viewer the `userId` the server would use defaults to the admin's own id instead of the intended target user's id, silently resetting the wrong user's memories. | Add a per-row confirmation tooltip/dialog identical to the existing `showReset` flow. Pass `userId` to `resetAgentMemories` when `isAdmin` is true: `resetMutation.mutate({ agencyId, agentNodeId, userId: isAdmin ? userId : undefined })`. |
| FE02 | HIGH     | apps/web/server/routers/agency.ts:1148-1218, 1413-1435                                                | Feature flag bypass  | `saveBuilder` accepts `nodeType: "autonomous_agent"` and `nodeConfig.executionMode: "agentic"` for any authenticated user. There is **no server-side feature-flag guard** on either the `autonomous_agent` node type or the `agentic` execution mode in `saveBuilder`. Other sensitive node operations (Tool API exposure, MCP bridge) check `getTenantFeatureFlag` before proceeding. A user whose tenant does not have the feature enabled can POST a `saveBuilder` payload with `nodeType: "autonomous_agent"` or `executionMode: "agentic"` and it will be persisted and executed. | In `saveBuilder`, after the ownership check, add: `if (agents.some(a => a.nodeType === "autonomous_agent" || a.nodeConfig?.executionMode === "agentic")) { const ok = await getTenantFeatureFlag("AGENCY_AGENTIC_MODE_ENABLED", tenantId); if (!ok) throw new TRPCError({ code: "FORBIDDEN", message: "Agentic intelligence is not enabled for this tenant" }); }` |
| FE03 | MEDIUM   | apps/web/client/src/components/agency/MemoryViewer.tsx:118 (`m: any`)                                 | Sensitive data / type safety | The memory list renders `m.content` at line 136 via JSX text (`<p>{m.content}</p>`), which is safe from XSS. However, the loop variable is typed `any`, and `m.confidence`, `m.useCount`, `m.lastUsedAt` are rendered without guarded coercions. If the server ever returns unexpected types (e.g., a confidence value that is a stringified object), it could render as `[object Object]` or produce a NaN display. Additionally, `m.memoryType` is interpolated directly into a CSS class selector string at line 121 (`TYPE_COLORS[m.memoryType]`). If `memoryType` is not one of the four expected values, the lookup returns `undefined` and the fallback `""` is used, which is safe — but the absence of TypeScript typing means regressions go undetected. | Replace `any` with the tRPC inferred type for `agencyAgentMemories` select output. Use `Number(m.confidence ?? 0)` and `m.useCount ?? 0` with explicit defaults. |
| FE04 | MEDIUM   | apps/web/client/src/components/agency/AutonomousConfigPanel.tsx:75-83 (maxTotalIterations slider)      | Input validation gap | The `maxTotalIterations` slider enforces `min=1 max=50` at the HTML level. The server validates this range correctly (lines 1424-1426 of agency.ts). However, the `qualityThreshold` slider in `AutonomousConfigPanel` (lines 153-162) has `min=0 max=1 step=0.05` at the client but the server (`agency.ts:1433-1435`) only validates `0 <= n <= 1` with no step constraint. A crafted request (bypassing the slider) could send `qualityThreshold: 0.123456789`, which passes server validation but may cause unexpected float-precision behaviour in the Python executor. This is low-severity on its own, but is worth noting that the `reflectAfterSteps` slider in `AutonomousConfigPanel` (lines 114-121, `min=1 max=10`) has **no corresponding server-side validation in `saveBuilder`** — only `maxPlanDepth`, `maxTotalIterations`, and `qualityThreshold` are validated at lines 1418-1435; `reflectAfterSteps` and `delegationMode`/`budgetAllocation` are stored as raw `z.record(z.unknown())` with no enum or range check. | Add server-side validation in `saveBuilder` for `reflectAfterSteps` (int, 1-10), `delegationMode` (enum: `self_only`, `delegate_to_agents`, `auto`), and `budgetAllocation` (enum: `equal`, `proportional`, `dynamic`) inside the `autonomous_agent` superRefine block. |
| FE05 | MEDIUM   | apps/web/client/src/components/agency/ExecutionTimeline.tsx:43, 60, 72                                | Uncontrolled data rendering | `evt.data.planVersion`, `evt.data.subtaskCount`, `evt.data.subtaskId`, and `evt.data.tokensUsed` are coerced to strings via `String()` and rendered directly as JSX text content. This is not XSS-vulnerable (React escapes text children), but there is no length cap on any of these. A malicious or malfunctioning SSE event with a `subtaskId` of 10,000 characters would render fully, potentially breaking the panel layout. The `agencyId` and `runId` props are accepted but never used in the component — they are presumably intended for future SSE subscription, but currently there is no such subscription, meaning the `events` prop must be fed from the parent (RunMonitorPanel or similar). If that parent ever passes unfiltered SSE data, the length issue becomes active. | Add length-cap truncation: `String(evt.data.subtaskId).slice(0, 128)` for display. Add a check for `String(evt.data.planVersion).length > 20` with a fallback of `"?"`. |
| FE06 | LOW      | apps/web/client/src/components/agency/MemoryViewer.tsx:78-85                                          | UX / destructive action | The "Reset All" button has a confirmation panel (`showReset` state), which is correct. However, the individual per-row delete button (line 127-134, `<Trash2>` icon) fires `deleteMutation.mutate()` immediately on click with no confirmation. Long-term memory entries may be valuable user data. A single mis-click causes an irreversible soft-delete with no toast notification and no undo. There is no loading/disabled state on the trash button during the mutation, so rapid double-clicks could dispatch the same `memoryId` twice (the server handles this idempotently via `isActive: false`, so no data corruption occurs, but it is still poor UX). | Add `disabled={deleteMutation.isPending}` to the trash button. Consider showing a Sonner toast with a brief timeout-based undo, or at minimum a confirmation tooltip on single-row delete. |

## Summary

**Overall verdict: CONDITIONAL PASS — 2 HIGH findings must be resolved before merge.**

The five components are clean on the most critical vectors: no `dangerouslySetInnerHTML`, no `localStorage` token storage, all mutations go through tRPC (no raw `fetch()`), and no secrets appear in component props or state.

The two HIGH findings (FE01: admin userId forwarding gap in `resetAgentMemories`; FE02: missing feature-flag gate in `saveBuilder` for autonomous/agentic nodeType) are blocking. FE02 in particular allows any authenticated user on any tenant to persist `autonomous_agent` nodes or `agentic` execution mode regardless of tenant feature entitlement, which is a billing/access-control gap.

The MEDIUM findings (FE04 missing `reflectAfterSteps`/`delegationMode`/`budgetAllocation` server validation; FE05 uncapped SSE data length) should be resolved in the same PR. The LOW findings (FE06 missing per-row delete confirmation; FE07 accessibility) can follow in a hardening pass.
