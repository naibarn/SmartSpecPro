## Findings Table

| ID  | Severity | File:Line | Anti-Pattern | Description | Recommended Fix |
|-----|----------|-----------|--------------|-------------|-----------------|
| F01 | CRITICAL | `mcp_oauth_manager.py:365` | Missing SSRF validation on OAuth URLs | `_token_request`, `_refresh_token`, and `revoke_token` call `httpx.AsyncClient.post()` with caller-supplied `token_url` and `revocation_url` with zero SSRF validation. An attacker who controls MCP server configuration (or whose OAuth provider is compromised) can redirect token requests to `169.254.169.254`, Redis, or any internal service. | Apply `_validate_url_scheme` + `_resolve_and_validate_dns` (already implemented in `mcp_client_manager.py`) to every URL before making an outbound HTTP call in `_token_request`, `_refresh_token`, and `revoke_token`. |
| F02 | CRITICAL | `mcp_oauth_manager.py:365` | `_find_state_data` performs an unkeyed Redis GET on the raw state nonce | The comment at line 363–365 reads: `result = await self._redis.get(state)`. The Redis key stored in `initiate_auth_code_flow` is `mcp:oauth:state:{tenant_id}:{server_id}:{state}` — not simply the state nonce. The `get(state)` call will **never match** any real key in production, causing every `handle_callback` invocation to raise `OAuthFlowError("Invalid or expired state parameter")` — the entire authorization_code + PKCE flow is broken. The comment acknowledges this ("The mock returns data for any key") — it was written to pass unit tests but has never worked against a real Redis instance. | The fix must build and look up the correct namespaced key. Because the callback only receives the `state` nonce, use `SCAN MATCH mcp:oauth:state:*:{state}` with a small COUNT hint, consume the cursor fully, and return the first match. Alternatively, maintain a reverse index key `mcp:oauth:state:nonce:{state}` pointing to the full namespaced key during `initiate_auth_code_flow`. Delete both keys in `handle_callback`. |
| F03 | CRITICAL | `mcp_oauth_manager.py:149,186,261,334` | `client_secret` serialized in plaintext into Redis OAuth state | `initiate_auth_code_flow` stores the full `state_data` JSON blob — which includes `"client_secret": client_secret` — in Redis at `mcp:oauth:state:{tenant_id}:{server_id}:{state}` (line 180–188). The client_secret then travels: Redis → `json.loads` → `_token_cache` in process memory. Any Redis compromise or memory dump exposes all MCP OAuth client secrets for all tenants. The `_token_cache` dict also stores client secrets in-memory indefinitely (lines 149, 261, 334). | Do not store the client_secret in Redis state. Store only `server_id` and `tenant_id` in Redis; look up the decrypted secret from the DB inside `handle_callback` using those IDs. Similarly, remove `client_secret` from the in-memory `_token_cache`; always resolve it from encrypted DB storage at refresh time. |
| F04 | HIGH | `mcp_oauth_manager.py:186,261` | OAuth state also stores `authorize_url` / `token_url` from user-supplied input without validation | `initiate_auth_code_flow` accepts `authorize_url` and `token_url` as parameters and stores both in Redis state without any SSRF check. `handle_callback` then reads `token_url` back from Redis and calls `_token_request` against it. Combined with F01, a caller with write access to `mcp_servers` can install a `token_url` of `http://169.254.169.254/latest/meta-data/` or `http://localhost:6379` and have the token exchange request directed there. | Validate `authorize_url` and `token_url` using `_resolve_and_validate_dns` at call time in `initiate_auth_code_flow`; reject private/loopback targets before storing in Redis. |
| F05 | HIGH | `mcp_client_manager.py:201,245` | Connection key collision — no tenant isolation in connection registry | The connection map key for HTTP is `f"http:{tenant_id}:{normalized_url}"` (line 201) and for streamable is `f"streamable:{tenant_id}:{normalized_url}"` (line 245). Two tenants connecting to the same third-party MCP URL will map to **different** keys (tenant ID is included), which is correct. However, `call_rpc` accepts any `McpConnection` object and makes no check that `conn.tenant_id` matches the currently-authenticated tenant. A caller who obtains a `McpConnection` object from another tenant's context can use it freely. | `call_rpc` should accept a `caller_tenant_id: int` parameter and assert `conn.tenant_id == caller_tenant_id` before proceeding; raise `McpConnectionError` on mismatch. This guard must also exist in `health_check` and `disconnect`. |
| F06 | HIGH | `mcp_oauth_manager.py:87-115` | In-memory `_token_cache` is process-global and never evicted | `_token_cache` is a plain dict keyed by `server_id` (integer). It holds access tokens, refresh tokens, and — per F03 — client secrets. Tokens are only removed when a new token is fetched; expired but non-refreshable tokens, tokens for deleted servers, and tokens belonging to deprovisioned tenants stay in memory indefinitely. In a multi-worker deployment (uvicorn `--workers N`), each worker maintains its own cache independently, making revocation via `revoke_token` unreliable — only the worker that owns the cache entry is affected. | Persist token cache entries to Redis under a namespaced key (tenant-scoped). On revocation, delete the Redis key so all workers observe the revocation on next `get_token` call. Add TTL matching `expires_at` to Redis entries so memory is reclaimed automatically. Remove `client_secret` from the cached payload (see F03). |
| F07 | HIGH | `api/health.py:204-215` | `/health/mcp` endpoint has no authentication guard | The `mcp_health_check` endpoint at `GET /health/mcp` is registered under the `health.router` which is mounted without any auth dependency (confirmed in `main.py:329`). The endpoint exposes `server_count`, `active_connections`, and `stdio_process_count` from the live MCP connection pool. While not individually destructive, this is operational intelligence (how many stdio sandboxes are active, how many servers are connected) that aids enumeration of the platform's internal tool integrations. The base `/health` check is also unauthenticated, but this endpoint discloses MCP-specific connection state. | Add `current_user: User = Depends(get_current_user)` to `mcp_health_check`, or at minimum require an internal service token (`X-Internal-Key` header checked against a secret) consistent with how other internal-facing endpoints are protected in this codebase. If the intent is infrastructure monitoring only, gate it on IP allowlist at the Nginx level. |
| F08 | MEDIUM | `mcp_client_manager.py:556-577` | `resolve_env` silently substitutes empty string for missing `$ref:encrypted` keys | When `env` contains a `$ref:encrypted` placeholder and `encrypted_env` does not have the corresponding key, `resolve_env` resolves the value to `""` (line 574) and logs only a warning. The empty string is then passed as the environment variable value to the sandbox container. Depending on the tool, an empty secret may be worse than a failure — e.g., an empty `OPENAI_API_KEY` causes the container's MCP server to make unauthenticated API calls that may still partially succeed or produce misleading errors. | Fail-closed: if a `$ref:encrypted` key is missing from `encrypted_env`, raise `McpConnectionError(f"Required env secret '{key}' not found in encrypted storage")` rather than substituting empty string. |
| F09 | MEDIUM | `mcp_client_manager.py:396-413` | HTTP response body accumulated in memory before size check is enforced | The streaming byte counter at line 390 does enforce the 1 MB limit during accumulation. However, line 413 calls `json.loads(body)` on the entire in-memory buffer. If the MCP server sends a response with a valid JSON preamble but continues with a follow-on stream (chunked encoding, keep-alive) that arrives only after the chunk loop exits, the already-accumulated `body` can contain valid but oversized JSON. This is a minor risk in practice but can be triggered by a slow MCP server that drips chunks. Additionally, if JSON parsing fails, the raw `body` bytes (up to 1 MB) surface in the `McpConnectionError` string propagated to callers, which may log or return it. | Wrap `json.loads(body)` in a try/except and do not include the raw body in the exception message. The existing `McpConnectionError(f"HTTP {resp.status_code}: {body[:200]}...")` at line 410 is correctly limited to 200 bytes — apply the same limit to parsing failure messages. |
| F10 | MEDIUM | `mcp_config_watcher.py:170-172` | Raw SQL query with no parameterization (static, but expands a risk surface) | Line 170–172 executes `text("SELECT id, name, config, config_hash, enabled, transport_type FROM mcp_servers")`. The query itself is static and not injectable. However, the pattern uses `text()` directly without a parameterized call, setting a bad precedent for future edits to this function that may add WHERE clauses with server_id or tenant_id filtering. There is no tenant-scoping applied — the query returns all rows from `mcp_servers` across all tenants. | Add tenant-scoped filtering: `text("SELECT ... FROM mcp_servers WHERE tenant_id = :tenant_id")` with bound parameters. Even in the watcher context (where the watcher monitors its own tenant), this is defense-in-depth against IDOR if the watcher is instantiated per-tenant. |
| F11 | MEDIUM | `mcp_client.py:33-54` | SSRF check in `mcp_client.py` does not perform DNS resolution — only checks literal IPs and hostname blocklist | `_validate_mcp_url` blocks literal private IPs and a short blocklist of hostnames (line 19–22). It does not resolve DNS. A hostname like `my-internal-server.attacker.com` that resolves to `10.0.0.1` passes the check. This is the gap that `mcp_client_manager.py`'s `_resolve_and_validate_dns` was designed to close, but `mcp_client.py`'s `call_tool` and `discover_tools` use only the weaker validator. | Replace `_validate_mcp_url` in `mcp_client.py` with a call to `mcp_client_manager.McpClientManager.connect_http()` (which runs the full DNS resolution check) rather than making raw `httpx.AsyncClient` calls. Alternatively, import and call `_resolve_and_validate_dns` from `mcp_client_manager` before establishing each connection in `discover_tools` and `call_tool`. |
| F12 | LOW | `mcp_metrics.py:63-65` | Internal manager state exposed via public `_connections` and `_stdio_counts` attribute access | `get_mcp_health` at lines 63–65 directly accesses `manager._connections` and `manager._stdio_counts` (name-mangled by convention as private). Any caller who imports `get_mcp_health` can observe live connection objects and tenant container counts without going through a controlled API. | Add a public `get_stats() -> dict` method to `McpClientManager` that returns only the aggregate counts. `get_mcp_health` should call `manager.get_stats()`. |
| F13 | LOW | `mcp_client_manager.py:443-448` | `_call_rpc_stdio` echo-via-base64 approach may silently truncate on certain sandbox runtimes | The approach `echo {b64} | base64 -d` pipes base64-encoded JSON-RPC through the sandbox shell. The comment at line 442 correctly notes this avoids shell metacharacter injection. However, `run_command` likely has an implicit command-line length limit (Linux ARG_MAX is 2 MB but some sandbox environments set lower limits). A large RPC payload that exceeds the limit will be truncated silently, producing a truncated JSON string that fails to parse. The error is caught and wrapped as `McpConnectionError` but the underlying cause (truncation vs. bad JSON) is opaque. | Log the base64 payload length before calling `run_command`, and compare against a configured maximum (e.g., 512 KB). Raise a descriptive `McpConnectionError` if the payload would exceed the limit, rather than allowing silent truncation. |

## Critical Path to Green

The three CRITICAL findings must be resolved before merge:

1. **F01 + F04** — Add SSRF DNS validation to `_token_request`, `_refresh_token`, and `revoke_token` in `mcp_oauth_manager.py`. Validate `authorize_url` and `token_url` in `initiate_auth_code_flow` before storing in Redis.

2. **F02** — Fix `_find_state_data` to resolve the namespaced Redis key. The current `get(state)` call against a raw nonce will never match real keys and makes the entire PKCE authorization code flow non-functional in production.

3. **F03** — Remove `client_secret` from Redis OAuth state storage and from the in-memory `_token_cache`. Resolve secrets from encrypted DB storage at exchange and refresh time.

## Notes on What Is Well-Implemented

- DNS rebinding prevention in `mcp_client_manager.py` (`_resolve_and_validate_dns`) is correct and fail-closed (line 78).
- Session ID validation regex at line 40 (`[a-zA-Z0-9_-]{1,128}`) is appropriate.
- Stdio transport correctly requires `OPENSANDBOX_ENABLED=True` and caps concurrency via `MAX_STDIO_PER_TENANT` with a lock.
- Base64 encoding for stdio JSON-RPC payload (line 443) correctly prevents shell injection.
- Response streaming with 1 MB byte counter is the right approach for unbounded response protection.
- PKCE S256 implementation (`_generate_code_verifier`, `_generate_code_challenge`) is cryptographically correct.
- OAuth state nonce uses `os.urandom(32)` — sufficient entropy.
- Redis state TTL of 600 seconds is appropriate for authorization code flow.
- `config_watcher.py` correctly classifies executable vs safe fields and blocks auto-apply of URL/command/env changes.
