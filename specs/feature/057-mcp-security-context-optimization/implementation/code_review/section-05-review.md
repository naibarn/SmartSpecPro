## Review Report

### Verdict: APPROVE_WITH_FIXES

### Findings

| Severity | File:Line | Issue | Recommended Fix |
|---|---|---|---|
| HIGH | `mcpPublicServer.ts:1012-1016` | **`_mcpSessionExpired` flag not honoured in batch mode.** When a batch request contains an item with an expired session, `processSingleRequest` sets `(req as any)._mcpSessionExpired = true` and continues. The batch handler at line 1057–1069 never inspects this flag; the response is sent as `200` with the JSON-RPC error embedded in the array. The HTTP 404 path (lines 1087–1090) is only reached for single-request flow. A client cannot distinguish a network/server error from an auth error without parsing the JSON body, which breaks MCP spec semantics for batch. | In `mcpHandler`, after `Promise.all` resolves for batch mode, check `(req as any)._mcpSessionExpired` and return `res.status(404).json(responses)` if set — or better, record expiry per-item and only elevate to 404 when all items failed with session-expired rather than silently mixing error types in a 200. |
| HIGH | `mcpPublicServer.ts:1099-1104` | **`mcpDeleteHandler` performs no session ID validation before calling `redis.del`.** Any string value in the `Mcp-Session-Id` header is passed directly to `sessionKey()` and then to `redis.del`. An authenticated caller can supply a crafted value such as `"../other:key"` or an arbitrarily long string to attempt deletion of unrelated Redis keys or trigger a CPU-bound key scan. This is an IDOR-adjacent risk on the Redis keyspace. The `loadSession` path in `processSingleRequest` does at least fail gracefully for non-existent keys, but the DELETE handler bypasses even that. | Apply UUID format validation (matching the pattern used by `randomUUID()`) before calling `redis.del`. Reject non-UUID session IDs with `204` (no information leakage on whether the key existed). Example: `const UUID_RE = /^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$/i; if (!UUID_RE.test(sessionId)) { res.status(204).end(); return; }` |
| MEDIUM | `mcpPublicServer.ts:977` | **`isNotification` variable declared but never used.** `const isNotification = id === undefined \|\| id === null` is computed at line 977 but the variable is never referenced after that. This is dead code and obscures the actual notification-detection logic (which is entirely handled by the `method === "notifications/initialized"` check at line 980). | Remove the `isNotification` declaration. If generic notification support for arbitrary `method` names without `id` is planned, the logic should key on the absence of `id` in the dispatch switch, not a local variable. |
| MEDIUM | `mcpPublicServer.ts:988-990` | **Concurrent `initialize` calls in the same batch silently lose all but the last session ID header.** `Promise.all` processes batch items concurrently. If a batch includes two `initialize` calls, both write to `(req as any)._mcpNewSessionId` independently; the last writer wins and the earlier session ID is silently dropped. The client receives a header for only one of the two sessions with no indication that a second session was created. This is a latent bug — the MCP spec does not allow two `initialize` calls in one batch, but the server should reject rather than silently corrupt. | Before processing the batch items, validate that at most one item has `method === "initialize"`. If more than one is present, return a top-level JSON-RPC error (`-32600 Invalid Request`) with a descriptive message rather than proceeding. |
| MEDIUM | `mcpPublicServer.test.ts:170-182` | **`notifications/initialized` test does not assert the HTTP 204 path correctly for notifications with a valid session.** The test sends the notification without any session-expiry risk (session is initialized first), which is correct, but the assertion on `res.status === 204` is actually verifying the path through `mcpHandler` where `result === null`. However, the test does not cover a second important case: a `notifications/initialized` sent as part of a batch should produce no entry in the response array. There is no batch test that mixes a notification with regular requests and then verifies `responses.length` decreased by the notification count. | Add a batch test: `[{method:"tools/list", id:1}, {jsonrpc:"2.0", method:"notifications/initialized"}]` and assert the response array has length 1 (notification excluded). |
| MEDIUM | `mcpPublicServer.test.ts:120-139` | **Batch size rejection test asserts `res.status` is `200` with a JSON-RPC error body, but this is an ambiguous contract.** The test at line 137 expects `res.status` to be `200`. A 200 response with a JSON-RPC error object at the top level is confusing — HTTP clients that inspect status codes only will consider the request successful. The MCP spec does not prohibit returning `400` for a malformed batch. The current implementation does return `200` (confirmed at `mcpPublicServer.ts:1053`). The test faithfully matches the implementation, but the implementation choice merits a comment explaining why 200 was chosen over 400. | This finding does not block merge but a code comment should be added at `mcpPublicServer.ts:1052–1054` explaining that `200` is returned (rather than `400`) because JSON-RPC 2.0 §5 requires error responses to always be `200 OK`. Alternatively, confirm against the MCP spec whether a batch-too-large condition warrants an HTTP-level 4xx. |
| LOW | `mcpPublicServer.test.ts:185-221` | **Session termination tests do not cover DELETE with no `Mcp-Session-Id` header.** The spec guidance (section-05-spec-compliance.md) shows that DELETE with a missing session ID should still return `204` (no-op). There is no test for this case. The implementation handles it correctly (the `if (sessionId)` guard at line 1100), but the happy-path-only coverage means a regression that converts the no-op to an error would not be caught. | Add a test: `DELETE /v1/mcp` without any `Mcp-Session-Id` header, assert `res.status === 204`. |
| LOW | `mcpPublicServer.test.ts:142-168` | **Protocol version negotiation tests do not assert the `Mcp-Session-Id` response header.** Both negotiation tests (`supported version` and `unsupported version`) verify `res.body.result.protocolVersion` only. Neither checks that `res.headers["mcp-session-id"]` is set. A regression that stops returning the session ID header would pass these tests silently, while clients following the negotiation flow would fail to retrieve their session ID. | Add `expect(res.headers["mcp-session-id"]).toBeDefined()` to both protocol-version negotiation tests. |

### Summary

The core spec compliance features are correctly implemented: batch routing, version negotiation, `notifications/initialized`, `ping`, DELETE-based session termination, and HTTP 404 for expired sessions all work as designed for the common single-request path. Two HIGH findings require fixes before merge: the `_mcpSessionExpired` HTTP 404 semantics are not propagated into batch responses, and the DELETE handler passes unvalidated header input directly to `redis.del` without UUID format checking. Two MEDIUM findings (dead `isNotification` variable and no guard against duplicate `initialize` in a batch) are straightforward one-to-five line fixes. The test suite covers all eight spec-required scenarios and the auth setup refactor in `makeApp` correctly mirrors the production middleware pattern.
