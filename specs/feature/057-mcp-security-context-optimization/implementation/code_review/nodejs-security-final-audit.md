## Findings Summary

| ID  | Severity | File:Line | Anti-Pattern | Description | Recommended Fix |
|-----|----------|-----------|--------------|-------------|-----------------|
| M01 | HIGH | `mcpServers.ts:649-651` | IDOR — missing tenant isolation on DELETE | `removeAssignment` verifies ownership via a SELECT+JOIN (line 631-643) but the subsequent DELETE uses only `eq(mcpServerAssignments.id, input.id)` with no tenantId guard. A race window exists between the SELECT and DELETE; more critically, the DELETE WHERE clause has no secondary isolation, meaning the guard can be trivially bypassed if the SELECT-based check is ever refactored away. | Change DELETE to: `.where(and(eq(mcpServerAssignments.id, input.id), eq(mcpServers.tenantId, ctx.user.tenantId)))` via the same inner join pattern, or pass the verified `assignment.id` from the SELECT result instead of `input.id` (they are the same value but naming the verified source makes the intent explicit). |
| M02 | HIGH | `mcpServers.ts:226-268` | Missing SSRF validation on `create` | The `create` mutation stores `input.config.url` (for `http` and `streamable_http` transport types) into the database without calling `sanitizeUri()` or `assertPublicIp()`. When this URL is later used by `testConnection` or `listDiscoveredTools` SSRF protection fires, but the URL is stored unchecked. A malicious admin can persist a private-IP URL (`http://169.254.169.254/...`, `http://10.0.0.1/...`) and the record will show `healthStatus: unhealthy` but the stored URL is available to any future code path that reads `config.url` without independently re-validating. The `update` mutation has the same gap (lines 295-333). | Call `sanitizeUri()` and `assertPublicIp()` on the URL at write time in both `create` and `update`, matching the pattern used by `testConnection` (lines 387-389). Reject the mutation rather than store an unvalidated URL. |
| M03 | HIGH | `mcpPublicServer.ts:949` | Tool name reflected in error response (information leak) | `handleToolsCall` at line 949 returns: `throw { code: -32601, message: \`Tool not found: ${toolName}\` }`. The caller-supplied `toolName` string is reflected verbatim into the error message returned to the API consumer. Although MCP clients are expected to send tool names derived from a prior `tools/list`, an external caller can send arbitrary strings including very long values or strings containing Unicode control characters. The comment at line 1052 explicitly bans this pattern for the method name (`"M28: Do not reflect method name in error"`) but the same rule was not applied to `toolName`. | Replace with a static message: `throw { code: -32601, message: "Tool not found" }`. If a tool-name reference is needed for debugging, log it server-side (not returned to the caller). |
| M04 | MEDIUM | `mcpServers.ts:589-597` | Type mismatch in `assignToTarget` agent ownership check | `agencyAgents.id` is `varchar(36)` (UUID string) in schema.ts (line 4866). `input.targetId` is a `z.string().min(1).max(36)`, so it is always a string. The comparison `eq(agencyAgents.id, input.targetId)` is correct. However, `agencyAgents.id` is `varchar`, while `mcpServerAssignments.targetId` is also `varchar(36)`. When `targetType === "agent"`, the ownership check joins through `agencies` to verify `tenantId` (line 594) — this is correct. The gap is that `targetId` has no UUID format constraint in the Zod schema (`z.string().min(1).max(36)` accepts any 36-char string), enabling an admin to assign an MCP server to a fabricated agent ID that passes the ownership check due to a NOT_FOUND error being thrown but does not prevent the `targetId` from being stored as a garbage value if the check logic is ever changed. Additionally, there is no input validation that `targetId` for `targetType === "tenant"` is the caller's own tenantId beyond the explicit string-equality check at line 577 — a subtle difference in UUID casing could bypass this. | Add `z.string().uuid()` for agent and agency `targetId` values, or add a `.superRefine()` that applies UUID format validation when `targetType` is `"agent"` or `"agency"`. |
| M05 | MEDIUM | `mcpPublicServer.ts:920-925` | `Number()` cursor conversion accepts floating-point and scientific notation | The cursor is converted via `Number(rawCursor)` (line 921). The subsequent guard on line 923 correctly rejects non-integers and out-of-range values via `Number.isInteger(cursor)`. However, `Number("1e2")` → `100` (integer, passes), `Number("1.0")` → `1` (integer via `Number.isInteger`, passes). These are not exploitable bypass paths given the guard, but `Number("  50  ")` (with surrounding whitespace) also silently coerces to `50`, which the spec does not intend. The cursor is meant to be an opaque string token returned by a prior `tools/list` response, not a freeform numeric input. | Validate that the raw cursor string contains only digits before numeric conversion: `if (rawCursor !== undefined && !/^\d+$/.test(String(rawCursor)))` throw invalid cursor. This closes whitespace-coercion and scientific-notation edge cases and enforces the opaque-token semantic. |
| M06 | MEDIUM | `mcpServers.ts:108-129` | HTTP/streamable_http config headers not validated on `create` | `validateHeaders()` is called (line 230-232) only when `"headers" in input.config && input.config.headers` is truthy. For `httpConfigSchema` (line 108-113), `headers` is optional. If omitted, validation is skipped — this is intentional and correct. However, the `streamableHttpConfigSchema` (line 124-129) has the same `headers` field but the `create` mutation only checks `"headers" in input.config`, which evaluates to `false` when `headers` is absent. This means an attacker who sends `{ headers: {} }` (empty object, truthy key exists) triggers validation, but omitting `headers` entirely skips it. The gap is that if `headers` is later added to a stored config via an update that forgets the guard, the BLOCKED_HEADERS protection is bypassed. This is a defense-in-depth issue rather than an active bypass since omitting blocked headers is safe. The same pattern applies to `update` (line 291). | Normalize the guard: call `validateHeaders(input.config.headers)` unconditionally (the function already returns early on `undefined`/`null` at line 48). Remove the `"headers" in input.config` outer check. |
| M07 | MEDIUM | `mcpPublicServer.ts:700` | `PYTHON_BACKEND_URL` falls back to `http://localhost:8000` with no warning | The tool dispatch for `smartspec.agency.tools.call` (line 699) reads `process.env.PYTHON_BACKEND_URL || "http://localhost:8000"`. If this env var is unset in a deployment where the Python backend is on a different host or port, the call silently succeeds against localhost (potentially hitting a different service on port 8000). Unlike `SMARTSPEC_PROXY_TOKEN` which emits a startup `console.warn` when missing, there is no equivalent warning for `PYTHON_BACKEND_URL`. | Add a startup warning (matching the `SMARTSPEC_PROXY_TOKEN` pattern used elsewhere in the codebase) when `PYTHON_BACKEND_URL` is not set. Alternatively, reference the canonical `ENV.pythonBackendUrl` constant if it exists, rather than a raw `process.env` read with a localhost fallback. |
| M08 | LOW | `mcpPublicServer.ts:1055-1061` | Thrown JSON-RPC errors expose `err.message` from arbitrary thrown objects | In `processSingleRequest` (line 1055-1061), if a thrown value has a numeric `.code` property it is forwarded to the caller via `jsonRpcError(id, err.code, err.message)`. Any service-layer code that throws a plain object with `{ code: number, message: string }` will have its message reflected to the external caller unchanged. The `dispatchToolCall` function at line 714 throws `{ code: -32603, message: \`Tool execution failed: ${response.status}\` }` — the HTTP status from the Python backend is included in the message. While a status code is low sensitivity, future callers that throw objects with more descriptive messages (e.g., DB errors wrapped by service code) could inadvertently leak internal details. | Restrict forwarded error messages to a static allowlist or strip messages from codes other than `-32602` (invalid params) and `-32601` (method not found). For `-32603` (internal error), always use a generic message and log the original. |
| M09 | LOW | `mcpServers.ts:79-101` | `toResponse()` returns `config` JSONB verbatim | The `toResponse()` helper (line 79-101) includes `config: server.config` in the response. The `config` object for `http`/`streamable_http` transports contains the server URL and optional headers. For `stdio` transport, it contains `command`, `args`, `env`, and `packageIntegrityHash`. The `env` field of `stdioConfigSchema` (line 119) is a `z.record(z.string())` with no restrictions — it may contain sensitive environment variable values (API keys, tokens) set by the admin when registering a stdio-based MCP server. These are returned to any admin who calls `list` or `getById`. | Apply the same encrypted-column pattern used for OAuth tokens: do not return `env` contents in the response. Return `hasEnv: !!(config.env && Object.keys(config.env).length > 0)` instead. Alternatively restrict `env` values to be stored encrypted via `crypto.ts` and return only key names. |

## Positive Findings (Confirmed Clean)

The following areas were explicitly audited and found to be correctly implemented:

- **Tenant isolation on all CRUD SELECT/UPDATE/DELETE paths:** `list`, `getById`, `create`, `update`, `delete`, `testConnection`, `listDiscoveredTools`, `assignToTarget` (all WHERE clauses include `eq(mcpServers.tenantId, ctx.user.tenantId)`). The `update` DELETE path (line 330) correctly includes tenantId in the WHERE clause.
- **Auth middleware:** All procedures use `adminProcedure` or `rateLimitedAdminProcedure` from `_core/trpc`. No public procedure is used for any mutation.
- **Rate limiting on `testConnection`:** Uses `rateLimitedAdminProcedure` (line 361) — the only mutation that makes an outbound network call per request.
- **OAuth secret encryption:** `oauthClientSecret` is passed through `encrypt()` before storage (lines 257, 323). The `toResponse()` helper returns `oauthConfigured: boolean` instead of the ciphertext.
- **Zod input validation:** All procedures have `.input(zodSchema)`. Schemas use `.strict()` on config objects to prevent extra field injection.
- **SSRF on `testConnection` and `listDiscoveredTools`:** Both call `sanitizeUri()` then `assertPublicIp()` before making any outbound fetch (lines 387-389, 486-488).
- **Header injection blocking:** `validateHeaders()` blocks `Host`, `Cookie`, `X-Forwarded-*` headers from being stored in server configs.
- **tools/call scope enforcement:** `handleToolsCall` re-checks `session.scopes` on every invocation (lines 953-958), preventing scope-elevation via a stale tools/list cursor.
- **Pagination cursor bounds:** `Number.isInteger` + `cursor >= 0` + `cursor <= 100000` guards prevent negative-index or overflow attacks on the `allTools.slice()` call.
- **Batch DoS protection:** `MAX_BATCH_SIZE = 100` enforced at line 1077-1079; multiple `initialize` calls in one batch rejected at line 1083-1086.
- **Tool name regex on discovery:** `mcpToolNameRegex` (`/^[a-zA-Z0-9_-]+$/`) applied to discovered tool names before namespacing (line 532), preventing prototype pollution or path-separator injection.
- **Session ID UUID format enforcement:** `UUID_RE.test(sessionId)` validated before Redis key construction in `mcpDeleteHandler` (line 1139), preventing Redis key prefix injection.
- **configHash computed server-side:** `computeConfigHash` is called with the validated config object, not a client-supplied hash, so clients cannot spoof the hash (lines 235, 317).
- **Cross-tenant assignment prevention for agencies and agents:** `assignToTarget` verifies agency tenantId (line 584) and agent-through-agency tenantId (line 594) before inserting the assignment record.

## Priority Order for Remediation

1. **M01** (HIGH) — IDOR on removeAssignment DELETE: straightforward WHERE clause fix, zero risk of regression.
2. **M02** (HIGH) — SSRF gap on create/update: add two `assertPublicIp` calls, mirrors existing testConnection pattern exactly.
3. **M03** (HIGH) — Tool name reflection: one-line change, directly contradicts the M28 comment in the same file.
4. **M04** (MEDIUM) — targetId UUID validation: add `.uuid()` to Zod schema for agent/agency target types.
5. **M05** (MEDIUM) — Cursor digit-only validation: add one regex check before `Number()` conversion.
6. **M06** (MEDIUM) — Header validation guard simplification: remove outer `"headers" in` check.
7. **M07** (MEDIUM) — PYTHON_BACKEND_URL missing startup warning.
8. **M08** (LOW) — Error message forwarding discipline.
9. **M09** (LOW) — Stdio `env` field exposure in toResponse.
