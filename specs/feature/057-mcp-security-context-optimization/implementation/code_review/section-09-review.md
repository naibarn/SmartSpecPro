| HIGH | `test_long_term_memory.py:388` | `embedding_service=object()` does not correctly simulate the SQL fallback path. The fallback is triggered when `_generate_embedding` returns `None` (not a 1536-length list). `object()` has no `embed` or `generate_embedding` attribute, so `getattr(service, "embed", None)` returns `None` and `_generate_embedding` returns `None` — which does happen to trigger the fallback. However, the test then asserts `mock_session.execute.await_count == 2` without verifying *which* execute call was the SQL fallback and not the vector query. The intent is unambiguous, but the assertion conflates the SELECT and the UPDATE, not the vector-vs-SQL path distinction. A second memory with an embedding present would silently cause the test to take the vector path and still pass. Replace `object()` with `AsyncMock()` with no `embed` attribute set, and add a negative assertion that `"embedding <=> CAST"` does NOT appear in the first execute call's SQL string. | Replace `embedding_service=object()` with a stub that has no `embed` attribute, and add `assert "embedding <=> CAST" not in str(mock_session.execute.call_args_list[0].args[0])` to confirm the SQL fallback path was taken, not the vector path. |
| HIGH | `test_long_term_memory.py` (autouse fixture, line 17) | `mock_embedding_service` patches `app.services.embedding_service.get_embedding_service`, but `long_term_memory.py` imports `get_embedding_service` via a **local import inside `_generate_embedding`**: `from app.services.embedding_service import get_embedding_service`. The `patch` target must match the lookup point — because the function does a fresh `from ... import` on every call (not a module-level attribute), the patch on `app.services.embedding_service.get_embedding_service` will intercept the import correctly only if `sys.modules` has already cached the module. This works today because `embedding_service.py` is imported at test collection time, but it is fragile. Any test that runs in isolation before the module is cached could bypass the fixture and attempt a real network call. The correct patch target is `app.services.long_term_memory.get_embedding_service` (the name as it would be bound in the module at the point of import). | Change patch target to `"app.services.long_term_memory.get_embedding_service"` if the production code binds the name at the local import site, or add a module-level import in `long_term_memory.py` so the name is patchable as a stable attribute. |
| MEDIUM | `test_long_term_memory.py:106` | `test_lazy_backfill_generates_missing_embedding_on_retrieval` asserts `mock_session.commit.await_count >= 2`. The `>= 2` lower bound is intentionally loose to accommodate the `use_count` UPDATE commit and the lazy backfill commit. However, the test does not assert the order of operations: the backfill commit must happen after the use_count UPDATE commit. If the implementation ever merges these into one commit, `await_count == 1` and the test fails, but the feature still works correctly. A tighter assertion would be: assert commit is called at least once and that `memory.embedding` was set to the expected vector — the existing `assert memory.embedding == [0.0] * 1536` covers the latter but the count assertion adds no verified invariant beyond "two DB round-trips happen". Consider removing the count assertion or explicitly asserting `commit.await_count == 2` and documenting why two are required. | Either tighten to `== 2` (and document the reason) or remove the commit count assertion, leaving only `assert memory.embedding == [0.0] * 1536`. |

If `sanitize_llm_input` strips the injection completely and replaces it with `[FILTERED]`, the HTML-encoded string would not be present. If `html.escape` runs first, `[FILTERED]` would not be present. Both assertions passing simultaneously implies the implementation applies the filters to different parts of the string (e.g., `memoryType` vs `content`), but the test content only sets `content`. Verify that both assertions can pass on the same string simultaneously by tracing the sanitization and escape order in the production code; if they cannot co-exist for the test input given, one assertion is vacuously satisfied and masks a missing test for the other path. | Read `format_memories_for_injection` (lines 323–346 of `long_term_memory.py`) and confirm whether `[FILTERED]` and the HTML-encoded form can both appear in the output for this single input. ### Summary

The diff correctly adds the required mock attributes (`last_used_at`, `created_at`, `confidence`, `embedding`) to all `MagicMock` memory objects, fixing the `TypeError` that occurred when hybrid scoring code computed `(now - ref_time).days` on an untyped mock. The new tests for semantic retrieval, lazy backfill, injected embedding service, and HTML-escape injection are structurally sound. Two issues require attention before merge: the autouse fixture patches the wrong module path (should target the local import site in `long_term_memory`, not the `embedding_service` module), and the SQL-fallback test does not assert that the vector query was actually skipped, making it possible for the test to pass while silently taking the wrong code path.
