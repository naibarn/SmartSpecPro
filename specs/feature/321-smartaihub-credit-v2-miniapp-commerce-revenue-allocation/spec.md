# SPEC-321 — Credit V2 (USD 1 = 10,000), Mini App Subscriptions & Multiparty Revenue

> **Current-revision note (R1.5, 2026-11-02):** Earlier proposal text is retained for provenance. If R0.x–R1.4 ledger, commerce, runtime, or autonomous-execution assertions conflict with the final R1.5 section or current owner-decision register, R1.5 controls.

## 0. Fixed owner decisions / authority
**Owner-confirmed**: NEW nominal credit conversion is **USD 1 = 10,000 SmartSIHub credits**, replacing historical **USD 1 = 1,000 credits**. Credits per USD multiply by 10. This is a *unit redenomination*, not by itself a 90% discount or increase in real spending power. A legacy available balance of 1,000 old credits economically corresponds to 10,000 new credits at an unchanged USD value.

SPEC-207 is the existing authority for wallet, reserve, spending authorization, ledger, payment, settlement, refunds and reconciliation. SPEC-280 owns pricing, usage metering, subscription revenue attribution and skill pricing policies. SPEC-303 owns verified legal/economic rights and recipient bindings. SPEC-321 is an **additive versioned policy/compatibility specification**, not authorization to fork any of those implementations or create a second ledger.

## 1. Credit denomination and conservation
`LEGACY_CREDITS_PER_USD=1000`, `NEW_CREDITS_PER_USD=10000`, `CONVERSION_FACTOR=10`, `CREDIT_UNIT_VERSION=2`. Use integer/decimal-safe math (no floating monetary rounding); USD/reference money denominated in minor units or precise Decimal. Version and timestamp every relevant price quote, wallet reservation, historical transaction and settlement. All user-facing screens must show unit-aware labels and the effective rate.

**Existing user funds MUST NOT lose value**. Before activating new unit in a shared canonical database: inventory balances (`users.credits`), immutable credit_transactions, reserved credits, remaining subscriptions, credit_packages, all pricing tiers, usage reports, creator revenue, miniapp fees, thresholds/free grants, refunds, admins and external integrations. Check precision/capacity/overflow and concurrent open reservations. Define one-authority, idempotent, auditable conversion run with dry-run and exact before/after snapshot.

Canonical default policy: `new_available_balance = old_available_balance * 10` and `new_nominal_cost = old_nominal_cost * 10`, and likewise all current applicable price/grant/budget/reservation configurations, so economic value remains unchanged unless a separate explicit pricing revision is approved. **Do not rewrite or delete historical ledger rows**; preserve original unit/version and original transaction amount. Add a compensating redenomination adjustment event for stored nominal balances when required, and make historical reports unit-aware. Historical transactions' effective USD value should not be reinterpreted as if they were issued in the new credit version.

If a field physically stores legacy credits without a unit version, introduce the smallest audited additive metadata mapping/unit epoch necessary; no broad schema replacement. In a shared DB, never run old and new writers with different unit interpretations against the same balance; choose a coordinated transition or version-aware compatibility adapter across both legacy smartaihub.app and new smartsihub.com. Both frontends must switch to consistent displayed units through the SAME authority. Capture source SHA, effective epoch, conversion job id, per-account reconciliation digest and rollback/forward-correction procedure.

Backfill/reservation strategy must be reconciled with real schema; source-level assumption of `1 USD = 1000` is not proof all deployed packages share that effective rate. Owner target rate is binding, deployed pricing discovery still required.

## 2. Offer types
`METERED_SKILL`: each invocable Skill in a Mini App has explicit canonical Offer and cost/price metadata even if the publisher chooses a sponsor-paid zero-price offer. Each permitted execution is metered, authorized, attributed to Mini App and Skill and charged only once via SPEC-207 if the payer is metered.

`MINIAPP_SUBSCRIPTION`: defined duration (typically monthly) and fixed recurring price. Subscription coverage is **strictly limited to newly authored, App-exclusive Skills whose canonical identity is bound to this Mini App**. Such Skills are included in the subscriber's monthly price and do not deduct per-invocation credits. **Every distinct invocation of any shared, platform, marketplace, third-party, or other-App Skill remains separately billable in credits even while the Mini App subscription is active.** Subscription never converts a shared Skill into a free benefit. Track all usage internally for cost/capacity and any contracted App-exclusive Skill royalties. Do not advertise a shared Skill as included in an unlimited plan. Published fair-use/capacity limits for App-exclusive Skills may apply if economically warranted.

### 2.1 Binding and classification — owner-confirmed invariant

- `APP_EXCLUSIVE_SKILL`: a Skill **written specifically for the named Mini App** (`appId`) as a distinct implementation/release, with verifiable original code/provenance, explicit App-only ownership/execution binding, and no permitted reuse from other Apps, central Skill Registry shared offers or unrelated workflows. Multiple deployments/white-label domains of the **same canonical App identity** may use that exclusive Skill subject to its App license; different App identities may not silently share it.
- `SHARED_BILLABLE_SKILL`: any pre-existing reusable Skill, Skill Registry/marketplace Skill, Core Skill, external/third-party Skill, Skill from another App, or a Skill that has been published/authorized for use by another App or workflow. This remains pay-per-use even when called from inside an App-exclusive Skill or an Agent workflow. Rebranding, aliasing, wrapping, re-exporting, forking metadata or copying an unchanged shared implementation MUST NOT confer subscription coverage.
- `UNVERIFIED_SKILL`: provenance, exclusive code origin or binding cannot be demonstrated. It MUST NOT receive subscription exemption. Quote a per-call price before execution or make the affected action unavailable until the Skill is classified; do not freeze unrelated Mini App features.
- `APP_EXCLUSIVE_SKILL` can have a separately contracted creator/licensor with royalty rights, but that contract does NOT make it reusable by another App. An App-private Skill invoking a shared Skill has an **independent metered child invocation** for each shared call; the parent subscription does not conceal those costs.
- First-party provider SDK/API calls are not automatically *Shared Skills* merely because they use a common vendor. Their cost is borne by the App's commercial policy when occurring inside an App-exclusive Skill, unless the App deliberately invokes a distinct shared billable Skill/capability. Do not relabel a shared Skill as direct provider I/O to evade billing.

### 2.2 Per-invocation billing and subscriber disclosure

Classify Skill using authoritative `skillId`, immutable `skillVersion`, `ownerAppId`, `scope`, registry visibility, actual dependency graph and effective `policyVersion` at **server-side admission time**, not the browser flag or publisher's marketing label. Persist a signed/versioned coverage decision with every action and `worker_jobs` record: `APP_EXCLUSIVE_INCLUDED` or `SHARED_METERED` (or `UNVERIFIED`). For the latter, resolve price and payer, display/offer the applicable quoted credits, authorize and reserve before external side effects, settle once when the logical invocation qualifies for charge, and refund/reconcile failures per SPEC-207.

Every **distinct accepted** shared-Skill invocation is charged once, including nested calls from subscription functions and headless Agents. Repeated Queue deliveries/retries of the same logical call are NOT new billable invocations and MUST NOT debit again; create a new stable child invocation ID when a workflow actually invokes the shared Skill a second time. A failed/rejected/non-executed call follows existing refund/no-charge policy; "charge every invocation" does not authorize charging duplicates or failed unadmitted attempts.

If an App-exclusive Skill later becomes shared or its pricing classification changes, update its offer/policy version; **do not silently start deducting credits from existing subscribers**. Before any newly metered invocation, show the new terms and require the ordinary per-call authorization/consent required by current user preferences. If consent is absent, block *that paid action* without silently granting free shared execution. Preserve prior subscription invoice terms and use a clear replacement/migration offer where needed.

Subscription invoice and marketplace listing MUST separately disclose **included App-exclusive Skills** and **external/shared Skills charged per use**. UI, WebMCP, remote MCP and headless HTTP MUST apply the exact same classification/quote/reserve/settle path. No alternative API route may bypass metering.

Optionally support trials, seats, team subscriptions, sponsored entitlements, usage tiers, annual billing and coupons through additive Offer policy; don't require all to launch the first two offer types. Currency USD/THB displays may use FX snapshot but credit denomination remains specified.

## 3. Four canonical economic roles (not necessarily four unique recipients)
1. `PLATFORM_INFRA`: SmartSIHub Core/platform infrastructure owner.
2. `TENANT_INFRA`: white-label tenant/operator/hoster, potentially own domain and Cloudflare account.
3. `MINIAPP_OWNER`: publisher/app owner; may self-host on platform or own Cloudflare account.
4. `SKILL_OWNER`: owner/licensor of an executed Skill; multiple Skills/owners may participate in a request.

**Exactly four revenue-allocation roles** are permitted in the Mini App / Skill commerce split: `PLATFORM_INFRA`, `TENANT_INFRA`, `MINIAPP_OWNER`, `SKILL_OWNER`. These are role slots, not necessarily four distinct users. Every payable allocation is a **canonical credit grant to the verified recipient user wallet** through existing SPEC-207 writer/ledger, carrying its role and source-event attribution; when several roles bind to one user, credits can be consolidated in the displayed balance while distinct role receipts are preserved. Where an owner is an organization, resolve its explicitly authorized recipient-user/wallet binding; do not pay a guessed admin or an email address. Missing roles follow a versioned, disclosed allocation policy; no silent transfer to Platform. No universal split percentages are implied.

**Affiliate/Referral MUST NOT enter the four-role revenue split or become a fifth recipient role.** A qualified referral receives a **single, separately funded promotional credit award** to the qualifying user's existing credit wallet, through the canonical credit ledger, keyed to a unique qualifying referral. The award is independent of ongoing app/skill revenue, not a recurring commission, not a percentage of every purchase, and not a multi-level referral tree. Any co-creator, agency/service contractor or channel partner is compensated under a separately negotiated service arrangement or legitimately assigned one of the four existing owner roles—not by adding recipient slots to each invocation. Payment processors, taxes, and cloud compute expenses remain expense/tax data, never recipient roles.

## 4. Pricing / allocation waterfall
**Credit-first model; no external cash payout in this implementation phase.** For each recognized paid usage or monthly subscription revenue event, identify the value distributable in **V2 credits** and apply only the four-role versioned split. The existing canonical SPEC-207 financial writer performs atomic debit/reservation/settlement and recipient credit postings with durable receipts. No new wallet or settlement ledger is introduced:
```
A) Skill pay-per-use (accepted unique invocation)
   payer wallet -charged_credits (once, when chargeable)
   platform user wallet +platform_share_credits
   tenant owner user wallet +tenant_share_credits
   miniapp owner user wallet +app_share_credits
   skill owner user wallet +skill_share_credits
   four shares sum exactly to the approved distributable credit amount

B) Mini App subscription (successful paid subscription period)
   verified invoice/payment -> recognized subscription credit-equivalent pool
   allocate pool ONCE per billable subscription period to four role bindings
   App-exclusive included Skills: no additional per-invocation payer debit
   Any shared Skill invoked inside the App: separate A) per-call debit/credit

C) One-time referral bonus (separate from A and B)
   approved platform promotion budget -> recipient user +bonus_credits ONCE
   no percentage of A/B, no fifth split role, no recurring referral commission
```
Subscription credit-equivalent allocation from a USD/THB payment MUST be funded and attributed to an accepted, non-duplicated payment/recognition event; a credit top-up alone is NOT earned revenue and MUST NOT trigger four-party allocation. Cash-payment receipts, payment processor fees, applicable tax and refunds remain in the existing financial accounting/receipts; they are not extra credit split recipients. If certain costs are retained before revenue allocation, the cost-bearing source and net distributable basis are versioned and transparent; do not mint unfunded credits or promise a cash-backed value that cannot be honored.
Version allocation snapshots with `offerId`, `priceVersion`, `revenuePolicyVersion`, `appId`, `skillId`, `tenantId`, `payer`, `billingContext`, `jobId`, the four `economicRole` values, `recipientUserId`, canonical wallet reference, source credit denomination, `chargedCredits`, `distributableCredits`, `creditedAmount`, rounding remainder ownership, cash-invoice source (when applicable), effective date, correction/refund links and one idempotency key per allocation event/role. Use exact-integer credit accounting and conservation assertions. Total recipient grants MUST equal the approved distributable credit basis, with cost reserves/funding clearly separated; do not count top-up credits as realized revenue. Provider/infra costs must identify the obligated payer and never silently confiscate creator credits.

For **every distinct shared Skill** execution, credit the four authorized recipient user wallets from its **per-call credit charge** at durable settlement; handle failures/refunds with linked correction entries. For the monthly Mini App Subscription, distribute the **recognized subscription-period credit pool once**, applying only four existing role slots. If no separately contracted exclusive Skill owner is entitled to a subscription share, apply a disclosed versioned absent-role rule; DO NOT create a phantom Skill owner or generic shared-Skill pool. Any contracted App-exclusive Skill creator receives a share **as credits in the verified recipient user wallet**, funded by the subscription-period pool, not by an extra subscriber per-call debit. Shared Skill owners are credited only via separately metered per-call events. Preserve historical receipts for no-usage, refunds/chargebacks, multiple exclusive creators, owner changes, cancellations, grace periods and temporary holds; no cash withdrawal route is activated in this phase.

## 5. Legacy adaptation audit — MUST implement consistently
Inventory and adapt `apps/web/server/services/creditService.ts`, `creatorRevenueService.ts`, `skillRevenueBilling.ts`, `pricingCalculator.ts`, `apps/web/server/routers/credits.ts`, billing topup + PromptPay/Stripe flows, model/media pricing catalogs, Admin screens, credit packages/grants, task budgets and reservation/outbox hooks, providers/LLM token to credit conversions, historic reports/exports and tests. `creatorRevenueService` currently contains a 2-role split; `skillRevenueBilling` has Tenant/Skill allocation primitives. Do NOT implement a second ledger in the new Hono Core. Update existing authoritative writers/shared compatibility first, or provide a versioned service contract that old and new clients both use.

## 6. Tenant/BYOC and merchant/payout rules
Separate legal seller-of-record, platform fee, tax obligations, payment gateway support and Cloudflare bill liability per Offer and white-label deployment. BYOC Cloudflare costs are not automatically borne by Platform. A Cloudflare account is a runtime/billing ownership fact, not a wallet recipient. **Current release performs internal credit attribution/grants only, NOT money withdrawal, bank transfers, stablecoin settlement, or cash escrow.** The verified user wallet recipient may represent an eligible economic owner/organization subject to authorization rules. Preserve source-of-credit lineage and outstanding liability to enable a separately designed future withdrawal feature; do not misrepresent earned credits as immediately withdrawable cash.

## 7. Integrity scenarios / no blanket deploy gates
Required targeted financial tests: old wallet 1000 -> new 10000; old cost 10 -> new 100; no economic change; unknown old unit reported correctly; existing 2-role creator split maps into 4-role policy only with identified beneficiaries; same logical action from headless/UI/WebMCP cannot double-charge; restart/retry/refund no duplicate; **exclusive App A Skill + active App A subscription -> no per-use debit**; **same subscription + Marketplace/Platform/App B/shared Skill -> per-call debit**; **App A exclusive Skill calling shared Skill twice -> two distinct metered child calls**; **same child Queue re-delivery -> no additional debit**; copied/rebranded Skill fails exclusive eligibility; subscription canceled/expired invokes per current quote; publisher opens an exclusive Skill to App B -> effective shared classification and prior notice before charging; unverified provenance never receives a free exemption; provider SDK inside true App-exclusive Skill follows disclosed App pricing; subscribed and non-subscribed paths produce correct 4-role allocations; refund reverses correct recorded allocation; multiple roles one recipient; convert while writer active denied or version-aware; rollback after conversion does not reinterpret balance; disabled skill/tenant no charge.

Release small non-financial UI safely without waiting for all commerce functionality. **Pause only affected money-moving actions** when balance/unit/recipient reconciliation is uncertain. Provide useful dev and human UAT on `aimarkethubs.com` and scoped live beta on `smartsihub.com` as soon as each safe capability works. Never let general inventory completeness become a global release veto.

## 8. Referral / Affiliate — One-time wallet credit award, never revenue share

- Define a referral link/code and verified referrer `recipientUserId`, referred user, qualifying event, program version, award credit amount and promotional funding source. The default trigger is the referred user's **first completed qualifying paid event**, not registration alone; allow program-specific trigger configuration with clear anti-fraud rules. The same referred user MUST NOT generate a second acquisition reward through another code, repeat purchase, event replay, program revision or retry; reverse a reward when its qualifying transaction is reversed under the published terms. No self-referrals, fake/linked-account farming or multi-level chains.
- Grant reward **once into that referrer's existing user credit wallet**, using canonical `creditService`/SPEC-207 ledger and stable idempotency key scoped to the qualifying referred user + acquisition event. Existing wallet balance UI includes the bonus, while transaction history identifies `REFERRAL_BONUS` source, program and funding budget. The event is funded from the allocated Platform marketing/promotional budget, not deducted from Platform/Tenant/Mini App/Skill Owner revenue shares and not created as a perpetual liability without an approved funding rule.
- Referral awards are promotional credits, not usage revenue earned by ownership. Record source class and effective terms to support a future withdrawal-eligibility decision; do not silently classify promotional credits as cash-withdrawable business earnings now.

## 9. User-wallet credit income — minimum implementation

- The **same canonical user wallet/balance** receives platform, tenant, App-owner, Skill-owner and one-time referral credit additions. Never introduce four separate role wallets, an affiliate cash commission ledger or a second financial authority. Keep immutable credit provenance fields / categorized transaction entries so reporting can distinguish purchased credits, service-earned credits, bonus credits, reservations and corrections without fragmenting the user's ordinary spendable balance.
- Each paid invocation that settles successfully: one canonical payer debit (when applicable) and four or fewer recipient-user credit postings under one durable settlement identity; duplicate Queue delivery/HTTP retry must be idempotent for payer and each recipient. Owner roles may point to the same user: record each role share yet add only the sum once per settlement; refund/chargeback produces linked reversals and never edits old ledger history.
- One subscription period and its successful funding event may generate **only one** allocation; repeated payment webhooks and renewal retries are not fresh income. Distinguish user top-up liability from actual Skill/Subscription revenue. Record pending/held earned credits when chargeback or service fulfillment risks require it; do not allow those amounts to be prematurely spent if doing so would create negative liabilities. Keep administrative reporting simple: balance, earned by source/role, spent, refunded, promotional bonus, pending, transaction history.
- Where funding costs/infra charges apply, record the disclosed distributable basis and ensure total grants are funded within the available pool. No silent issuance of credits to recipients from unverified provider payments.

## 10. Future withdrawal — reserved scope, NO current implementation

- **Do not implement bank/PromptPay/foreign-currency withdrawals or cash-conversion UI in this release.** Design a future separate spec/phase around withdrawable credit classes, verified owner identity, minimum eligible amount (configurable, not hard-coded), available-vs-pending balance, holds, currency/FX quote, fees/taxes, AML/KYC applicability, payout provider, failed payouts, reversals and audit receipts.
- A single wallet can present unified spendable credits while its immutable transaction provenance supports a future **withdrawable-earned** projection. Do not promise that purchased or promotional credits are withdrawable; the eligible source classes will be decided explicitly before launch. This prevents arbitrary cash redemption of promotional grants and avoids requiring a second wallet now.
- UI may show `Withdrawals: coming later` as informational copy, but MUST NOT advertise a functioning payout, guaranteed USD redemption or minimum withdrawal threshold that has not been adopted.

## 11. Additional targeted integrity tests for R0.8

1. Skill charge 100 credits: authorized four recipient credits sum to exactly the distributable pool, no fifth share; repeat event creates zero additional wallet changes.
2. Two owner roles bound to the same user: role history is distinct, total wallet increment is correct without double-posting.
3. First valid referred-user paid event awards exactly one platform-funded referral bonus to the referrer's user wallet; two payment webhooks, retries, second purchases and program version changes do not award again.
4. Fake referral, self-referral, or reversed qualifying payment is rejected/reversed under policy; no change to the four-role split of the original sale.
5. Subscriber runs App-exclusive Skill: no per-call subscriber debit; subscription-period recipient credits issued once from verified funding; nested shared calls still debit and distribute per call.
6. Purchased-top-up credits alone generate no four-way creator earnings; price-unit conversion from 1,000 to 10,000 credits/USD preserves balances, quotes, award values and outstanding reservations.
7. No cash withdrawal endpoint, payout button, bank transfer, escrow or new economic wallet activated; historical source classification is sufficient to design withdrawals later.
8. Wallet/financial error affects only the attempted money-moving action; UI/portfolio and unrelated development Deploy continue for human UAT.

## R0.9 — Agentic Payments / Platform Subscription / PAYG integration

**Priority owner policy — SPEC-322:** The **SmartSIHub Platform Subscription** is independent of the existing `MINIAPP_SUBSCRIPTION`. It adds a configurable number of PLATFORM_MONTHLY_CREDIT_GRANT credits **once per verified paid period** into the same canonical user wallet, with versioned rollover/expiry and consumption-priority policy. Purchased wallet credits, monthly platform credits and role-earned credits carry source lineage. Platform plan monthly credit grants are NOT four-role Mini App/Skill sale revenue. A human MUST have a canonical SmartSIHub user account before Mini App use. Linked Agents can act under an explicit scoped spend mandate; no browser required for supported actions.

Implement `PREPAID`, `AUTO_TOPUP` and `PAYG_POSTPAID`: quote expected amount + documented buffer, atomically hold/reserve, measure actual usage, settle only actual, release unused hold; pause further billable work when reserve extension is denied. Class-based allowed negative balance is versioned and independently bounded by payer, mandate and policy; default zero until explicitly enabled. A class limit is **not** an additional credit grant. PAYG unsettled debt produces receivable/collections records; four-role creator earned credits remain pending/non-spendable until payment or defined guaranteed funding is recognized to avoid unfunded credit creation. Existing data/credit conversion, referral once-only, App-exclusive-only Mini App subscriptions and four-role credits rules stay unchanged. Do not add a second ledger or payout system.

At target health and financial reporting surfaces, separately present platform plan credit grants, credit purchases, platform spent credits, PAYG reserved credits, available credit-line headroom, negative debt and Mini App subscription entitlements. Payment processor top-up/renewal/collection must have stable unique verification and grant keys; repeated callback is not a fresh purchase. See SPEC-322 for primary cross-provider interoperability and agent authority contract.

## R1.0 — Portable Mini App billing is platform-controlled, App data is not
Every hosted/BYOC/self-hosted Mini App uses the **same canonical Core** entitlement, credit unit v2, Quote/Reserve/Usage/Settlement, exclusive-Skill subscription policy and four-recipient allocation where it sells through SmartSIHub. Changing a Mini App DB or hosting account cannot transfer custody of user credit balances or create a second earned-credit ledger. `smartspec` stores App commercial control-plane metadata only, never new App domain business tables. A self-hosted App can opt out of platform commerce only under an explicit externally managed commercial offer that does not falsely claim SmartSIHub billing or entitlements.


## R1.1 — Owner-directed autonomous bootstrap and priority order (2026-11-01)

**Normative owner directive:** ALL development of the new SmartSIHub platform SHALL be initiated, orchestrated, observed and accepted through the *currently running* `https://smartaihub.app` Autonomous Implements / Autonomous Mini App Creator facilities, using their existing SPEC-224 Job/Run, Runner, Workspace, Harness and deployment authorities. `smartaihub.app` is the **temporary development control plane**, not the new SaaS Core implementation or the new production domain. This rule applies to source changes, builds, tests, release requests, UAT and repair work; executors may run CLI internally as delegated tools. An emergency out-of-band repair is permitted ONLY when the old UI/control path is nonfunctional; reconcile its exact SHA/Run/receipts back into the canonical record as soon as recovery permits. Never claim that a task was executed through the UI unless actual Run evidence confirms it.

The priority order is fixed for planning: **P0 legacy autonomous-system repair/proof → P1 fresh lightweight Core/Shell → P2 Chat → P3 Autonomous Mini App Creator → P4 new Autonomous Implements → P5 selective autonomy handover → P6 Public Portfolio/Marketplace → P7 other modules**. Thin dependencies (login, job contracts, SDK, billing read-only, public designs) MAY be built in parallel; this is an execution priority, not a global blocking gate. No new Core/Mini App is allowed to write business data into canonical `smartspec` other than the existing narrowly registered Legacy module data exception under SPEC-323.

The development loop SHALL be: **Goal entered on old website → durable Run and owned Debian workspace → implement/test/build → real `aimarkethubs.com` UAT → scoped `smartsihub.com` Cloudflare beta when appropriate → user feedback → automatic child repair/continue**. A defect in the existing control plane becomes an **in-scope bootstrap repair task** for the affected operation, not a reason to abandon the migration or create another approval system. Preserve task identity, source SHA, logs and work artifacts through restart/disconnect; no silent success claims. The new autonomous implementer becomes the primary authority only after it has completed real development tasks and recovery/rollback tests; user-visible traffic switches selectively, with the old tool retained as fallback until stable. See SPEC-324 and [roadmap](../../../docs/smartsihub-r1.4/ROADMAP-AUTONOMOUS-IMPLEMENTATION.md).

P0–P4 use existing SPEC-207 financial authority for logged development work; do not create a temporary second wallet or let the legacy and new runtimes interpret the same credits in different denominations. Demonstrate end-to-end real or bounded test credit charging for Chat/Creator before activating the corresponding paid operation. Unrelated nonfinancial UAT remains available.

### R1.4 shared invariants (normative)

1. **Identity and domains.** `smartsihub.com` is the confirmed Cloudflare **production** hostname; `aimarkethubs.com` is the Debian-first new-platform development + real-human UAT; `smartaihub.app` is the still-running legacy system AND the sole initial user-facing development-command center, to be retired as a controller only after proven selective handover. Hostname, `NODE_ENV`, public link or site labels MUST NOT be used as substitute for verified runtime target, role or payment authority.
2. **No parallel financial or job authority.** PostgreSQL `smartspec` continues to own canonical identity, tenancy, wallet/credits, subscriptions, marketplace/app IDs, and `worker_jobs`; registered **legacy-migrated data** may stay there. New stateful Mini App business data MUST use an app-specific store outside Core; stateless Apps need none. Rust, TypeScript, Mini App, Browser and external Agent MUST access central financial/job effects through the versioned authorized contracts, not invent private settlement or job ledgers.
3. **Technical baseline.** Fresh minimal **TypeScript/Hono Core Workers**, **React/TypeScript fixed shell + optional OpenUI interactive renderers**, **Astro public marketplace** built from scratch, **Rust-native long-running supervisor** and TypeScript Queue transports. Never convert/copy the legacy server wholesale or require Rust/Wasm in every Core API. Optimize JS/asset/bundle size and queries using measurements, without blocking unrelated UAT on advisory targets.
4. **User-centric autonomy.** P0 repairs and exercises existing `smartaihub.app` Autonomous Implements / Creator; P1 new Core; P2 Chat; P3 Mini App Creator; P4 new Autonomous Implements; P5 selected authority handover; P6 portfolio/public marketplace; P7 remaining modules. Priorities allow parallel safe preparation, never global step-by-step approval loops. Scope only actual unauthorized data/finance, wrong-target deployments, unsafe effects or unavailable nondelegable authority.
5. **Chat-first, always-on when truly hosted.** Human Chat is the front door; direct HTTPS/MCP enables Agent use without UI. Dynamic inline diagrams/interactive forms/OpenUI and artifact/browser side-panels render one canonical action/run identity. `worker_jobs` persists independently of user browser sessions, but **do not claim cloud 24/7 persistence** for a job whose only authorized executor is an offline user device.
6. **Browser and Computer Use.** SPEC-208 remains authoritative: deterministic eligible-route policy then optional Clef bounded decision; direct API/MCP first, Chromium/Playwright dependable pilot, **Moli explicitly unqualified for production pending isolation/security evidence**, Kitesurf only supported beta profiles, Windows/Linux desktop via approved Runner. Browser snapshots/session state are not durable Job authority. WebMCP browser tools are optional early-preview projections, not a headless server API or permission escalator.
7. **Economic and commercial identity.** 1 USD = 10,000 **new** credits; preserve old purchased/earned value by atomic denomination-versioned x10 migration for old units, avoid historical ledger rewrite and mixed unit writers. Only four revenue roles (Platform, Tenant Infra, Mini App, Skill) credit verified owner user wallets. One-time referral bonus is Platform-funded, not a fifth share. SmartSIHub **platform** subscription (monthly credits) is distinct from Mini App subscription (only new **exclusive** in-app Skills included); all shared/external Skills charged per distinct invocation. Pay-as-you-go reserve/actual settle/unused release and per-class overdraft default **zero** unless authorized. Users must have a SmartSIHub account; paid platform subscription is not universally mandatory.
8. **Cross-provider portability and idempotency.** Core remains PostgreSQL; independent new Mini Apps use app-owned **D1** / independent PostgreSQL or self-hosted storage under **BYOC** or managed deployment. **Idempotency** is required for job admission, shared Skill usage, credit reservation/settlement, subscription grants, referral bonuses and replayed webhooks; this is a business-effect invariant rather than a new global approval gate.
9. **Visual product contract.** Include Light, Dark, and Balance theme tokens and three **reference** mockups.
