# Release Note

## Feature 082

Work OS: Case Ledger and Operating Queues

## สรุปสั้น ๆ

Feature นี้ทำให้ระบบมี "ศูนย์กลางการจัดการงาน" ที่ชัดเจนขึ้น

แทนที่งานจะกระจายอยู่หลายหน้า หลายคิว หลายบันทึก ตอนนี้งานธุรกิจจะถูกมองเป็นเรื่องเดียวกันตั้งแต่ต้นจนจบ เช่น

- งานเข้ามาจากหลายช่องทาง
- งานถูกจัดเข้าเคสกลาง
- งานถูกส่งต่อให้คนหรือทีมที่รับผิดชอบ
- งานที่ต้องรออนุมัติจะเห็นชัด
- งานที่มีปัญหาหรือใกล้ครบกำหนดจะถูกเตือน
- งานที่เสร็จแล้วจะมีผลลัพธ์และประวัติย้อนหลังให้ดูได้

พูดง่าย ๆ คือ ระบบนี้ช่วยให้ "รู้ว่างานอยู่ไหน ใครรับผิดชอบ และติดอะไรอยู่" ได้ในที่เดียว

## ได้อะไรบ้าง

### 1. งานทุกชิ้นมีศูนย์กลางเดียว

งานหนึ่งเรื่องจะไม่กระจัดกระจายไปคนละที่อีกต่อไป

- ระบบจะสร้างงานหลักให้เป็นเรื่องเดียวกัน
- งานเดียวกันสามารถโยงกับงานย่อย งานอนุมัติ และผลลัพธ์สุดท้ายได้
- ทำให้คนที่เข้ามาดูภายหลังเข้าใจเรื่องราวของงานได้ครบ

### 2. มีคิวงานที่มองเห็นง่าย

ผู้ที่มีสิทธิ์จะเห็นงานในรูปแบบคิว เช่น

- งานที่รอทำ
- งานที่ต้องส่งให้ทีมอื่น
- งานที่ต้องรออนุมัติ
- งานที่มีข้อยกเว้นหรือปัญหา
- งานที่ใกล้ครบกำหนดหรือเกินกำหนด

### 3. มีประวัติการส่งต่องานชัดเจน

ระบบบันทึกว่า

- งานถูกส่งต่อจากใครไปหาใคร
- เปลี่ยนเจ้าของงานเมื่อไร
- เปลี่ยนเพราะอะไร

จึงช่วยให้ตรวจสอบย้อนหลังได้ง่าย และลดปัญหางานหายกลางทาง

ถ้ามีงานจาก desktop หรือ execution ภายนอก ระบบจะเก็บ progress, artifact, และ worklog กลับมาอยู่ใน timeline เดียวกันได้ แม้ปลายทางจะ offline หรือ stale ชั่วคราว

### 4. การอนุมัติและข้อยกเว้นเห็นชัด

ถ้างานต้องรออนุมัติ หรือเกิดปัญหาบางอย่าง ระบบจะแสดงสถานะให้เห็นทันที

- งานที่รออนุมัติจะไม่หายไปในบันทึก
- งานที่มีปัญหาจะถูกดึงขึ้นมาให้เห็น
- งานที่ต้องแก้ไขต่อจะมีร่องรอยให้ตรวจสอบได้

### 5. มีสัญญาณเตือนเรื่องเวลา

ระบบจะช่วยบอกว่างานไหน:

- ใกล้ครบกำหนด
- เกินกำหนด
- เสี่ยงจะช้า

ทำให้ทีมดูแลงานได้ก่อนที่จะกลายเป็นปัญหาใหญ่

### 6. มีหน้า Work Request สำหรับผู้ใช้ทั่วไป

ผู้ใช้ทั่วไปจะมีหน้าส่งงานเข้า Work OS โดยตรง

- เส้นทางหน้าเว็บ: `/work/request`
- ใช้สร้าง request ใหม่จาก chat, webhook, form, API, document flow หรือ manual input
- เลือกมอบหมายให้ตัวเอง หรือเลือกทีมของตัวเองเป็นเจ้าของงานได้
- เหมาะกับคนที่อยากเริ่มงานของตัวเองโดยไม่ต้องเข้า console ของผู้ดูแล

เมื่อส่งแล้ว ระบบจะสร้าง request และ case ให้ติดตามต่อได้

### 7. มีหน้า Work OS Console สำหรับผู้ดูแล

ผู้ดูแลหรือ domain admin จะมีหน้ารวมสำหรับดูภาพรวมของงาน

ในหน้านี้สามารถ:

- ดูภาพรวมงานทั้งหมด
- เปิดดูคิวงาน
- คลิกเข้าไปดูรายละเอียดของงานหนึ่งเรื่อง
- ดูประวัติการส่งต่องาน
- ดูคำอนุมัติ ข้อยกเว้น ผลลัพธ์ และสถานะเวลา

### 8. มีทางเริ่มงานจากหน้า Chat

หน้า Chat จะมีตัวบอกทางให้รู้ว่าเรื่องไหนควรถูกยกระดับเป็นงานที่ติดตามได้

- กดเพื่อเปิด Work Request ได้ทันที
- ผู้ดูแลสามารถข้ามไป Work OS Console เพื่อจัดการ request และ import งานเก่า
- ช่วยให้ทีมรู้ว่าตอนใดควรคุยต่อในแชท และตอนใดควรเริ่มงานจริงใน Work OS

### 9. มีเส้นทางรับงานเข้าระบบที่ชัดเจน

Work OS ไม่ได้รอให้คนมานั่งสร้างงานด้วยมืออย่างเดียว งานสามารถเข้ามาได้จากหลาย trigger เช่น

- ผู้ใช้ส่งคำขอผ่าน chat แล้วระบบแปลงเป็นงานจริง
- ระบบภายนอกส่ง webhook เข้ามา
- ฟอร์มหรือ API สร้างงานใหม่
- งานจากเอกสารหรือ flow อัตโนมัติ
- งานที่ถูกตั้งให้วิ่งตามเวลา เช่น schedule trigger

พูดง่าย ๆ คือ งานเข้ามาได้จาก “จุดเริ่มต้นของธุรกิจ” หลายแบบ ไม่ได้ผูกกับหน้าเดียวใน UI

## ใช้ดูผ่านหน้าไหน

ฟีเจอร์นี้ดูแลผ่านหน้า UI หลัก 2 จุด:

### 1. Work OS Console

- เส้นทางหน้าเว็บ: `/admin/work-os`
- ใช้สำหรับดูและจัดการงานแบบรวมศูนย์
- สิ่งที่เห็นในหน้านี้:
  - ภาพรวมสถานะงาน
  - คิวงาน
  - รายละเอียดงานที่เลือก
  - ประวัติการส่งต่องาน
  - คำอนุมัติ
  - ข้อยกเว้น
  - ผลลัพธ์ของงาน
  - สถานะเวลา

> หมายเหตุ: หน้านี้เป็นหน้าติดตามและจัดการงานเป็นหลัก
> ส่วนการสร้างงานเข้า Work OS จะมาจาก trigger / integration / API ที่เชื่อมไว้กับระบบอื่น
> ถ้ายังไม่เชื่อมจุดรับงาน งานจะยังไม่เข้าระบบเอง

### 2. Admin Monitoring

- เส้นทางหน้าเว็บ: `/admin/monitoring`
- ใช้ดูภาพรวมการทำงานของระบบ
- ในหน้านี้มีปุ่มพาไปหน้า Work OS Console ได้ทันที
- เหมาะสำหรับคนที่เริ่มจากหน้ามอนิเตอร์ระบบแล้วอยากไล่ดูว่างานติดอะไรอยู่

### ใครเข้าได้

- ผู้ดูแลระบบ
- domain admin
- ผู้ใช้ทั่วไปที่อยู่ใน tenant เดียวกัน เพื่อสร้าง work request และดูงานของตัวเอง

ถ้าเป็นผู้ใช้ทั่วไป จะเห็นหน้า Work Request และ My Requests แต่จะไม่เห็น Work OS Console แบบเต็มรูปแบบ

## ใช้งานอย่างไร

### งานเข้ามาได้อย่างไร

งานใหม่จะเกิดขึ้นเมื่อมี trigger เข้ามา เช่น chat, webhook, form, API, document flow หรือ schedule

จากนั้นระบบจะ:

- สร้าง work request เป็นงานตั้งต้น
- เปิด work case เป็นแฟ้มกลางของเรื่องนั้น
- ใส่ owner เบื้องต้นให้ ถ้าระบบรู้ว่าควรไปอยู่ทีมไหนหรือคนไหน
- ถ้าความมั่นใจต่ำ งานจะถูกส่งไป triage แทนการเดา

จากนั้นผู้ดูแลสามารถ:

- ตรวจดูว่างานมาจากช่องทางไหน
- ใส่ความสำคัญหรือความเร่งด่วน
- ส่งงานให้คนหรือทีมที่เหมาะสม

### งานเป็นของใคร

Work OS รองรับเจ้าของงานได้หลายแบบ เช่น

- คน
- ทีม
- คิวงาน
- บทบาทหรือ role
- แบบผสม

ถ้ามีการส่งต่องาน ระบบจะบันทึกไว้ว่า:

- เดิมอยู่กับใคร
- ย้ายไปที่ไหน
- ย้ายเพราะอะไร

### ถ้างานต้องส่งต่อ

ผู้ดูแลสามารถเปลี่ยนเจ้าของงานหรือทีมรับผิดชอบได้

ระบบจะบันทึกไว้ว่า:

- เดิมอยู่กับใคร
- ย้ายไปที่ไหน
- ย้ายเพราะอะไร

### ถ้างานต้องรออนุมัติ

ระบบจะแสดงงานที่รอการตัดสินใจไว้ชัดเจน

เมื่ออนุมัติหรือไม่อนุมัติ ระบบจะอัปเดตสถานะให้เห็นต่อเนื่อง

ถ้างานอนุมัติเข้ามาจาก flow อื่น ระบบจะผูกการตัดสินใจนั้นเข้ากับงานเดียวกัน ไม่ให้แยกกันคนละที่

ถ้า agent ภายนอกหรือ automation หางานที่ปลอดภัยไม่เจอ ระบบจะส่งเข้า triage แทนการเดา

### ถ้างานมีปัญหา

ถ้างานติดขัดหรือเสี่ยงล่าช้า ระบบจะเปิดเป็นข้อยกเว้นให้เห็นได้ทันที

ทำให้ทีมรู้ว่าต้องแก้ตรงไหน ไม่ต้องไล่หาจากบันทึกจำนวนมาก

automation ที่ทำได้ในเวอร์ชันนี้ เช่น:

- ถ้า SLA ใกล้หลุดหรือหลุดแล้ว ระบบเปิด exception ให้อัตโนมัติ
- ถ้า approval timeout หรือมี policy block ระบบยกระดับเป็น exception ได้
- ถ้างานถูกเชื่อมกับ task เดิม ระบบจะดึงประวัติเดิมเข้ามาเป็น timeline เดียวกัน

### งานผูกกับทีมอย่างไร

ถ้างานต้องวิ่งเข้าทีมใดทีมหนึ่ง ระบบจะผูกงานกับ:

- team
- room
- run
- หรือ role ที่รับผิดชอบ

ถ้าเป็นงานย่อยที่ต้องให้ทีมลงมือทำจริง ระบบจะสร้าง task ที่ผูกกับ team นั้นและติดตามต่อใน Work OS ได้

### ถ้างานเสร็จแล้ว

ระบบจะบันทึกผลลัพธ์ของงานไว้เป็นหลักฐาน

ทำให้ดูย้อนหลังได้ว่า:

- งานจบแบบไหน
- มีผลกระทบอะไร
- มีการแก้ไขต่อหรือไม่

### ถ้าจะเอางานเก่ามาเข้าระบบ

Work OS มีทางเชื่อมสำหรับนำงานเก่าหรือ task เดิมเข้ามาแนบกับ case เดียวกันได้

ทำให้ทีมที่กำลังย้ายระบบ:

- ไม่ต้องทิ้งประวัติเดิม
- ไม่ต้องเปิดหลายหน้าคนละที่
- ดู timeline ของเรื่องเดียวกันได้ครบขึ้น

ถ้างานเกิดจาก desktop progress, local artifacts, หรือ local worklog ระบบจะ sync กลับมาเป็นหลักฐานบน case timeline เดียวกัน ไม่แยกเป็นประวัติฝั่ง desktop อีกชุดหนึ่ง

## เหมาะกับใคร

ฟีเจอร์นี้เหมาะกับคนที่ต้องดูแลงานแบบ end-to-end เช่น

- ผู้ดูแลระบบ
- ทีมปฏิบัติการ
- หัวหน้าทีม
- ทีมอนุมัติ
- ทีมซัพพอร์ตหรือทีมที่ต้องรับงานต่อกันหลายขั้น

## ประโยชน์ที่เห็นได้ชัด

- รู้ว่างานอยู่ขั้นไหน
- ลดงานตกหล่น
- ส่งต่องานได้เป็นระบบ
- ตรวจสอบย้อนหลังได้ง่าย
- เห็นงานค้าง งานช้า และงานเสี่ยงได้เร็วขึ้น
- ทำให้การทำงานร่วมกันระหว่างทีมชัดเจนขึ้น

## ข้อควรรู้

- ฟีเจอร์นี้ออกแบบมาสำหรับผู้มีสิทธิ์ดูแลงาน ไม่ได้เปิดให้ทุกคนแก้ไขทุกอย่าง
- งานแต่ละเรื่องจะมีประวัติและสถานะของตัวเอง จึงดูย้อนหลังได้ว่าเกิดอะไรขึ้นบ้าง
- จุดประสงค์หลักคือทำให้ "งานทั้งเรื่อง" เห็นได้ในที่เดียว ไม่ใช่แค่เห็นเฉพาะหน้าจอใดหน้าจอหนึ่ง

## สรุปท้ายสุด

Feature 082 เปลี่ยนระบบให้จากการ "เก็บงานกระจัดกระจาย" ไปเป็น "จัดการงานแบบมีศูนย์กลางเดียว"

ผลลัพธ์คือคนทำงานและคนดูแลงานจะเข้าใจงานได้ง่ายขึ้นว่า:

- งานนี้คือเรื่องอะไร
- ใครกำลังรับผิดชอบ
- ต้องรออะไรอยู่
- ติดปัญหาตรงไหน
- และงานจบแบบไหน
