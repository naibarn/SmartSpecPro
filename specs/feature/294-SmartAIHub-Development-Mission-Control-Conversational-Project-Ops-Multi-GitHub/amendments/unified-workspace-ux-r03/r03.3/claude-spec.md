# R03.3 Implementation Spec

Implement an explicit authenticated DEV-only `/dev/mission-control-live` route separate from R03.2 demo routes. It uses Modular Core session/workspace authorization and only existing canonical tenant Mission, Chat Job/Task projection, Attempt and event APIs. The view preserves the approved R03.2 layout while clearly labeling `LIVE · READ ONLY`; no fixture fallback, no mutation, no assumed Harness identities. It offers workspace selection from authenticated memberships, Mission/execution selection, canonical IDs, event cursor/status where available, and truthful unavailable states. Exact Task deep links include the Mission, conversation, Job, Run and Attempt identifiers available from canonical projections, and the destination re-fetches the authorized conversation Task Control projection before showing matching records. Return navigation preserves the source URL/context, but browser storage is context only, never authorization.

The Core API adds one authenticated read-only workspace-level Mission listing route by reusing the existing `listMissions(userId, workspaceId)` function and existing owner/workspace authorization. Existing per-conversation list/detail/task-control and turn status/event APIs remain the detail authorities. No schema, scheduler, event store, adapter registration, or lifecycle mutation is added. Automated tests cover authentication, requested-workspace membership, query contracts, live/demo separation, exact identity filtering, unavailable Harness data, and safe return navigation.

Upstream evidence gap: current Modular Core Chat Task projections return nullable Harness/Agent/Run/Executor/Machine identity fields and provide no Harness catalog, live event stream, or deep evidence API. The deployed UI renders only returned Mission/Job data and labels unavailable facts explicitly. The R03.3 final genuine-Harness acceptance remains open until a real authorized canonical relationship is available; no synthetic row or inferred mapping may close it.
