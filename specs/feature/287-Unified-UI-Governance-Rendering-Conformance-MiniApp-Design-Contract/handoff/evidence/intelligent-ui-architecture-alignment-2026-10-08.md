## 4. Architecture Decision Record

**ADR-UI-01 — Compose existing UI, action, policy, economic, and execution owners.**

- **Decision:** Put generated surface protocol/registry/streaming/action-binding semantics in SPEC-240; visual/design/rendering governance in SPEC-287; design-time providers/artifacts in SPEC-270; client action/task mapping in SPEC-226; agent-to-orchestrator delegation in SPEC-279; authorization in SPEC-220; economic checks in SPEC-207; durable execution in Feature 195; portable backend/app deployment in SPEC-288/261; knowledge portability in SPEC-281 and existing retrieval/memory owners.
- **Rationale:** These boundaries are already represented in source documents and runtime seams. A second router, component registry, permission engine, billing store, memory authority, or queue would conflict with current ownership rules.
- **Clarification:** SPEC-279 is not the generic user-facing action protocol. UI clicks/forms follow the client action boundary (SPEC-226) and are server-authorized by SPEC-220. SPEC-279 is used only when an agent-originated command/delegation path applies.
- **Consequences:** Providers may propose presentation and data, but server-stamped scope and schema validation control rendering. Only trusted server bindings can invoke actions. Approval chrome is host-owned. Long-running work uses `worker_jobs`/outbox. Headless agents call the same authorized action/capability contracts without mounting UI.
- **Rejected:** New SPEC; LLM-authored executable React/HTML with backend access; UI-specific memory/billing/permission/job stores; routing all UI actions through SPEC-279; automatic production deployment of every transient surface.
- **Status:** Document decision only; canonical owner conflicts and implementation acceptance remain open as detailed above.

### Target architecture

```text
User intent + authenticated tenant/project/resource context
  -> existing assistant/capability routing (269; 256 only after authority reconciliation)
  -> presentation choice: text | structured result | chart/table/form | transient surface | persistent Mini App
  -> SPEC-240 surface proposal -> schema + component/version validation
  -> incremental validated patches -> SPEC-287 design/render/accessibility conformance
  -> client action mapping (226) OR agent-originated delegation (279)
  -> SPEC-220 server authorization -> SPEC-207 quote/reserve/meter (when billable)
  -> trusted human approval when policy requires
  -> Feature 195 worker_jobs + outbox for durable work; existing direct adapter only for bounded synchronous work
  -> authoritative result + audit receipt -> fresh authorized render
  -> explicit promotion flow to a persistent/portable Mini App (288/261; knowledge via 281)
```

The LLM can select a permitted presentation class and propose schema-conforming content. It cannot define new privileged components, tenant identity, resource scope, authorization, cost, approval, or execution destination.
