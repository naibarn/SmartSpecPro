# R03.4 consumer identity boundary (2026-11-16)

This is a consumer-side compatibility note for SPEC-294 R03.4. It does not change SPEC-310's proposal/gate status or authorize a Native Harness runtime, dispatch route, or new execution authority.

- `runner_nodes.runnerId` is a canonical Runner identity, not a Harness instance ID.
- A Runner capability snapshot currently defines capabilities, workspaces, resource class, platform and freshness. It does not define a validated Harness type or stable Harness instance ID.
- `runner_execution_sessions` binds a canonical Job, attempt number, Runner and session. `worker_jobs`, `worker_job_attempts` and `worker_job_events` retain their existing authority.
- A Chat Conversation/Thread/Mission association is valid only when a producer persists the exact canonical binding and each consumer reauthorizes its owner, tenant and workspace. A shared title, tenant, timestamp, or display label is not a correlation key.
- `driverId`/adapter IDs describe an execution driver contract; they MUST NOT be relabeled as Harness type without an approved versioned producer contract.
- Until a producer publishes that contract, Harness identity and Mission association are `NOT_CAPTURED`/`UNAVAILABLE`; no Synthetic R03.2 fixture may enter the R03.3/R03.4 LIVE route.

Evidence and current source map: SPEC-294 R03.4 `source-to-canonical-identity-map.md`. The local DEV Runner service observed during this review was inactive; that observation is not a claim about other registered Runner hosts. This note does not satisfy the SPEC-310 G0/G1, runtime, or owner-acceptance gates.
