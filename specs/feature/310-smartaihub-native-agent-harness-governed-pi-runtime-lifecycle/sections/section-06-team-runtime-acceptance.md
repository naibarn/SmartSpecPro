# Section 06 — Team, Runtime Lifecycle and Acceptance

## Objective

Plan subordinate Native child attempts, trusted managed Pi updates and truthful multi-platform acceptance while preserving existing team, job, economic and development authorities.

## Requirement IDs

R1.3.4–R1.3.6a; A55–A68; applicable R1.0/R1.1/R1.2 criteria after source reconciliation.

## Scope

SPEC-269 team plan, canonical worker job parent/child attempts, SPEC-207/280 accounting, SPEC-278 Runner recovery/runtime pinning and SPEC-271 evidence. No independent team scheduler, ledger, workspace source of truth or Orca requirement.

## Prerequisites

Sections 03–05 as applicable; explicit parent/child fencing, budget and writer contracts; authorized Windows/Linux/cloud targets; independent verifier ownership. SPEC-224 protected E2E has priority.

## Deliverable and completion predicate

Bounded children have independent attempt/grant/usage receipts; shared Pi installation remains pinned per active run; single-writer or safe candidate-merge semantics hold for non-Git content; signed update/rollback works on certified targets; acceptance evidence is independent and real.

## Verification and evidence

Concurrency, recovery, update/rollback and failure-injection tests; actual target screenshots/logs only when performed; Gateway and settled-credit receipts; SPEC-271 independent evidence. Keep production flag disabled until all applicable proofs and existing authorization allow it.

## Blocker challenge

Treat missing target, credentials or owner authority as a scoped external evidence wait. Continue non-production contract and deterministic recovery work; never mark mocked Windows/cloud/Gateway/credit evidence as pass.
