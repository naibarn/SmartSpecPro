| HIGH | `CustomToolCreator.tsx:155-158` | Edit mode fetches via `listCustomTools` with `search:""` and `limit:1`, then reads `tools[0]`. This is fragile — if the search returns multiple tools from a different ordering, it will silently prefill the wrong tool. `listCustomTools` returns results ordered by `createdAt` desc; a newly-created tool could displace the target. The procedure does not accept a `toolId` filter. | Either add a `getCustomTool(toolId)` query to the backend, or filter `tools[0]` by `tool.id === editToolId` after fetching. | MEDIUM | `CustomToolCreator.tsx:155-158` | The `listCustomTools` query is always mounted (due to `(trpc as any).agency?.listCustomTools?.useQuery?.()` pattern) but the `enabled` option is passed as `{ enabled: open && !!editToolId }`. This is a conditional hook violation — React requires hooks to be called in the same order on every render. If `(trpc as any).agency?.listCustomTools?.useQuery` is `undefined` (e.g. the tRPC client doesn't have this procedure yet), `?? { data: undefined }` returns a plain object, which is fine. ### Contract Compliance Detail — Critical Backend Mismatch

The `listCustomTools` backend query (confirmed at `agency.ts:3025-3046`) selects:
`id`, `name`, `description`, `toolType`, `httpMethod`, `riskLevel`, `icon`, `category`, `version`, `strictSchema`, `oneCallAtATime`, `hasHeaders`.

It does **not** select: `inputSchema`, `outputSchema`, `retryPolicy`, `endpoint`.

The edit-mode prefill code at `CustomToolCreator.tsx:222-229` references `tool.config?.endpoint`, `tool.retryPolicy?.maxRetries`, `tool.retryPolicy?.backoffMs`, `tool.inputSchema`, `tool.outputSchema` — all of which will be `undefined` from the `listCustomTools` response. The endpoint field will always show blank in edit mode. The `inputSchema`/`outputSchema` editors will always reset to null.

This means edit mode is functionally broken for the endpoint, retry policy, and schema fields. The backend must either: (a) add a `getCustomTool(toolId)` procedure that returns the full row, or (b) expand `listCustomTools` to include these fields.

---

### Summary

The implementation delivers the core UI structure — multi-step wizard, visual/raw schema editor, tool-type badges, edit/delete hover actions, and reasonable test coverage for the happy path. However, three production-blocking issues exist: edit mode is broken because `listCustomTools` does not return enough data to prefill the form (endpoint, schemas, retry policy all come back as `undefined`), existing encrypted headers are silently wiped on any update, and the `AGENCY_CUSTOM_TOOLS_ENABLED` feature flag is not registered in the type system or applied anywhere in the frontend. The `confirm()` dialog for destructive deletes and the optional-chaining hook pattern are medium-priority polish items that should also be addressed before merge.
