## Review Report

### Verdict: APPROVE_WITH_FIXES

### Findings

| Severity | File:Line | Issue | Recommended Fix |
|---|---|---|---|
| HIGH | `useAgencyStream.ts` (reconnect block) | `startSSEConnection` is declared as a plain `function` statement inside the `useAgencyStream` function body (outside `useCallback`) but closes over `setToolCalls`, `setGuardrailEvents`, `setIsPollingFallback`, `runIdRef`, and `lastEventIdRef`. Because it is a plain function it is recreated on every render. `reconnectTimerRef.current = setTimeout(() => startSSEConnection(params, runCounter), delay)` captures the function reference at the time the timer is set, which is safe for the timer case, but `handleSSEEvent` is also a plain inner function that calls all the state setters and refs. Neither function is stabilized with `useCallback`. In React 18 Concurrent Mode, if the component re-renders between a reconnect timer firing and the reconnect completing, the stale `params` closure passed to `setTimeout` may include a stale `agencyId` or `message`. Fix: either wrap `startSSEConnection` / `handleSSEEvent` in `useCallback` with correct deps, or move them outside the component and accept all mutable state as explicit parameters (the ref pattern already handles most of this). At minimum add a guard inside the timeout callback that checks `runIdRef.current === null` (i.e., a new `connect()` has been called) before proceeding with the reconnect. |
| HIGH | `useAgencyStream.ts` (polling fallback) | The spec requires that when `isPollingFallback` is true the hook calls `tRPC agency.getRun` on a 3-second interval. The implementation sets `isPollingFallback = true` and immediately returns with a comment: `"set the flag so the consumer can handle polling externally. For now, just mark as polling mode."` This means after 3 SSE failures the hook emits no further state updates. `isStreaming` stays `true` (it was never set to `false` in this path), causing the UI to show a permanently spinning "streaming" state with no new content. The `PollingFallbackBanner` renders but data never refreshes. Fix: set `setIsStreaming(false)` in the polling-fallback branch, start the polling interval using `pollingIntervalRef.current = setInterval(...)` as the spec prescribes, and call `trpc.agency.getRun.fetch(...)` inside it. If tRPC client access inside the hook is the concern, the hook already lives alongside tRPC hooks in the codebase — import and call `trpc` directly, or accept a `onPollForStatus` callback option to keep the hook pure. |
| HIGH | `AgencyChat.tsx:799–816` | `scrollRef` is not passed to `AgencyChatStream`. The existing outer container at line 645 still holds `ref={scrollRef}`, but `AgencyChatStream` renders its own `<div ref={scrollRef} className="flex-1 overflow-y-auto p-4">` which will receive `undefined` for `scrollRef` (the prop is optional and not forwarded). The auto-scroll logic at `AgencyChat.tsx:196–197` writes `scrollRef.current.scrollTop = scrollRef.current.scrollHeight` against the outer container. Meanwhile `AgencyChatStream` renders a second inner scrollable `div` without the `ref`, so that div's scroll position is never managed. In practice the outer container is now a fixed-height non-scrolling wrapper and new messages will overflow without auto-scrolling. Fix: remove the outer `ref={scrollRef}` from `AgencyChat.tsx:645` and pass `scrollRef={scrollRef}` as a prop to `AgencyChatStream`, or remove the `scrollRef` prop from `AgencyChatStream` entirely and keep the existing outer-container scroll management intact (remove the inner `ref` from `AgencyChatStream`). |
| HIGH | `useAgencyStream.test.ts` ("reconnection includes Last-Event-ID header") | The spec-required test for reconnection is titled "reconnection replays from Last-Event-ID" and must assert: (1) the second fetch call includes `"Last-Event-ID": "3"` header, and (2) fallback does not trigger on first reconnect. The implemented test closes the stream naturally (not as an error) — `controller.close()` causes `done=true`, which hits `setIsStreaming(false)` and returns without entering the catch block. No reconnect occurs and no second fetch is made. The test only asserts `msg?.content === "Hi!"` — it verifies `id:` line parsing but never exercises the reconnect path or the `Last-Event-ID` header on a second request. This test is structurally correct for "last event id is stored" but does not satisfy the spec's reconnect assertion. Fix: simulate the first connection dropping with a thrown error (not a clean close), then verify that `fetchSpy.mock.calls[1][1].headers["Last-Event-ID"] === "3"` on the reconnect call. |
| MEDIUM | `AgencyChatStream.tsx:157–164` | The agent-switch badge between messages is dead code. The block filters `activityEvents` and checks `e.timestamp > (msg as any).__ts`, but `AgencyStreamMessage` has no `__ts` field — the cast `(msg as any).__ts` always evaluates to `undefined`, so `e.timestamp > undefined` is always `false`. No badges render from this block; only the bottom-of-stream batch render (lines 178–195) produces badges, which shows all agent switches at the end of the conversation regardless of where they occurred in the message flow. Fix: either add a `timestamp: number` field to `AgencyStreamMessage` (populated at message creation time in the hook) and use it here, or remove the between-messages filtering logic entirely and document that agent-switch badges are only shown at the end of the message list. |
| MEDIUM | `useAgencyStream.ts` (cancel `useCallback` deps) | The `cancel` callback is declared with an empty dependency array `[]` but reads `runIdRef` and `currentAgencyIdRef` via `.current`. This is intentionally safe for refs. However, it also calls `abortRef.current?.abort()`. The `useCallback` has no deps, which is correct for refs — but the function is marked `async` and has a `try/catch` with no state setter on the error path. The real issue is: if `cancel("immediate")` is called while `connect()` is in progress (before the `meta` event), `runIdRef.current` is still `null` (it was reset in `connect()`), so the fetch call is skipped. The abort fires correctly but no cancel request is sent to the backend. The backend run continues until timeout. Fix: either pass `runId` as a parameter to `cancel()` from the `AgencyChat.tsx` side (where the caller can hold it from the `meta` event), or fall back to sending the cancel with only `agencyId` and no `runId` so the backend can cancel the most-recent in-progress run for that agency. |
| MEDIUM | `AgencyChat.tsx:813` | `console.log("[AgencyChat] approval submit: ...")` logs `approvalKey` and `feedback` directly. `approvalKey` is a UUID (low sensitivity), but `feedback` may contain sensitive user content that should not appear in browser console logs in production. Fix: remove the `console.log` entirely; the TODO comment is sufficient. If debug logging is needed, gate it behind `import.meta.env.DEV`. |
| MEDIUM | `useAgencyStream.test.ts` ("disconnect cleans up") | The spec requires: "Assert: abort controller signaled" and "Assert: reconnect timer cleared." The test only asserts `result.current.isStreaming === false`. It does not verify the abort controller was signaled (e.g., `expect(abortSpy).toHaveBeenCalled()`) or that `clearTimeout`/`clearInterval` were called. This is a weakly-specified test — it would pass even if `disconnect()` merely called `setIsStreaming(false)` without touching the abort controller or timers. Fix: spy on `AbortController.prototype.abort` before calling `disconnect()` and assert it was called. |
| LOW | `AgencyChatStream.tsx:148` | Active tool calls are rendered inline only when `msg.isStreaming === true`. If the last assistant message finishes (`isStreaming: false`) before all tool calls complete (a race between `text_delta` ending and `tool_end` arriving), `activeToolCalls` will be non-empty but the inline tool list will not render. They will appear in the post-stream "completed tool calls display" block (lines 169–175) instead — but only after `isStreaming` becomes `false`. This is a cosmetic gap rather than a correctness bug, but it can look like tools "disappeared" then "reappeared." Consider rendering active tool calls independently of `msg.isStreaming` — either always render the tool list when `activeToolCalls.length > 0`, or tie visibility to the global `isStreaming` prop rather than per-message `isStreaming`. |
| LOW | `useAgencyStream.ts` (HTTP error path — reconnect) | The `!res.ok` branch (lines in `startSSEConnection`) calls `setError`, `setIsStreaming(false)`, and `return` — which is correct for 401/403/404. But for 503 (transient server error), this path exits without recording a failure timestamp or attempting reconnection. Only exceptions from the `fetch()` call itself (network-level errors) enter the catch block that drives reconnect logic. A server returning HTTP 500 or 503 will permanently terminate the stream with an error rather than triggering the 3-attempt reconnect window. Fix: treat `res.status >= 500` as a transient error — enter the reconnect path instead of the permanent error path. |
| LOW | `useAgencyStream.ts` (legacy `tool_call` / `tool_result`) | Legacy `tool_call` and `tool_result` events are still forwarded to `activityEvents` but do not update the new `toolCalls` state. An agency backend running the old emitter (without `tool_start`/`tool_end`) will therefore produce activity panel entries but the `AgencyChatStream` tool spinner UI will never render for those runs. This is acceptable given the backward compat constraint, but it should be documented. The spec states to "map legacy names to new handlers internally" — the current implementation leaves `tool_call` events unrouted to `toolCalls`. Fix or document: either create a `ToolCallState` entry from `tool_call` / update it from `tool_result`, or add a comment explaining this deliberate gap. |
| LOW | `AgencyChatStream.test.tsx` ("cancel button") | The test opens the dropdown by clicking the trigger button but never asserts that `onCancel` was called with any mode. The test body ends after `fireEvent.click(cancelBtn)` — clicking the trigger only opens the dropdown; it does not invoke `onCancel`. `onCancel` is only called when a `DropdownMenuItem` is clicked. The test as written verifies the cancel button renders and opens a dropdown but not that it actually calls `onCancel("immediate")` or `onCancel("after_turn")`. Fix: after firing the click on the trigger, also fire a click on the `DropdownMenuItem` with text "Cancel Now", then assert `expect(onCancel).toHaveBeenCalledWith("immediate")`. |

### Summary

The core implementation is structurally correct and comprehensive: all 10 new event types are handled, all 8 legacy events remain backward compatible, the `AgencyChatStream` component renders every spec-required UI element, and cancel/reconnect/replay logic follows the spec contract. The test suite covers nearly all required scenarios with genuine assertions.

Four issues require fixes before merging: the polling fallback activates the flag but never starts the polling interval (leaving users with a frozen UI); `scrollRef` is not forwarded to `AgencyChatStream` from `AgencyChat.tsx`, breaking auto-scroll; the reconnect-replays test does not actually trigger a reconnect; and `startSSEConnection` as a plain inner function has stale-closure risk under Concurrent Mode. Three MEDIUM issues are notable: dead code in the between-messages agent-switch badge logic, an exposed `approvalKey`+`feedback` `console.log` in production code, and a cancel test that opens the dropdown but never asserts the callback was invoked.
