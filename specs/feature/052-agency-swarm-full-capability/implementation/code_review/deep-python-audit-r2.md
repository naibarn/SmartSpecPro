## Findings

| ID  | Severity | File:Line | Anti-Pattern | Description | Recommended Fix |
|-----|----------|-----------|--------------|-------------|-----------------|
| F01 | HIGH | `python-backend/app/services/agency_error_handler.py:95` | RunTerminatedError swallowed in retry | `execute_retry` uses bare `except Exception` which catches `RunTerminatedError` (a subclass of `Exception`). If a retried node raises `RunTerminatedError` (e.g. via a terminate-strategy handler inside `_dispatch_node`), it is caught, stored as `last_error`, and re-raised only after all retries exhaust — delaying termination by up to `maxRetries * backoffMs` seconds and emitting misleading SSE retry events. | Change the `except Exception as exc:` block to first re-raise `RunTerminatedError`: `if isinstance(exc, RunTerminatedError): raise`. Place this check as the first statement inside the except block, before storing `last_error`. |
| F02 | HIGH | `python-backend/app/services/agency_orchestrator.py:1762–1769` | Error handler infinite loop via fallback chain | `_handle_error` strategy `"fallback"` calls `await self._execute_node(self.nodes[redirect_id], ctx)` directly. If the fallback target node also fails and has the current node as its own fallback, or if two error_handlers watch each other's fallback targets, execution recurses with no depth limit. Python stack depth will eventually raise `RecursionError` (not caught), crashing the worker. | Add a `_error_handler_visited: set[str]` to `ExecutionContext` (or pass as parameter). Before executing the fallback target, check if `redirect_id` is already in the visited set; if so, skip to `fallbackMessage` instead of recursing. |
| F03 | HIGH | `python-backend/app/services/agency_orchestrator.py:354–358, 391–396` | Graph cycle causes unbounded recursion | `_execute_node` is purely recursive — router and conditional_branch nodes call `await self._execute_node(...)` with no visited-set or stack-depth guard. A graph with a cycle (node A → router → node A) causes infinite Python call-stack growth and a `RecursionError` crashing the Celery worker. The existing `MAX_LOOP_TIMEOUT` in `LoopHandler` does not protect other node types. | Maintain a `_visited_node_ids: set[str]` counter in `ExecutionContext` (or as a parameter), and enforce a hard `MAX_GRAPH_DEPTH` (e.g. 50). Raise a `RunTerminatedError` or return an error string when the limit is hit. |
| F04 | HIGH | `python-backend/app/tasks/agency_creator_task.py:136, 234` | User-controlled `model` field with no allowlist | `model: str = payload.get("model", "gpt-4o")` is read directly from user-supplied Celery task payload with no validation. This string is passed to `LLMGatewayClient.chat_completion(model=model, ...)`. An attacker can specify an arbitrary model identifier to: (a) bypass tenant-level model restrictions, (b) force calls to expensive models, or (c) probe the gateway for enumerable model IDs. | Define an `ALLOWED_CREATOR_MODELS` set (e.g. `{"gpt-4o", "gpt-4o-mini", "claude-3-5-sonnet-20241022"}`). Validate and replace with default if not in allowlist: `model = model if model in ALLOWED_CREATOR_MODELS else "gpt-4o"`. |
| F05 | MEDIUM | `python-backend/app/tasks/agency_creator_task.py:481–543` | No planSteps count limit in `_llm_plan` response | `_llm_plan` parses and returns the full LLM-generated plan dict. The resulting `plan.get("planSteps")` list is passed to `_llm_design` and then `_validate_spec`, which iterates over every node. If the LLM returns a plan with 100 `planSteps`, `_validate_spec` will build 100 nodes, call `_implement_agency` with them (an O(n) loop per node for tool validation), and attempt to POST a very large payload to the internal API. There is no upper bound on node count. | Add `MAX_PLAN_STEPS = 20` and truncate: `plan["planSteps"] = plan["planSteps"][:MAX_PLAN_STEPS]` before returning from `_llm_plan`. Also enforce the same cap in `_validate_spec` early-return. |
| F06 | MEDIUM | `python-backend/app/tasks/agency_creator_task.py:443–461` | `_fetch_available_skills` SSRF via `INTERNAL_API_BASE` env var | `base_url = os.getenv("INTERNAL_API_BASE", "http://localhost:3000")` is used without any scheme or host validation before making an `httpx.AsyncClient.get()` call. If an attacker can influence the `INTERNAL_API_BASE` environment variable (e.g. via a compromised config store or misconfig), or if a future code path allows the value to flow from user data, this becomes a server-side request forgery vector. The `tenantId` query param is also passed as-is from user payload with no sanitisation. | Pin `base_url` to a hardcoded default (`http://127.0.0.1:3000`) that can only be overridden by a validated allow-list in `settings`. Do not read this from an env var that can contain arbitrary hostnames. For `tenantId`, validate it is alphanumeric/UUID format before including in query params. |
| F07 | MEDIUM | `python-backend/app/services/agency_guardrails.py:344–379` | `custom_endpoint` fails open on external service error | After SSRF validation passes, if the external endpoint call raises any exception (timeout, connection error, non-2xx after `raise_for_status`), the handler returns `GuardrailResult(passed=True, action="allow")`. A strict-mode `custom_endpoint` guardrail therefore fails **open** on network errors, which is inconsistent with the fail-closed behaviour applied to all other strict guardrails (line 94–99). | Honour the guardrail `mode` field inside `_strategy_custom_endpoint`: pass `mode` as a parameter and return `GuardrailResult(passed=False, action="block", message="External guardrail unreachable")` when `mode == "strict"` and the call fails. |
| F08 | MEDIUM | `python-backend/app/services/agency_guardrails.py:347–358` | `custom_endpoint` timeout not capped | `timeout_ms = config.get("timeout", 5000)` is read directly from user-supplied guardrail config with no upper-bound cap. A user could set `timeout=3600000` (1 hour), blocking an async worker slot for that entire duration per guardrail evaluation. | Cap: `timeout_ms = min(int(config.get("timeout", 5000)), 30_000)` (30-second ceiling). |
| F09 | MEDIUM | `python-backend/app/services/agency_run_context.py:56–62` | `get_sync` / `set_sync` bypass lock in concurrent contexts | The file docstring and comments state these sync helpers are "only safe when no concurrent async writes are in progress" and that "parallel fan-out callers must use async methods instead". However, there is no enforcement: nothing prevents `parallel_fan_out` branches from calling `get_sync` / `set_sync` on a shared `AgencyRunContext`. A race condition would produce silent data corruption (lost updates) with no error. | Either remove `get_sync`/`set_sync` entirely and require all callers to use the async API, or add a runtime assertion: `assert not self._lock.locked(), "get_sync called while async lock is held"`. Add a comment on `parallel_fan_out` in the orchestrator explicitly prohibiting sync access. |
| F10 | LOW | `python-backend/app/services/agency_error_handler.py:22–37` | `scrub_error_payload` homoglyph bypass | `SCRUB_PATTERNS` match ASCII literals (e.g. `postgresql://`, `sk-`, `Bearer`). A Cyrillic homoglyph substitution (e.g. `роstgresql://` using Cyrillic `р` U+0440 instead of Latin `p` U+0070) would pass all 14 patterns undetected and leak connection string fragments into SSE events or context. This is a low-exploitability issue because it requires the error message itself to contain homoglyphs, which would only occur if an upstream library or injected value used them. | Add Unicode normalisation before scrubbing: `import unicodedata; result = unicodedata.normalize("NFKD", raw).encode("ascii", "ignore").decode("ascii")` applied to `raw` before the pattern loop. This converts homoglyphs to their closest ASCII equivalents. |
| F11 | LOW | `python-backend/app/services/agency_communication_flows.py:50–70` | `maxRoundTrips` only enforced at call-site check | `RoundTripTracker.is_limit_reached` correctly checks the limit, but the tracker instance lives only in `AgencyOrchestrator._round_trip_tracker` (an in-memory dict per orchestrator instance). For long-running Celery tasks that restart (e.g. due to worker restart with `acks_late`), the tracker is reset to zero on each task start, allowing unlimited round-trips across restarts. | Persist the round-trip counter in Redis under a key scoped to `run_id` + agent pair, with TTL matching the run timeout. Check Redis on `is_limit_reached` if a Redis client is available, with in-memory fallback. |

## Non-Findings (Confirmed Safe)

- **`_validate_spec` idempotency** — Function is purely transformative (normalises config, strips invalid IDs, sets defaults). Running it twice on already-validated data produces identical output. No database writes, no side effects. Safe to call multiple times.
- **`AgencyRunContext` tenant isolation** — Each agency run constructs a new `AgencyRunContext` instance. No shared singleton. Redis keys are scoped by `run_id` (in `AgencyEventEmitter`). Tenants cannot access each other's contexts via this class.
- **SSE event data leakage** — `AgencyEventEmitter.emit` is generic and does not itself add node configs or API keys. The risk is at call-site. Reviewed all `emit()` calls in orchestrator: `error_handled` events use `scrub_error_payload`, `text_delta` contains only agent output text, `agentic_cycle` contains only cycle number and status. No API keys or `user_token` values are directly included in emitted event data.
- **`pii_detection` regex compilation errors** — `PII_PATTERNS` are module-level constants compiled at import time (not at request time from user input). A compilation failure would crash the worker at startup, not silently fail at runtime. No user-controlled patterns reach `re.compile`.
- **JSONPath ReDoS** — `jsonpath_ng` uses a PEG parser (Lark grammar), not Python `re` under the hood for expression parsing. The primary ReDoS risk vector (backtracking regex) does not apply. The 500-char limit and exception catch are adequate defensive layers.
