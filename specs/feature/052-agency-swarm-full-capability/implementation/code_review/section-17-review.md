### Findings

| Severity | File:Line | Issue | Recommended Fix |

| HIGH | `agency_conditional_branch.py:997` | **ReDoS risk in `regex` operator**: `re.search(rule_value, str_val)` compiles a user-supplied regex on every evaluation with no timeout or length cap. A pathological pattern like `(a+)+$` applied to a long string can hang a worker for seconds. | Add a regex length guard (`if len(rule_value) > 200: return False`) and wrap `re.search` in `re.escape`-validated compilation, or run with a `signal.alarm`/`asyncio.wait_for` timeout. At minimum, add a max-length check on `rule_value` before calling `re.search`. |
| HIGH | `agency_conditional_branch.py:1040` | **`evaluate_rule_based` signature drops the `ctx` parameter**: The spec (`section-17-conditional-branch-node.md:141`) requires the signature `evaluate_rule_based(rules, previous_output, ctx)` because the `ctx` parameter is required to give rule evaluation access to `ExecutionContext` for potential future read of metadata. More critically, the orchestrator passes only two positional arguments, so today this is consistent — but the Vitest schema test (`agencyConditionalBranch.test.ts`) cannot test the cross-check of `defaultTargetNodeId` against the live node list because the context argument is absent. This is a contract deviation. | Accept that the pure-function design omitting `ctx` is a deliberate simplification, but document it explicitly. The spec text states `ctx: ExecutionContext` in the signature — if the deviation is intentional, update the spec note or add a comment explaining that `ctx` is handled by the orchestrator wrapper. |
| HIGH | `agency.ts:823-824` | **`defaultTargetNodeId` not cross-validated against sibling node IDs**: The spec (§7, validation list item 1) explicitly requires that `defaultTargetNodeId` must reference a node ID present in the same agency's node list. The implementation only checks `!cfg?.defaultTargetNodeId` (non-empty string) but never verifies the value resolves to a real node. Same omission applies to `rule.targetNodeId` and `category.targetNodeId`. The `.superRefine()` block has access to the full `agents` array on the outer object, making this cross-check feasible. | Inside the `conditional_branch` validation block, collect all node IDs from the agents array: `const nodeIds = new Set(input.agents.map(a => a.id))`. Then assert `nodeIds.has(cfg.defaultTargetNodeId)`, and similarly check each `rule.targetNodeId` and `category.targetNodeId`. |
| MEDIUM | `ConditionalBranchNodeCard.tsx:448-470` | **`context_check` mode renders zero source handles on the canvas**: The card renders per-rule handles for `rule_based` and per-category handles for `llm_classify`, but the `context_check` branch has no equivalent handle rendering for `contextConditions`. Spec §4 says "One source handle per rule/category" and lists all three modes under the same handle contract. In `context_check` mode users cannot draw edges from individual condition branches; only the `default` handle is available, making per-condition routing impossible in the canvas. | Add a `context_check` handle block analogous to the `rule_based` and `llm_classify` blocks, mapping `contextConditions` to source handles with IDs derived from `cond.targetNodeId` or array index. |
| MEDIUM | `agency_conditional_branch.py:1093-1103` | **`evaluate_llm_classify` creates a new `httpx.AsyncClient` per call**: Instead of reusing the module-level or injected client (which is the established pattern in `agency_tools.py`), it constructs a fresh `AsyncClient` for each classification request, bypassing connection pooling and making the function harder to mock reliably. The orchestrator already has `self.http_client` available. | Pass the existing async HTTP client as a parameter (`client: httpx.AsyncClient`) or use a module-level singleton. The test mock pattern is currently workable but fragile. |
| MEDIUM | `agencyConditionalBranch.test.ts` (entire file) | **Vitest tests validate a locally-redefined schema, not the `saveBuilder` procedure itself**: All 7 spec-required Vitest tests import nothing from `agency.ts` and instead reconstruct the Zod schema inline. If the `saveBuilder` `.superRefine()` block is updated or contains a bug, these tests cannot catch it. The tests prove the schema shape, not the procedure behavior. | Either import the `conditionalBranchSchema` extracted from `agency.ts` (or test via a tRPC test client calling `saveBuilder`) so the tests verify the actual gate in the router. At minimum, add a comment clearly stating these are schema unit tests and a companion integration test against the procedure is needed. |
| MEDIUM | `agency_orchestrator.py:1208` | **`incoming[0]` assumes exactly one incoming edge**: When a `conditional_branch` node has more than one incoming edge (fan-in topology after a parallel branch), only the result of the first incoming edge is used as `previous_output`. The second incoming result is silently discarded. This is the same issue noted in prior section reviews for other routing nodes. | Document in a comment that multi-input `conditional_branch` nodes only inspect the first incoming edge's result, and that future fan-in support requires an aggregation step before this node. If the orchestrator already has a convention for this (e.g., `router` does the same), cite it. |
| MEDIUM | `NodePropertyPanel.tsx:17` (emoji map) | **`conditional_branch` is assigned the aggregator emoji (`\uD83D\uDD00`, 🔀)**: The aggregator node already uses this emoji. Sharing an emoji causes visual ambiguity in the node type badge display. The spec does not prescribe an emoji but the `GitFork` icon used in the card suggests something like ⑂ or a fork symbol. | Use a distinct emoji, e.g., `\u2BD1` (⯑) or `\u29D6` (⦖), or simply `"🔀"` after confirming it is not already used by another node type. |
| LOW | `test_conditional_branch.py` | **Spec test case "defaultTargetNodeId validated to exist in agency node list — raises error if missing" is absent**: The pytest file covers all 17 spec-required test cases except this one. The orchestrator's `_evaluate_conditional_branch` correctly falls back to `defaultTargetNodeId` when `result_target not in self.nodes`, but there is no test that verifies the orchestrator handles a `defaultTargetNodeId` that itself is not in `self.nodes` (the fallback-of-last-resort string message). | Add a test that calls `_evaluate_conditional_branch` with a `defaultTargetNodeId` not present in `self.nodes` and asserts the graceful fallback path is taken (returns `None` or the string message). |

### Summary

The section-17 implementation is structurally complete: all three evaluation modes are implemented in a well-factored pure-function module, the orchestrator wiring is correct, the amber-themed canvas card renders with the right icon and badges, and the property panel form is fully featured. Three issues require fixes before merge. The `saveBuilder` validation does not cross-reference `defaultTargetNodeId` or per-rule/category `targetNodeId` values against the agency's actual node list, which the spec explicitly requires and which is feasible within the existing `.superRefine()` context. The `context_check` mode produces no per-condition source handles on the canvas card, making per-condition edge drawing impossible for that mode. The `regex` operator in `evaluate_rule_based` applies user-supplied patterns with no ReDoS protection, which is a denial-of-service risk given that orchestrator workers are shared across tenants. The bundled out-of-scope changes (fal.ai async fix, spec-054 artifacts) should be separated into a dedicated commit.
