### Findings

| Severity | File:Line | Issue | Recommended Fix |
|---|---|---|---|
| HIGH | `agency_orchestrator.py` (diff +341–+378) | **Checkpoint 3 (handoff guardrails) is entirely absent.** Spec §3 "Orchestrator Integration" requires guardrails to be executed at three checkpoints. Only input (CP1) and output (CP2) are implemented. The handoff path — when the orchestrator routes a message from one agent to another — never calls `execute_guardrails(..., is_handoff=True)` with the receiving agent's guardrails. | In `_execute_agent_node` or wherever the orchestrator dispatches a handoff, load the *receiving* agent's guardrails and call `execute_guardrails(receiving_guardrails, handoff_message, "input", is_handoff=True)`. Add a corresponding test in `test_agency_guardrails.py`. |
| HIGH | `agency_orchestrator.py` (diff +1065–+1070) | **Input guardrail guidance and redaction applied in wrong order.** At CP1, the code first checks `action == "guidance"` (prepends text), then separately checks `redacted_message` and overwrites `augmented_message`. If a PII-redact guardrail fires (action="redact", passed=True, redacted_message set), the guidance branch is skipped, but then the redacted message immediately *replaces* `augmented_message`, discarding the guidance prefix from any earlier guidance-mode guardrail that already ran. The combined-mode path (guidance failure followed by redact) silently drops the guidance. Additionally, a pure guidance result with `redacted_message=None` still falls through to the redact branch check harmlessly, but the ordering creates confusion. | Merge both conditions: apply redaction first if present, then prepend guidance text if any. A single `if result.action in ("guidance", "redact")` block that applies both transformations in order would be cleaner. |
| HIGH | `agencyGuardrails.test.ts` (lines 44–201) | **tRPC procedure integration tests are entirely absent.** All tests in the Vitest file exercise only inline Zod schemas reconstructed in the test body, or call imported validator functions directly. No test uses `createCallerFactory` (as required by the spec test pattern) to call the actual `createGuardrail`, `updateGuardrail`, `deleteGuardrail`, `assignGuardrailToAgent`, or `testGuardrail` procedures with a mocked `db` and `ctx`. The spec required 12 procedure-level tests (including cross-tenant FORBIDDEN assertions, tenantId-from-session enforcement, CONFLICT handling). Zero of those 12 are present; the file instead duplicates the schema-enum validations that the Zod schemas already guarantee. | Rewrite the test file using `createCallerFactory` as documented in the spec. At minimum: add tests for `updateGuardrail` cross-tenant FORBIDDEN, `createGuardrail` inserting `tenantId` from ctx (not from input), `assignGuardrailToAgent` cross-tenant FORBIDDEN, `assignGuardrailToAgent` CONFLICT on duplicate, and `testGuardrail` calling the Python backend. |
| HIGH | `agency_orchestrator.py` (diff +1083–+1114) | **Output guardrail retry logic is scoped to one guardrail at a time but response variable overwrites between iterations.** The nested loop iterates over output guardrails, and on retry it calls `self.adapter.run(... message=feedback ...)`, assigning the result to `response`. If there are two output guardrails (G1 and G2), G1's retry path sets `response = retry_result.response`, then the outer loop moves to G2, which now validates G1's already-revised `response` — this is correct intent. However, on the last retry attempt when `out_result.passed` is False, the `break` statement on line `if out_result.passed: break` only breaks the *inner* (`for attempt`) loop, not the outer guardrail loop. The outer guardrail loop then continues to G2 with the *failed* `response`. The spec says "if failed after all attempts: in strict mode, return error message." The current code returns the error only at the end of the inner loop, then falls through to return `response` (which failed G1's validation) to G2. A strict-mode final failure should short-circuit the outer loop too. | After the inner `for attempt` loop exits without passing, check `if not out_result.passed and g.mode == "strict": return ...` immediately (currently done but execution falls through to `return response` at the function level regardless). Use an explicit `break` + post-loop check on the outer loop, or restructure with `else`. |
| MEDIUM | `agency_guardrails.py` (line ~835) | **`regex_match` strategy has no ReDoS (regex denial-of-service) protection.** `re.search(pattern, message, re.IGNORECASE)` is called with an arbitrary user-supplied pattern string. The spec explicitly calls out "Regex DoS: compiled regex patterns should use a timeout or a safety check." The implementation does none of this. A pathological pattern like `(a+)+$` against a long message will hang the event loop. | Either: (a) compile regex with `regex` library (third-party, with timeout support), (b) enforce a max message length before regex evaluation (e.g., 50,000 chars, which the tRPC `sampleMessage` field already caps), or (c) use `concurrent.futures` with a thread-pool timeout. At minimum add a `len(pattern) <= 1000` guard at runtime (the Zod layer enforces this at creation, but the execution engine should not trust stored data unconditionally). |
| MEDIUM | `internal_guardrails.py` (lines 615–622) | **`test_guardrail` endpoint constructs a `GuardrailDefinition` without `validation_attempts`, `sort_order`, or `enforce_on_handoff`, relying on dataclass defaults, but the `type` is hardcoded to `"input"`.** If a caller sends a request to test an `output`-type strategy (e.g., `json_schema`), the endpoint will still execute it correctly (the strategy function itself is type-agnostic), but the `execute_guardrails` filtering will match it against the hardcoded `"input"` type and the guardrail will still be included in the result (since the test guardrail's `.type` and the passed `guardrail_type` are both `"input"`). This means the endpoint cannot be used to test `output`-mode retry behaviour accurately. More critically, there is no validation that `request.strategy` is one of the 7 allowed values — an unknown strategy silently returns `passed: True` (fail-open path in `_dispatch_strategy`). | Add a `Literal["keyword_block", "regex_match", "llm_classify", "json_schema", "max_length", "pii_detection", "custom_endpoint"]` type annotation on `GuardrailTestRequest.strategy`, or validate against the `STRATEGY_MAP` keys and return a 422 if unknown. |
| MEDIUM | `agency_service.py` (diff +1130–+1162) | **Raw SQL with positional row indexing (`row[0]` through `row[9]`) is fragile.** If the column order in the SELECT changes during refactoring, all index references silently map to the wrong fields with no type error. For example, `row[8]` is assumed to be `isEnabled` and `row[9]` to be `agentId`, but there is no enforcement. The `text()` query is not tested. | Use named mappings: either `result.mappings().all()` with `row["isEnabled"]` etc., or switch to an ORM join via SQLAlchemy 2 select statements. Add a test in `test_agency_guardrails.py` (or a new integration test) that exercises `_load_guardrails_for_agents` with a seeded DB. |
| MEDIUM | `agency_orchestrator.py` (diff +1059) | **`agent_guardrails` variable is declared *before* `augmented_message` is finalized by KB context retrieval.** The variable is captured at `augmented_message = ctx.get_context_text()` (diff line 1056), then CP1 runs on that value. However, the spec's Checkpoint 1 is meant to guard the full message that the agent will receive, including KB context appended later in `agent_instructions`. If the KB context retrieval adds further text after CP1, the input guardrail never sees that appended content. The spec does not explicitly define the ordering, but placing CP1 before KB augmentation means an admin's keyword-block rule for confidential data could be bypassed if that data enters via KB injection. | Move CP1 to after all augmentation of `augmented_message` is complete (after KB context is appended to agent instructions), or document the deliberate early-execution decision and ensure KG context is not expected to carry sensitive guarded content. |
| MEDIUM | `agencyGuardrails.test.ts` (lines 99–113) | **SSRF tests call `validateSsrfUrl` directly from the module import but the import is hoisted above the `vi.mock` calls.** `import { validateSsrfUrl } from "../../services/ssrfValidator"` at line 40 is a static import that runs before any mocks. If `ssrfValidator.ts` has top-level side effects or depends on modules that are mocked elsewhere, this can produce unexpected results. Additionally, the test verifies that `validateSsrfUrl` throws but does not verify the Zod `.superRefine()` in the actual `createGuardrail` procedure plumbs the error back correctly (since no procedure-level tests exist). The SSRF tests are fine as standalone unit coverage of the validator, but they do not cover the integration path. | Accept these as standalone SSRF validator unit tests. Add a procedure-level test (via `createCallerFactory`) that submits a `custom_endpoint` strategy with a private IP endpoint and asserts a Zod `PARSE_ERROR` response. |
| LOW | `agency_guardrails.py` (line ~874) | **`llm_classify` sends the user message directly in the `user` role with no system prompt.** The spec says "The `config.prompt` is set by the guardrail creator (admin/owner), not the end user" and "user content is placed in the human-message role only." However, the implementation constructs a single-element messages list `[{"role": "user", "content": prompt}]` where `prompt` already contains the verbatim user message substituted in via `.replace("{message}", message)`. If the guardrail creator's prompt template is poorly designed, the user message can craft a jailbreak by making the combined text appear as an instruction. The spec requires a fixed prompt template where user content is in the human role *separately*. | Split into a two-message format: `[{"role": "system", "content": prompt_template_without_message}, {"role": "user", "content": message}]`. This prevents prompt injection via message content. |
| LOW | `updateGuardrail` in `agency.ts` (diff ~+335) | **`updateGuardrail` performs a `SELECT *` without a `tenantId` filter on the initial ownership fetch.** Line `db.select().from(agencyGuardrails).where(eq(agencyGuardrails.id, input.guardrailId))` fetches by ID alone, then checks `existing.tenantId !== tenantId` in application code. This pattern is safe logically but wastes a DB round-trip and is subtly different from the CREATE path (which uses an `and(eq(agencies.id, ...), eq(agencies.tenantId, tenantId))`). Also applies to `deleteGuardrail`, `testGuardrail`, and `removeGuardrailFromAgent`. | Use `and(eq(agencyGuardrails.id, input.guardrailId), eq(agencyGuardrails.tenantId, tenantId))` in the WHERE clause directly, returning NOT_FOUND for both the "does not exist" and "wrong tenant" cases (acceptable from a security perspective since the ID is UUID). This eliminates the separate `if (existing.tenantId !== tenantId)` check and avoids leaking existence of cross-tenant IDs. |
| LOW | `agency_guardrails.py` (line ~880) | **`llm_classify` response comparison uses substring matching (`block_if in content`).** If `blockIf = "harm"`, any response containing `"harm"` anywhere — including `"no harm detected"` or `"harmless"` — will trigger a block. The spec says "Compare response text (lowered, stripped) against `config["blockIf"]` (lowered)" without specifying exact vs. substring matching, but the intent from the test spec ("LLM returns `harmful`" with `blockIf: "harmful"`) suggests exact or word-boundary matching. | Use `content.strip() == block_if` for exact match, or `re.search(rf"\b{re.escape(block_if)}\b", content)` for word-boundary matching. Document the matching semantics in a code comment. |
| LOW | `listGuardrails` in `agency.ts` (diff ~+385) | **`listGuardrails` is missing a rate-limit middleware.** Every other guardrail procedure applies `createRateLimitMiddleware({ namespace: "agency-guardrail", limit: 30, windowMs: 60_000 })` via `.use()`, but `listGuardrails` is a bare `protectedProcedure` with no rate limit. A malicious authenticated user could hammer the list endpoint to enumerate guardrail configurations or drive up DB load. | Add `.use(createRateLimitMiddleware({ namespace: "agency-guardrail", limit: 30, windowMs: 60_000 }))` to `listGuardrails`. |

### Summary

The Python layer (execution engine, strategies, orchestrator integration, internal test endpoint) is well-implemented and largely spec-compliant. All 7 strategies are present, the fail-open contracts are correct, SSRF protection is applied at both creation and execution time, and the pytest test suite covers all spec-required strategy cases.

Three issues require immediate attention before merge: the handoff checkpoint (CP3) is entirely absent from the orchestrator diff despite being a first-class spec requirement; the Vitest test file contains no procedure-level tests (only schema unit tests that duplicate what Zod already guarantees, leaving the tRPC auth and tenant-isolation logic completely untested); and the output guardrail retry loop has a control-flow defect where a strict-mode final failure does not short-circuit the outer guardrail loop. The `regex_match` strategy also lacks ReDoS protection, which the spec explicitly called out as a key security consideration.
