## Review Report — Section 15: Observability & Tracing

### Verdict: APPROVE_WITH_FIXES

### Findings

| Severity | File:Line | Issue | Recommended Fix |
|---|---|---|---|
| HIGH | `agencyTraceService.ts:980-985` | `DELETE ... LIMIT` is non-standard SQL. PostgreSQL does **not** support `LIMIT` on a `DELETE` statement; only MySQL does. This will throw a syntax error at runtime and the batch-delete loop will never make progress. | Replace with a CTE-based batch delete: `WITH batch AS (SELECT id FROM agency_run_traces WHERE "tenantId"=$1 AND "createdAt"<$2 LIMIT 1000) DELETE FROM agency_run_traces WHERE id IN (SELECT id FROM batch)`. |
| HIGH | `agencyStream.ts:267-270` | `ev.data` at the `trace_complete` branch is typed as `Record<string, unknown>` from `JSON.parse`, but `persistRunTrace` expects `TracePayload` which requires `runId`, `agencyId`, `tenantId`, and `trace` as non-optional fields. No runtime validation is performed. A malformed or incomplete `trace_complete` event from Python will call `persistRunTrace` with a partial object, producing a DB insert with undefined required fields that either crashes or silently stores corrupt data. | Add a Zod runtime parse of `ev.data` against `TracePayload` schema before calling `persistRunTrace`. On validation failure, log the error and skip persistence rather than calling with unsafe input. |
| HIGH | `agency_service.py:947-949` | Trace is never persisted on the **legacy agent path** (when `should_use_orchestrator()` returns `False`). `TraceCollector` is only instantiated and `emit("trace_complete", ...)` is only called inside the orchestrator branch. The legacy multi-agent path (lines 953–onward) has no `TraceCollector` integration whatsoever, so every agency run on the legacy path produces zero trace data. | Instantiate `TraceCollector` before the `should_use_orchestrator` branch fork, and emit `trace_complete` at the end of the legacy path the same way the orchestrator path does. |
| HIGH | `scheduler.ts:1042-1045` | The `sweepExpiredRunTraces` function is **never registered** as a cron job. The function is exported and defined but nothing in `apps/web/server/_core/index.ts` or any other entry point calls or schedules it. The spec required a daily cron at 03:00 UTC. Expired traces will never be deleted. | Import `sweepExpiredRunTraces` in `server/_core/index.ts` and schedule it with the same `setInterval`/cron pattern used by `startPendingMediaScheduler` or another existing periodic job, targeting daily execution. |
| MEDIUM | `agencyTraceService.ts:844-845` | `persistRunTrace` silently returns on `!db` without logging. A missing DB connection during `trace_complete` handling means the trace is silently dropped — the SSE `.catch` logs a generic error but the `!db` guard path emits nothing. | Replace `if (!db) return;` with `if (!db) { console.error("[AgencyTraceService] DB unavailable, dropping trace for runId:", payload.runId); return; }` to preserve observability when the guard fires. |
| MEDIUM | `scheduler.ts:1035-1037` | `sweepExpiredRunTraces` uses a **single global retention value** from `systemSettings`, then applies it to all tenants. The spec requires per-tenant retention overrides (Test 8 in the spec: "retention cleanup respects per-tenant retention override"). The test itself in `agencyTraces.test.ts` is also absent — neither the code nor the test implement per-tenant retention. | Query per-tenant overrides by joining against a per-tenant settings key (e.g., `category="agency", key="trace_retention_days"` scoped by `tenantId`), falling back to the global default only when no per-tenant override exists. Add the missing test. |
| MEDIUM | `agency_orchestrator.py:228` | The `type` argument for non-agent nodes (router, aggregator, skill_call, knowledge_base, human_approval) is hardcoded to `"tool_call"`. These are distinct node types in the spec and producing misleading span types will make the trace viewer show all non-agent nodes as tool calls. The spec defines valid span types as `agent_turn`, `tool_call`, `guardrail`; the type mapping for orchestrator nodes is underdefined. | Map orchestrator node types explicitly: `router` / `aggregator` / `knowledge_base` / `skill_call` → `"tool_call"` is acceptable if a new type is not desired, but `human_approval` should map to a distinct label or `"guardrail"`. Document the mapping decision in a comment. |
| MEDIUM | `agencyTraces.test.ts:715-760` | The Vitest tests for `listRunTraces` only assert that specific Drizzle builder methods were **called** — they never assert that the `tenantId` filter was actually included in the `where` clause. The spec required "listRunTraces filters by tenantId" as a correctness assertion (not just a call-count check). A bug that drops the `tenantId` condition entirely would not be caught. | In the `listRunTraces` tests, capture the argument passed to `mockDb.where` and assert it contains the `tenantId` eq-condition, or use `expect.objectContaining` on the call args. Add the per-tenant retention override test that the spec requires. |
| MEDIUM | `agencyStream.ts:267` | `trace_complete` is emitted to SSE clients **before** being persisted. Clients will see the event in the SSE stream (it is written to `res` at line 264 before the `persistRunTrace` call on line 268). Browsers listening to the stream could navigate away or refresh before persistence completes, potentially consuming the event without the DB row existing yet. While `.catch` is used, there is no retry mechanism. | Reorder: call `persistRunTrace(ev.data)` and await it (or use a fire-and-forget queue) **before** flushing the event to the SSE client so observers can rely on the trace being queryable when they receive the event. Alternatively, document explicitly that traces may not be immediately queryable. |
| LOW | `agency_trace_collector.py:1364-1374` | `start_span` is **not** protected by `asyncio.Lock`. Only `start_span_async` acquires the lock. The orchestrator calls the synchronous `start_span` (not `start_span_async`) at line 225 of `agency_orchestrator.py`. If concurrent tool calls in section-19 loop nodes call `start_span` directly, the dict mutation is unprotected. | Either make `start_span` acquire the lock internally (using `asyncio.get_event_loop().run_until_complete` is not viable; restructure to always use `start_span_async` from async contexts) or document clearly that `start_span` is only safe to call from the synchronous orchestrator main loop (not from concurrent asyncio tasks). |
| LOW | `TraceViewerTimeline.tsx:373` | `totalDurationMs` falls back to `Math.max(...spans.map(s => s.endMs ?? 0))` when `trace.durationMs` is null. If all spans have `endMs: null` (e.g., for a run cancelled mid-span), `Math.max()` will return `0` and all timeline bars will render at 0% width, making the view look broken. | Guard: if `totalDurationMs === 0` after the fallback, hide the timeline bars and show a "Duration unavailable" placeholder rather than rendering invisible bars. |
| LOW | `RunHistoryPanel.tsx:189` | Pagination control renders only when `total > LIMIT` (20). If exactly 20 traces exist and offset is 0, the "Previous"/"Next" controls never appear. This is correct. But the pagination range display (`{offset + 1}–{Math.min(offset + LIMIT, total)}`) shows `1–20` even when `total < 20` because `offset` starts at 0. When `total = 0`, the empty state branch renders instead, which is fine. The edge case is `total = 0` while `isLoading = false` — the empty state and the `traces.map` both render simultaneously because `!isLoading && traces.length === 0` shows the empty state but the `div.space-y-1` is also rendered (with no children). This is harmless but unnecessary. | Move the `div.space-y-1` wrapper inside a conditional so it does not render when `traces.length === 0`. |
| LOW | `agencyTraces.test.ts` | **Two spec-required tests are absent**: (1) "listRunTraces supports dateRange filter" — present in spec TDD, not implemented; (2) "retention cleanup respects per-tenant retention override" — present in spec TDD, not implemented. The test file covers 9 of 10 spec-required Vitest tests (counting the 2 sweep tests). | Add the missing two tests. |

### Summary

The core `TraceCollector` class is well-implemented: span hierarchy, secret scrubbing, output truncation, async-safety variants, and `get_trace_summary` are all correct and thoroughly tested in pytest. The `agencyTraceService.ts` and tRPC procedures (`listRunTraces`, `getRunTrace`) correctly enforce tenant isolation. The frontend `RunHistoryPanel` and `TraceViewerTimeline` are functionally complete and follow existing Sheet/tRPC patterns.

Four blocking issues require fixes before merge: (1) the `DELETE ... LIMIT` syntax will crash on PostgreSQL and must be rewritten as a CTE-based batch delete; (2) `trace_complete` event data is passed to `persistRunTrace` without runtime validation, creating a path for corrupt DB inserts; (3) the legacy agent path (non-orchestrator) never creates or emits a trace, leaving a large category of runs unobserved; (4) `sweepExpiredRunTraces` is defined but never scheduled, meaning expired traces will accumulate indefinitely.
