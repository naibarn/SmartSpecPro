### Findings

| Severity | File:Line | Issue | Recommended Fix |
|---|---|---|---|
| HIGH | `agency.ts:777-780` | `getById` leaks encrypted MCP tokens — `agencyAgents` is fetched with `.select()` (all columns), which includes `mcpServerTokensEncrypted`. Every caller of `getById` (frontend builder, any client with read access) receives the encrypted token blob in the response payload. | Use a column projection: `db.select({ id, name, nodeType, ... /* omit mcpServerTokensEncrypted */ }).from(agencyAgents)`. Return a boolean `hasMcpTokens` flag instead. |
| HIGH | `agency.ts:4038-4042` | `submitApproval` has no tenant isolation check on the conversation lookup. The query at line 4041 fetches `agencyConversations` by `runId` alone — no `tenantId` filter. A user in tenant B who guesses a `runId` belonging to tenant A's run can approve or reject it (they only need to know the UUID). | Add `eq(agencyConversations.tenantId, tenantId)` to the WHERE clause, or verify `conv.tenantId === tenantId` after fetch and throw FORBIDDEN if they differ. |
| HIGH | `agency.ts:2345-2348` | `restoreVersion` fetches the version by `versionId` alone before verifying the owning agency's tenant. The version row is loaded unconditionally at line 2345; tenant check happens at lines 2353-2358. Between the two queries, no lock is held. More critically: snapshot payload is applied verbatim from the DB — the `nodeConfig` field on every node is inserted without any schema validation. A snapshot that was saved while malicious `nodeConfig` content was present (e.g., crafted `systemPromptOverride`, `outputSchema` with injection payloads, `approvalKey` spoofing) is replayed directly into `agencyAgents`. The restore path skips the `saveBuilder` Zod `.superRefine()` validation. | Fetch version with a single join that also asserts `agencies.tenantId = tenantId` (eliminates two-step SELECT). Pass the snapshot `nodeConfig` through the same Zod schema used by `saveBuilder` before inserting, or at minimum strip fields that are not in a known-safe allowlist. |
| HIGH | `agency_orchestrator.py:1582-1589` | `_call_skill` does not pass `tenant_id` to the skill execution endpoint. The POST to `/api/v1/skills/execute` carries the user JWT (`ctx.user_token`) but no explicit `tenant_id` in the body. If the skill execution endpoint derives tenant from the JWT rather than a body param, this works — but if it trusts a body-supplied `tenant_id` (or if the JWT is shared/federated), the tenant scope of the skill call is ambiguous. More concretely: the `context` field passed to the endpoint is `ctx.get_context_text()`, which includes `ctx.results` from all prior nodes. If a prior `knowledge_base` node retrieved documents from a different tenant scope (impossible by design, but a defence-in-depth gap), those documents are forwarded verbatim to the skill. | Add `tenant_id: ctx.tenant_id` to the skill execute request body and verify server-side that the JWT-derived tenant matches. Document explicitly that `ctx.tenant_id` is the authoritative scope for all downstream calls from `_call_skill`. |
| MEDIUM | `agency_orchestrator.py:942-956` | `_shared_tools_cache` is populated once per orchestrator instance and reused for all nodes in the run. The cache has no tenant scope stamp. If an orchestrator instance is ever reused across runs (e.g., pooled or accidentally shared via a class-level cache higher in the call stack), shared tools from run A are silently used in run B. The cache itself is correctly scoped to `agency_id`, but there is no assertion that the `agency_id` belongs to `ctx.tenant_id` at cache population time. | At cache population time, assert `agency_id`'s `tenantId` matches `ctx.tenant_id`. Add a comment making it explicit that the instance MUST NOT be reused across tenant contexts. |
| MEDIUM | `agency_orchestrator.py:122` | `ctx.results: dict[str, str]` grows unbounded as nodes execute. There is no size cap on either the number of entries or the length of each entry value. In a long graph with many agent nodes that each produce large outputs, `ctx.results` can accumulate several MB. `get_context_text()` reads up to 5 knowledge items and truncates each to 300 chars, but it reads ALL `ctx.results` and truncates each to only 200 chars — still unbounded in entry count. In a `parallel_fan_out` with 10 branches × 10 sub-nodes = 100 entries, at 200 chars each this is 20 KB passed to every subsequent LLM call, inflating tokens and costs silently. | Cap `ctx.results` at a maximum of N entries (e.g., 50) using an LRU or FIFO eviction policy. Alternatively, cap `get_context_text()` to the most-recent K results only. Document the current behaviour explicitly. |
| MEDIUM | `agency_orchestrator.py:1797-1799` | `data_transform` node's `outputKey` is written into `ctx.shared_context` using the node-config-supplied key string with no validation. A malicious or misconfigured `outputKey` of `"approval:abc123"` would collide with the approval tracking namespace used by `_await_approval` (line 1659: `key.startswith("approval:")`). An attacker who can edit a node's `nodeConfig` (e.g., via a compromised `saveBuilder` call or a malicious version restore) could inject a fake pending-approval entry, causing `_await_approval` to immediately find a pre-seeded `approval_key` and skip waiting for real human input. | Validate `outputKey` against a denylist of reserved prefixes (`"approval:"`, `"browser:"`, etc.) at save time in the `saveBuilder` Zod schema and at execution time before writing. |
| MEDIUM | `agency.ts:1073` (`update`) | The `update` procedure lacks rate limiting. Unlike `saveBuilder` (also unrate-limited, but a noted pre-existing gap), `update` can change an agency's `topology`, `triggerPhrases`, `systemPrompt`, and `cacheConversationStarters`. A tight loop of update calls is the only mechanism needed to cause repeated Drizzle write load with no throttle. Several write procedures are similarly unrate-limited: `update`, `saveBuilder`, `delete`, `createConversation`, `shareAgencyWithGroups`, `unshareAgencyGroup`, `restoreVersion`, `routeResult`. | Apply `createRateLimitMiddleware` to `update` (suggest: 30 req/min), `delete` (10/min), `createConversation` (20/min), `saveBuilder` (20/min), `restoreVersion` (10/min). The other read procedures (`list`, `getById`, `listVersions`, etc.) are lower priority. |
| MEDIUM | `agency_orchestrator.py:1295-1310` | `parallel_fan_out` with `merge_strategy = "first_complete"` cancels pending branch tasks via `task.cancel()` after the first result arrives. The `branch_ctx` objects for cancelled branches are appended to `branch_contexts` (line 1369+) and their `step_attempts` are copied back to the parent. But cancelled branches may have already submitted LLM calls that were charged credits — the cancel only prevents Python from awaiting the result, not from the LLM provider completing the request and billing the account. Since each branch uses `ctx.clone()` (with the same `user_token` and `tenant_id`), all N branch LLM calls fire immediately and billing occurs even for branches whose results are discarded. | Document this as a known "fire-and-forget billing" limitation in the `parallel_fan_out` docstring. Consider adding a pre-flight credit reservation across all branches before dispatch, returning surplus at merge time. At minimum, log the number of cancelled-but-billed branches in the step_attempts. |
| LOW | `agency_tools.py:657-666` | `resolve_shared_tools_for_agency` queries `agency_shared_tools` by `agencyId` only, with a LEFT JOIN to `agency_tools`. There is no tenant assertion in this query — the function trusts that the `agency_id` was already verified by the caller. This is correct today because `_shared_tools_cache` is populated in `_execute_agent_node` which runs in a context where `agency_id` is from `self.agency_config` (set by the trusted Node.js dispatcher). However, if `resolve_shared_tools_for_agency` is ever called from a new path that accepts an agency_id from user input, the missing tenant filter becomes a cross-tenant leak vector. | Add a `tenant_id: str` parameter to `resolve_shared_tools_for_agency` and add `AND agencies."tenantId" = :tenant_id` to the query via a JOIN on `agencies`. Makes the function safe regardless of call site. |
| LOW | `agency.ts:2437 (restoreVersion)` | After restore, the version snapshot is applied without updating `agencyVersions` to record the restore event. If a user restores to version 3, then later lists versions, they see versions 1–5 with no indication that version 3 was most recently active. There is no audit trail for restores, making incident investigation difficult. | Insert an `agencyVersions` row (or a separate `agencyRestoreLog`) after the transaction commits, recording `restoredFromVersionId`, `restoredByUserId`, and `restoredAt`. |
| LOW | `agency_orchestrator.py:447-459` | Inline parallel edge execution at the bottom of `_execute_node` (lines 445-459) does not use `ctx.clone()` — all parallel branches share the same `ExecutionContext` instance. Concurrent writes to `ctx.results[node_id]` from `asyncio.gather` are therefore not serialized. Two branches writing different `node_id` keys are safe, but if the same `node_id` appears in multiple branches (which shouldn't happen in a valid graph but is not validated), the last writer wins silently. This is a different code path from `_execute_parallel_fan_out`, which does clone correctly. | Use `ctx.clone()` for each branch in the inline parallel path, matching the fan-out pattern. Add a graph-validation assertion that no `node_id` appears in more than one parallel branch. |

### Summary

The orchestrator correctly propagates `tenant_id` through `ExecutionContext` to all major sub-calls (`AgencySwarmAdapter`, `retrieve_agent_knowledge`, cross-agency `execute_agency_call`). The most critical new findings are: (1) `getById` exposes encrypted MCP tokens in the API response because the `agencyAgents` SELECT uses a wildcard projection; (2) `submitApproval` has no tenant scope check on the conversation lookup, allowing cross-tenant approval injection using only a guessed UUID; (3) `restoreVersion` inserts snapshot `nodeConfig` data verbatim without re-running the `saveBuilder` Zod validation, creating a path to inject unsafe node configurations that bypassed the current schema guards. Secondary concerns are the unbounded `ctx.results` growth in long graphs, the `data_transform` `outputKey` collision with the approval namespace, and the 8+ write procedures that lack rate limiting.
