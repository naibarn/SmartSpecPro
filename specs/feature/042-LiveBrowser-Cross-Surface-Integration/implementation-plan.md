# Implementation Plan - Feature 042

Feature 042 should be implemented as a product-integration layer around the existing live-browser runtime, not as a new runtime. The plan is to promote `Browser Session` into a shared capability with one user-facing language contract, one navigation contract, one additive shared data contract, and explicit integration paths for Chat, Agency Swarm, and Virtual Workflow.

The first implementation stream is a shared UX, contract, and routing foundation. Introduce a browser-session presentation contract in the web client and shared types layer that converts internal runtime language into user-facing labels and statuses. This contract should own primary CTA names such as `Open Browser Session`, `Continue in Browser`, `Reopen Browser Session`, `Take Control`, `Return to AI`, `Needs Your Input`, and `Review Required`. In the same stream, define one additive shared data contract for `browserSessionSummary`, `browserSessionLaunchContext`, and `browserSessionReturnContext` so every surface is reading and writing the same browser-session metadata. Replace the current hardcoded close behavior in `AutomationPage.tsx` with origin-aware navigation using that launch and return metadata, so a Browser Session can be opened from Chat, Agency, Workflow, or direct deep links without losing parent context.

The second stream is Chat integration. The architectural choice for this phase is to reuse the existing full-page Browser Session route rather than creating a second right-panel browser implementation. Chat should gain a first-class Browser Session entrypoint in the shell and a resumable browser-session summary within the conversation thread. The thread should carry a human-readable summary object or artifact-like representation rather than free text or raw runtime fields. Opening a Browser Session from Chat must preserve conversation context, and returning from the session must place the user back into the same thread with the same relevant panel or thread selection restored. Chat should also surface browser-related waiting states in a lightweight, explicit way so the user can see when the AI is waiting for review or input without needing to discover the separate automation page first.

The third stream is Agency Swarm integration. The architectural choice for this phase is to add a dedicated `browser_session` primitive rather than overload `skill_call`. Agency Builder should expose browser collaboration as a first-class concept with user-facing configuration labels that describe what the agency is doing in product terms. Agency Chat should gain a structured sidecar or embedded state rail for browser-session state, including at minimum running, review required, needs user input, person in control, reconnecting, and ended. Agency approval UI should reuse the shared state labels and action labels so the browser collaboration flow is legible without exposing implementation jargon. Existing agencies that do not use browser-session primitives must remain valid without migration.

The fourth stream is Virtual Workflow semantics. The architectural choice for this phase is to preserve legacy `web_automation` for one-shot behavior and add an additive browser-session node family for collaborative flows. The preferred set is `browser_session_start`, `browser_session_instruction`, `browser_session_wait_for_user`, and `browser_session_review_gate`. The registry-driven workflow editor is already capable of rendering richer inputs, so the main change is to expand the backend node contract and make the web editor surface the new semantics. The output contract needs stable, meaningful fields such as `browser_session_id`, `session_status`, `review_state`, and `pending_user_step`, rather than one-shot-only extracted data. Compatibility must be explicit: saved workflows using `web_automation` continue to run unchanged, new nodes are additive, and load/save logic should normalize versions without forcing a bulk migration.

The additive workflow nodes should start with a narrow, explicit contract rather than an open-ended generic shape. `browser_session_start` should accept a goal, optional start URL, and launch context, then return `browserSessionId`, `sessionStatus`, and `browserSessionSummary`. `browser_session_instruction` should accept `browserSessionId` and `instructionText`, then return the updated summary. `browser_session_wait_for_user` should accept `browserSessionId`, `waitReason`, and `timeoutSeconds`, then expose `pendingUserStep` alongside session status. `browser_session_review_gate` should accept `browserSessionId`, `reviewReason`, and `reviewSummary`, then output `reviewState`. This keeps downstream workflow nodes predictable and reduces schema churn.

The fifth stream is shared state mapping, compatibility, and responsiveness. Browser-session state must be rendered consistently across Automation, Chat, Agency, and Workflow surfaces. A shared adapter layer should map raw runtime status fields into one consistent set of product states, with a stable copy contract for badges, banners, and action prompts. This adapter should also provide a compatibility layer so older live-browser fields and older workflow node outputs still behave correctly during rollout. Compact layouts remain observe-first: Browser Session may still be opened from Chat or Agency on mobile, but manual control remains unavailable there and the copy must explain that limitation clearly instead of silently hiding it.

The rollout should proceed in dependency order and behind per-surface feature flags. Start with the shared naming, contract, and navigation foundation, because every other surface depends on those semantics. Then wire Chat integration behind `chatBrowserSessionEntry`, because it exercises the main user-facing path with the least schema risk. Agency integration comes next behind `agencyBrowserSessionUi`, since it adds a new UI primitive but can still reuse the same runtime. Workflow changes should land after the shared browser-session contract is stable and stay behind `workflowBrowserSessionNodes`, because node semantics and backward compatibility are the highest-risk part of the feature. If a surface flag is off, that surface falls back to existing behavior while Feature 036 remains fully usable.

## Impact Map

Existing features likely to regress are the dedicated automation route, existing live-browser resume flows, chat conversation navigation, agency message rendering, workflow node serialization, and approval/takeover banners. These areas should be treated as high-signal regression zones throughout implementation.

## Regression Prevention Strategy

Use focused regression coverage instead of one large end-to-end bet. Keep the existing Feature 036 test suites intact. Add targeted tests for route return behavior, chat reopen flows, agency browser-state rendering, workflow node schema compatibility, shared status-to-copy mapping, and compact-layout observe-only behavior. Roll out in stages behind surface-specific capability checks or tenant feature flags rather than a single all-or-nothing launch. Ownership should remain explicit across web client, Node API contract, and Python orchestration changes so regressions do not hide in cross-service seams.

## Rollout Matrix

Use tenant-aware rollout flags so surfaces can be enabled independently:

- `chatBrowserSessionEntry`
  - Enables Browser Session entrypoints and summaries inside Chat
  - Fallback when off: Chat behaves exactly as it does today

- `agencyBrowserSessionUi`
  - Enables Agency builder primitive and Agency Chat browser-session rendering
  - Fallback when off: Agency continues to use existing graph and chat behavior

- `workflowBrowserSessionNodes`
  - Enables new additive browser-session workflow nodes and related execution rendering
  - Fallback when off: only legacy `web_automation` remains visible and executable

These flags should be added to the existing tenant feature flag contract in `apps/web/shared/featureFlags.ts`, validated and resolved through `apps/web/server/services/tenantFeatureFlagService.ts`, exposed via the existing tenant feature flag router, and rendered in `apps/web/client/src/components/admin/TenantFeatureFlagsPanel.tsx`. Shared language and origin-return fixes are foundational and should ship with the dedicated automation surface once validated, because they reduce fragmentation instead of creating a new optional feature branch.

The admin panel should use explicit, user-facing labels for the new flags so operators understand rollout intent:

- `Chat Browser Session` — Start and reopen Browser Session from Chat
- `Agency Browser Session` — Show Browser Session nodes and session state in Agency
- `Workflow Browser Session Nodes` — Enable collaborative Browser Session nodes in Workflow

## Observability And Analytics

The integration layer should emit enough telemetry to answer both operational and product questions. Client-side product analytics should follow the existing PostHog helper pattern used elsewhere in the frontend, with a dedicated Browser Session analytics module under `apps/web/client/src/lib/analytics/`. The initial event set should include `browser_session_opened`, `browser_session_reopened`, `browser_session_return_navigation_failed`, `browser_session_take_control_blocked`, and `browser_session_mobile_observe_only_seen`. These events should include origin surface, compact-layout state, and whether the session was newly created or resumed.

Operational signals on the web or runtime side should reuse existing metrics or structured-log patterns rather than creating a one-off telemetry path. The minimum signal set should include `browser_session_launch_total`, `browser_session_waiting_for_user_stale_total`, `browser_session_take_control_blocked_total`, `workflow_browser_session_legacy_fallback_total`, and `agency_browser_session_render_failure_total`. These signals should feed rollout confidence, incident triage, and compatibility validation. Ownership should be explicit: web owns chat and navigation telemetry, Python or orchestration owns workflow fallback and browser-session runtime signals, and Agency integration owns conversation-surface rendering failures.

Use low-cardinality labels only. The preferred baseline is `origin_surface` with values `automation`, `chat`, `agency`, and `workflow`, plus `reason_category` with values `policy`, `step_up`, `state`, `navigation`, `render`, `legacy_fallback`, and `unknown`. Avoid labels derived from session IDs, URLs, tenant names, or free text. Release-gate and alert thresholds should be defined around a few actionable conditions: return-navigation failures above baseline, stale `Needs Your Input` states beyond the chosen threshold, unexpected non-policy spikes in blocked control attempts, and workflow legacy fallback remaining elevated after rollout.

## Optional Infra Hardening

This feature can ship without environment-specific dashboards and alert routing, but the plan should leave ready-made defaults for follow-up ops work. The recommended starting threshold for return-navigation failures is greater than 2 percent over 15 minutes during canary and greater than 1 percent over 30 minutes during broader rollout. The recommended stale-wait starting threshold is a warning above 5 stale `Needs Your Input` sessions older than 10 minutes and a critical alert above 15 stale sessions older than 15 minutes. The recommended workflow legacy fallback starting threshold is a warning above 20 percent after rollout week 1 and a critical alert above 10 percent after the agreed stabilization window. For non-policy blocked control attempts, the starting thresholds are a warning above 5 events in 15 minutes and a critical alert above 20 events in 15 minutes.

The optional dashboard package should include at least six views: Browser Session opens and reopens by origin surface, exits with return-navigation success versus fallback, stale `Needs Your Input` sessions over time, blocked `Take Control` attempts by reason, workflow legacy fallback rate, and Agency browser-session render failures. If the team uses saved queries rather than dashboards, these should exist as reusable query templates instead.

Alert routing should follow ownership boundaries already implied by the rollout plan: web or frontend on-call for return-navigation issues, workflow or Python orchestration owner for legacy fallback and runtime session-state issues, and Agency owner for browser-session rendering failures in Agency surfaces. Each alert should point to a short runbook entry that describes verification steps, flag rollback options, and which fallback behavior to expect when a surface is disabled.

## Operator Copy And Admin Controls

The rollout plan should also standardize the operator-facing wording used in tenant feature flag controls so rollout intent is obvious in the admin UI. The preferred labels are `Chat Browser Session`, `Agency Browser Session`, and `Workflow Browser Session Nodes`. Their descriptions should explain user-visible outcomes, not implementation details. This is important because the feature will be rolled out surface by surface, and operators should be able to understand what each flag changes without reading engineering notes.

## Data Safety Strategy

Risk classification: `low`.

The preferred plan is migration-free for the first implementation wave. Browser-session summaries should be carried in existing JSON-friendly UI and API contracts rather than requiring new relational tables. Workflow and agency changes should be additive and backward-compatible, using optional fields and compatibility adapters. Saved workflow and agency documents should be normalized on load and saved with version-aware serializers where necessary, rather than forced through a destructive bulk migration. Because no destructive schema change is planned in this wave, a database backup or restore runbook is not required for the base scope. If implementation later proves a persistent relational browser-session artifact table or workflow migration is necessary, the migration strategy must remain non-destructive: expand first, backfill or adapt second, contract only after verification.

## Compatibility Notes

Feature 036 dedicated entrypoints must continue to work. Existing saved workflows that use one-shot `web_automation` must still execute without requiring manual edits. Existing agencies without browser-session nodes must remain valid. Internal live-browser protocol fields can stay unchanged at the transport layer, but new UI surfaces must render only the product-facing terminology contract. The compatibility strategy should prefer additive node types, load-time normalization, and version-aware serialization over one-off migration scripts unless implementation proves that adapters are insufficient. The same principle applies to tenant flags and analytics wiring: new flags and events must be additive and must not break existing tenant configuration or analytics initialization paths.

## Follow-Up Uplift - Advanced Automation And Human Handoff

The original 042 plan covers cross-surface Browser Session wiring, but it stops short of the advanced automation behaviors needed for research-heavy and semi-automated transactional tasks. The next planning wave should extend the feature without discarding the existing architecture: keep one Browser Session runtime, then add execution, rendering, invocation, and safety layers that make the runtime useful for real browse-and-compare work.

The first follow-up stream is Agency runtime execution. The `browser_session` agency node must become executable inside the Python orchestrator, not only valid in the builder. Add an explicit executor that can create a Browser Session, persist the active `browserSessionId` in run context, emit structured browser-session events back into Agency Chat, and honor configured handoff modes such as continue running, review required, needs user input, or take control. This stream closes the current gap where Agency Chat can manually open a Browser Session but a running agency cannot reach that state autonomously from its graph.

The second follow-up stream is the Browser Session renderer. The current workspace contract already carries viewer and controller stream tokens, so the plan should use those existing contracts to add a real remote viewport component rather than inventing a second browser abstraction. The renderer should support observe mode, interactive takeover mode, reconnect fallback, and token refresh handling. Compact layouts should remain observe-only in this phase. This stream is necessary before positioning Browser Session as the UI for login pages, checkout pages, or other high-friction websites because users need to see the actual page state, not just title and URL summaries.

The third follow-up stream is natural invocation from Chat and Agency. The initial entry buttons should remain, but the product also needs a structured launch path from conversational intent. The safest first step is assistant-proposed launch cards with explicit user confirmation before creation. This keeps launch deterministic, traceable, and policy-friendly while still letting users ask for browser work directly from Chat or Agency. The launch artifact should capture the triggering message, origin surface, and launch kind so future analytics, replay, and approvals can distinguish suggested launches from direct launches.

The fourth follow-up stream is research and booking comparison semantics. SmartSpecPro should normalize comparison-oriented outputs instead of leaving price, distance, availability, and booking evidence inside free text. Add a reusable comparison contract and UI summary model for browse-heavy tasks such as ticket comparison, hotel comparison, and shortlist generation. The plan should explicitly optimize for human-reviewed recommendations and evidence capture first. Auto-purchase or fully unattended booking stays out of scope for this wave because the higher-value near-term win is high-quality compare-and-decide support with strong handoff safety.

The fifth follow-up stream is barrier-aware human handoff. Today the system already supports `Needs Your Input`, `Review Required`, takeover, and step-up authentication, but the next plan should distinguish login, captcha, payment review, and booking confirmation barriers explicitly. These barrier types need durable contracts because downstream agency and workflow logic must branch on them, and the UI must explain why the AI paused. Captcha completion and irreversible submit actions should always move through a human-controlled or explicitly approved path rather than generic continuation.

The sixth follow-up stream is rollout and validation hardening for advanced automation. Add scenario-driven verification for agency-executed Browser Sessions, rendered browser streams, launch-card flows from Chat, explicit login or captcha barriers, and commitment gates before payment or booking confirmation. These should be treated as advanced rollout slices, potentially behind additional feature flags if needed, so teams can canary the risky behaviors independently from the already-shipped cross-surface foundation.
