# Claude Plan

This plan describes how to implement Feature 075 as the architectural umbrella for SmartAIHub's unified web + desktop agent platform.

The implementation should preserve the existing codebase's useful local-execution substrate while changing the product contract from "permissive shell with point features" to "governed Desktop Host integrated with the SmartAIHub control plane."

The plan assumes the provisional interview answers captured in `claude-interview.md`, especially:

- the old localhost `python-backend` path is compatibility-only during migration
- worker-fabric projection is opt-in
- `local-unverified` outputs remain local by default
- managed Pi integration starts sidecar-first unless later evidence strongly favors embedded mode

## Architecture Shape

The target architecture has three major layers:

1. `Web control plane`
   - owns auth, policy, device identity, package registry, signing, revocation, gateway routing, and shared run history
2. `Desktop Host`
   - owns local orchestration, local file intelligence, workspace management, runtime adapters, secrets, and audit emission
3. `Execution runtimes`
   - Pi for interactive local agent work
   - Agency Swarm for multi-agent local orchestration
   - existing external worker runtime family where desktop-local execution is not the correct path

The most important architectural rule is separation of concerns:

- the server remains the source of truth for identity, trust, revocation, shared objects, and policy
- the desktop remains the source of truth for local execution state, staged artifacts, local file indexes, and device-scoped runtime operations

## Section 01: Canonical Surface, Device, and Contract Foundation

This section establishes the shared vocabulary and schemas that every later section depends on.

The implementation should introduce a dedicated shared contract module for Desktop Host instead of overloading worker-runtime contracts with desktop-only concepts. That shared module should define:

- device registration payloads and policy snapshots
- desktop package trust and package state enums
- unified run labels for surface, runtime, trust, locality, and workspace
- policy freshness and compatibility metadata
- explicit compatibility flags for migration-only 004-era behavior

On the server side, the first database and service work should create a first-class device model. The team should add device records, enrollment metadata, policy snapshot versioning, and revocation state to the main schema and wrap them in focused services rather than spreading this logic across ad hoc routes.

The feature-flag layer should also be extended here. Feature 075 needs rollout gates for:

- desktop-host enablement
- desktop package sync
- advanced local mode
- desktop agency runtime
- desktop worker-fabric projection

This section also locks the reconciliation rule between Desktop Host and the worker family. The worker registry should keep `desktop_zeroclaw_managed` as the compatibility identity when Desktop Host participates in worker-fabric behavior, but internal product labels shown to users should remain `Pi` and `Agency Swarm`.

The implementation output for this section should include a short supersession artifact that maps which 004, 070, and 071-074 behaviors remain active, which are compatibility-only, and which are now overridden by Feature 075. That matrix is needed so later sections do not accidentally reintroduce deprecated assumptions.

The output of this section is the contract baseline the rest of the system can safely build on.

## Section 02: Package Trust, Sync, and Materialization

This section defines the trusted distribution pipeline for desktop-executable artifacts.

The implementation should add a package envelope around the current bundle world instead of replacing the current bundle structure. Existing skill manifests, reviewed script-bundle metadata, and compatibility signals should remain the inner payload. The new outer envelope should add:

- package identity and versioning
- package type
- signer identity
- trust class
- payload digest
- capability manifest digest
- compatibility range
- revocation metadata

The server should expose a package registry, signed metadata download path, and revocation feed. The desktop should implement a package sync cache plus a local materializer that converts server-published packages into runtime-specific local artifacts. Those artifacts should be explicit about:

- runtime destination
- resolved capability manifest
- local bundle path
- signer and trust metadata
- revocation freshness deadline

This section must also settle trust propagation for outputs. Outputs generated by `local-unverified` or `project-local` packages should carry provenance metadata and remain trust-tainted until promoted through an explicit review workflow. Shared org surfaces should not be allowed to silently accept those outputs as if they were generated by verified packages.

The team should treat quarantine and revocation as first-class lifecycle states. A package that fails signature validation, compatibility checks, or freshness requirements should fail closed before materialization or execution.

## Section 03: Local File Intelligence and Workspace Manager

This section transforms the current raw local primitives into a governed substrate for desktop-local execution.

The local file side should move from absolute-path access to a root-governed model. The desktop needs services for:

- managed root registration
- root policy evaluation
- metadata indexing
- full-text indexing
- preview and snippet extraction
- optional vector indexing where policy allows it
- staged attachment into workspaces and runs

This work should not simply bolt more logic onto `file_commands.rs`. That file can remain a low-level helper layer, but managed flows should route through dedicated local-file services that resolve user actions against approved roots, user consent, and org policy.

The workspace side should wrap today's Docker primitives in a workspace manager. The workspace manager should own:

- profile selection
- mount allowlists
- egress classes
- resource limits
- temporary output directories
- connector sidecar access rules
- writeback policy for generated artifacts

This section must also introduce parser isolation and sensitive-root safety. Preview extraction and indexing for PDFs, Office files, images, and archives should run in contained workers or containers where practical. The UX should make root registration visible and revocable by the user so that the trust model stays understandable.

The file-intelligence subsystem should also define lifecycle rules for derived data. Preview cache, snippet cache, metadata stores, full-text index files, and optional vector indexes should have explicit retention, purge-on-root-removal, and purge-on-offboarding behavior. Where the operating system supports it, these stores should live in OS-protected or encrypted-at-rest locations rather than plain unmanaged cache directories.

Writeback should be modeled explicitly rather than as a side effect of file access. The workspace and local-file layers should support separate modes for:

- read/search only
- write into managed output folders
- user-confirmed writeback into approved roots
- advanced local mode overrides

## Section 04: Execution Router and Pi Runtime Host

This section introduces the control logic that decides how a run is executed and provides the first major governed local-agent runtime.

The run router should be implemented as a deterministic, inspectable decision layer that takes into account:

- task metadata
- package trust class
- file-scope requirements
- workspace requirements
- connector requirements
- runtime availability
- policy restrictions
- degraded or offline state
- explicit user or admin routing constraints

The output of the router should include both the selected runtime and the rationale used for that choice. The rationale must be stored in a machine-readable form so UI, audit, and support tooling do not invent different explanations later.

Pi integration should be introduced as a Desktop Host adapter, not as an uncontrolled runtime dropped directly into the app. Because the current planning assumptions favor isolation, the first managed implementation should prefer a sidecar or RPC-style boundary. The adapter should be responsible for injecting:

- gateway-only provider configuration
- runtime-scoped credentials
- Desktop Host tool adapters for governed file search, staged attachments, connector actions, and server APIs
- workspace and package materialization context

Desktop-to-platform transport should follow the same truthful production posture already established in the worker family: HTTP-first, MCP-second. MCP remains a supported capability path, but Desktop Host should not depend on MCP as the only production contract for core platform access.

The plan should treat sidecar-first as a decision, not as an unresolved preference. Embedded Pi integration can be revisited later, but only after the team can prove equivalent crash isolation, policy enforcement, secret scoping, and operability across supported desktop platforms.

This section must explicitly inherit Feature 070's truthfulness rules. A run should only be labeled `Local` when the actual data path and execution path justify that claim. If desktop-mediated execution still relies on server-side persistence or control-plane processing in a meaningful way, the correct label is `Hybrid`.

## Section 05: Agency Swarm and Connector Runtime

This section adds the complex orchestration layer and the managed connector runtime.

Agency Swarm should be treated as a separately managed local runtime whose packaging and persistence are owned by Desktop Host. The desktop should materialize server-authored agencies into local runtime bundles that include:

- topology and communication flow definitions
- prompt and instruction assets
- capability manifest and policy descriptor
- runtime config for gateway routing
- adapter configuration for Desktop Host-managed file, connector, and server access

Because current Agency Swarm guidance assumes application-owned conversation persistence, Desktop Host must own thread storage and recovery instead of relying on hidden server-managed thread identifiers.

The default managed packaging posture should prefer a Docker-contained Agency Swarm runtime unless platform-specific evidence later justifies a different default. That keeps the runtime aligned with the broader managed workspace strategy and avoids granting it unconstrained host execution by accident.

Agency Swarm must follow the same managed gateway posture as Pi. In managed mode the Desktop Host should inject gateway-only model configuration, reject unmanaged provider keys, and fail closed if the runtime cannot be started under those constraints.

The connector runtime should expose narrow, host-managed actions rather than arbitrary SDK freedom in managed mode. The implementation should treat connectors as governed capabilities with:

- device-scoped secret storage
- connector-specific approval rules
- outbound audit
- per-connector policy toggles
- scoped runtime injection

This section also owns hybrid orchestration handoff. The router and runtime contracts should allow Pi to do discovery, file preparation, or user-facing back-and-forth, then hand the prepared context to Agency Swarm when the work becomes orchestration-heavy.

## Section 06: Unified UX, Cross-Surface Handoff, and Run Labels

This section turns the architectural work into a coherent user experience.

The web and desktop surfaces should reuse shared label helpers, trust badges, package detail components, and run-detail semantics wherever possible. The team should avoid separate ad hoc desktop-only wording for concepts that already exist in the web control plane.

The first-run desktop experience should become a guided bootstrap flow covering:

- sign-in
- device registration
- policy validation
- runtime dependency checks
- local-root selection
- package sync
- health verification

The cross-surface handoff model should support:

- `Open in Desktop`
- `View on Web`
- project continuity across surfaces
- consistent run and package URLs or resolvers

This section must also make provenance understandable at a glance. Users should be able to tell, without reading raw logs, whether a run was local, hybrid, external, or server-side and what trust class applied to the package or artifact involved.

## Section 07: Security, Governance, Audit, and Offboarding

This section provides the enforcement model that makes the rest of the plan enterprise-safe.

Capability manifests should be enforced at multiple checkpoints:

- install and sync
- materialization
- run start
- tool invocation
- connector invocation
- secret issue
- file access
- outbound action

The device lifecycle should be completed here. Enrollment bootstrap, refresh tokens, runtime-scoped execution tokens, re-auth triggers, and offboarding cleanup all need explicit ownership. The desktop should cache policy and revocation state with freshness limits, but the server remains authoritative for disable and quarantine decisions.

The credential model should be proof-of-possession capable rather than bearer-only. The device should hold key material registered during enrollment, and refresh or runtime token minting should require a challenge/response bound to that device identity. This section should also define re-key flows, bootstrap invalidation after first bind, and cloned-device suspicion handling.

The audit model should prioritize structured metadata and redacted references rather than raw file contents or secrets. Audit coverage should include:

- device enrollment and disable events
- package sync and revocation outcomes
- managed root registration
- runtime selection
- high-risk approval decisions
- outbound allow/deny decisions
- connector usage

This section also owns the signed update trust chain. Desktop app updates and bundled runtime support payloads should verify against trusted metadata and fail closed on signature mismatch or unauthorized downgrade. Emergency rollback should be possible only through an explicit policy-authorized path, not through silent client-side downgrade behavior.

Update security should include trusted signer-set management, signed key rotation, and an emergency compromised-key response path. The update metadata should be sequenced strongly enough that replayed or stale manifests cannot silently roll a device backward.

Finally, this section should define the approval and step-up matrix for destructive writes, non-default workspace mounts, connector outbound actions, shell escalation, and unverified package execution. The approval matrix should be machine-readable so both UI and audit surfaces rely on one source of truth.

DLP-aware outbound checks should cover more than generic HTTP calls. The enforcement model should explicitly evaluate:

- connector outbound messages
- model prompt bodies that include sensitive local snippets
- shared-surface publication of trust-tainted outputs
- export or upload flows originating from managed workspaces

## Section 08: Rollout, Migration, and Regression Matrix

This section governs how the platform evolves from the current state without breaking existing users or making misleading claims.

The rollout should be phased and feature-flagged. The safest sequence is:

1. device identity and policy contracts
2. package trust, signing, and materialization
3. local-file governance and managed workspace profiles
4. Pi runtime host and run router
5. Agency Swarm runtime and connector runtime
6. UX unification, hardening, signed updater chain, and offboarding polish

Each phase should also have an explicit exit gate. Foundation is not complete until one-time bootstrap plus proof-of-possession-capable device binding exist. Local substrate is not complete until raw path discovery is no longer the default managed UX and derived file caches purge correctly. Runtime unification is not complete until both Pi and Agency Swarm enforce gateway-only startup. Enterprise hardening is not complete until signer rotation, offboarding cleanup, and main-channel DLP controls are live.

The migration plan should preserve existing useful local capabilities behind explicit advanced or compatibility pathways while the governed replacements are being built. The team should avoid a single big-bang switch from the current Tauri shell posture to fully managed Desktop Host behavior.

Regression work in this section should focus on truthfulness and safe coexistence:

- 004-era localhost flows must be labeled as compatibility-only where they still exist
- worker-fabric features from 071-074 must remain operational
- current local execution and local AI behavior must not regress accidentally
- docs and UI labels must not imply governance or locality guarantees that are not yet implemented

This section should also codify degraded-mode expectations. Desktop may continue local browsing, indexing, history viewing, and package inspection when the gateway or control plane is unavailable, but managed LLM execution and trust-sensitive execution should stop once policy or revocation freshness windows expire. There should be no silent direct-provider fallback in those states.

## Delivery Sequence and Ownership

The implementation should proceed as four delivery waves:

1. `Foundation and trust`
   - Section 01 and Section 02
2. `Managed local substrate`
   - Section 03 plus the approval model from Section 07
3. `Runtime unification`
   - Section 04 and Section 05
4. `Product coherence and hardening`
   - Section 06, the rest of Section 07, and Section 08

This sequencing keeps governance ahead of raw runtime enablement, which is important because the current repo already has powerful local primitives that are easier to expose than to secure retroactively.

## Testing and Verification Strategy

The implementation should follow the repo's current mixed testing model rather than imposing a single framework:

- Vitest for web/shared contract logic, label rendering, routing decisions, policy snapshots, and server services
- Cargo tests for Tauri-side policy enforcement, package sync/materialization, local-file services, workspace management, and runtime adapters
- Pytest only for migration-critical `python-backend` compatibility flows that remain live during the transition

Each section should add contract and denial-path coverage before happy-path integrations. The most important regression tests are the ones that prove the system fails closed when signatures, policy freshness, capability scopes, or locality labeling would otherwise drift.

## Major Risks to Manage During Implementation

The highest-risk failure modes are:

- preserving the old permissive Tauri shell behavior under a new governed brand without enough real enforcement
- creating a second runtime taxonomy that conflicts with the existing worker registry
- building runtime integration before device and package trust are settled
- letting local-unverified outputs contaminate shared org surfaces
- over-claiming `Local` when the true behavior is `Hybrid`
- adding desktop-local power without a signed update trust chain and offboarding model

Implementation decisions should be judged against one question: does the change make the unified product more truthful, more governed, and easier to reason about across web and desktop at the same time?
