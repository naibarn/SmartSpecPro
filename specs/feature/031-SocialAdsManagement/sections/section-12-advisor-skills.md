## Goal

After this section, a user clicks "วิเคราะห์เพจนี้" (Pages tab) or "วิเคราะห์โฆษณา" (Advisor tab / Overview) and gets a structured Thai report — summary, health assessment, strengths, issues, prioritized recommendations with fact citations — generated by an LLM whose ENTIRE intelligence lives in lowercase `skill.md` files. TypeScript builds facts only. Reports are persisted with their facts snapshot, credits are charged post-hoc by actual token usage, weekly scheduled reports run through the jobs worker, and any `suggestedAction` can only be applied through the Section 08 guarded mutation path by explicit user click.

## Background context (read once before coding)

**Skill-first policy (MANDATORY, spec §18.1 + project memory):**
- Facts builders emit raw computed metrics ONLY — no thresholds, no scoring, no "good/bad" labels, no advice strings in TS. Every judgment lives in `skill.md` and is applied by the LLM. Changing advice logic = editing `skill.md` (auto-synced by `skillRegistry.ts`, 60s cache) — no code deploy.
- ⚠️ The skill loader reads **lowercase `skill.md`** before `SKILL.md`. Author the lowercase file ONLY — a past bug shipped dead advice in an uppercase twin. A regression test pins this.
- Facts JSON sent to the LLM contains metrics + page/campaign names only — never tokens, secrets, or other PII (CLAUDE.md AI/LLM secret rules).

**Execution path (spec pipeline decision):** `executeSkill` CANNOT run llm-only skills. The advisor service loads skill content via the registry and calls `invokeLLM` directly, then `deductCreditsForModel` after. Model comes from `resolveEnabledLlmModelId` — respect user/model-selection policy, never auto-escalate.

**Verified codebase facts for this section (checked 2026-07-17):**

### 3. `socialAdvisorService.ts`

```ts
/**
 * Runs one advisor report end-to-end. NEVER calls provider mutations.
 * Pipeline: resolve model → build facts → load skill → invokeLLM → lenient parse
 * (≤2 LLM retries) → persist socialAdvisorReports row → deductCreditsForModel
 * (post-hoc, actual usage) → audit event.
 */
export async function runReport(params: {
  userId: number; tenantId: string;
  subjectType: "page" | "ad_account" | "campaign";
  subjectId: string;
  goal?: AdvisorGoal;           // grow_followers | increase_reach | increase_engagement | increase_video_views | general_health
}): Promise<{ reportId: number; report: AdvisorReport | null; parseFailed: boolean; creditsCharged: number }>;

/** Display-only estimate: facts-JSON length → token approximation × model input
 *  rate + typical output allowance. Never used for the actual charge. */
export async function estimateReportCost(params): Promise<{ credits: number; model: string }>;
```

Pipeline details (order matters — tests pin it):
1. `resolveEnabledLlmModelId()` — null → actionable Thai error, stop before spending any Graph/DB effort.
2. Facts: `subjectType === "page"` → `pageFactsBuilder` (Section 11); else `adsFactsBuilder`. Skill slug: `page → "social-page-advisor"`, else `"social-ads-advisor"`.
3. `getSkillByIdAsync(slug)` → system prompt = `skill.systemPrompt ?? skill.skillContent`; missing/disabled skill → fail closed with actionable error. (Skills auto-sync from the folder; no manual seeding.)
4. `invokeLLM({model, messages: [{role: "system", content: skillPrompt}, {role: "user", content: JSON.stringify({facts, goal, reportSchemaVersion: 1})}], outputSchema: {name: "social_advisor_report", schema: advisorReportJsonSchema}})`. Read actual token usage from the invoke result (verify exact `InvokeResult` usage field names in `_core/llm.ts` at implementation time).
5. `parseAdvisorReport` — on failure re-invoke up to 2 times (append a short corrective instruction); final failure → persist with `report: {raw, parseFailed: true}`.
6. Insert `socialAdvisorReports` row (factsSnapshot = exact facts object, skillName, modelUsed) → now the id exists → `traceId = "social-ads-advisor:" + reportId` (update the row).
7. `deductCreditsForModel({userId, model, inputTokens, outputTokens, tenantId, skillSlug: slug, sourceType: "social_ads_advisor", idempotencyKey: "social-ads-advisor:" + reportId, metadata: {subjectType, subjectId}})` — sum usage across parse retries; store `creditsCharged` on the row.
8. Audit: `social_ads_advisor_report` event (payload through `sanitizeForActionLog`; facts snapshot summary only, truncated).

**Credit source type edit (`creditService.ts`):** append `"social_ads_advisor"` to the `CreditSourceType` union (`:17-27`) and add a `case "social_ads_advisor": return "skill";` to `normalizeCreditSourceType` (`:34-46`). Do NOT touch `creditSourceTypeEnum` in `drizzle/schema.ts` — no migration in this section.

### 6. Skill folders (the intelligence — Thai-first, authored per spec §18.2/§18.3)

Both folders: lowercase `skill.md` ONLY, `schemas/input.schema.json`, `schemas/ui.schema.json`. Frontmatter (both): `category: chat_assistant`, `auto_trigger: false`, `enabled_by_default: true`, `version: "1.0.0"`, sensible `icon`/`tags`/`priority`.

**`social-page-advisor/skill.md`** body (author in Thai; structure, not prose stubs):
- How to read the facts: growth rates in context of page size + cadence; humility on small samples; compare the page against its own history, never absolute industry numbers.
- Analysis dimensions: follower dynamics (adds vs removes — churn vs stagnation), reach efficiency (reach per post vs follower base), engagement quality (reactions vs comments vs shares weighting), content-mix performance, posting cadence & timing (grounded in the per-slot histogram), video/Reels opportunity, cross-promotion & ads linkage.
- Recommendation rules: every recommendation MUST cite the specific fact(s); priority สูง/กลาง/ต่ำ = impact × effort; concrete how-to steps with a measurable `recheckMetric`.
- **Output Format section** = the §18.4 JSON schema verbatim (skills follow Output Format exactly; `suggestedAction` always `{type: "none"}` for page reports).

**`social-ads-advisor/skill.md`** body additionally:
- Diagnosis dimensions: spend efficiency per objective; creative-fatigue signals (frequency trend + CTR decay — judgment, no hardcoded cutoffs); audience saturation; budget concentration risk; objective-fit sanity; learning-phase awareness; issues triage (which DISAPPROVED/WITH_ISSUES to fix first, and how).
- Recommendations: budget reallocation bounded by the user's guardrails (state the bound explicitly), targeting/placement experiments, creative refresh grounded in top/bottom performers, restart-vs-iterate guidance, next A/B design.
- **Provisional-data humility:** metrics flagged `provisional: true` in the facts must be treated as provisional in the advice.
- `suggestedAction` MAY be emitted per recommendation, restricted to `pause | budget_adjust | none` with `targetId` + minimal `params`; instruct the model that these are suggestions rendered as buttons — never executed by the skill.
