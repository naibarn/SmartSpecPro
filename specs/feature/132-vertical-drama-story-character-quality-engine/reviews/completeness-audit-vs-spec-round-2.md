# Feature 132 Deep-Plan — Completeness Audit vs. spec.md (Round 2)

Date: 2026-07-09
Method: 9 independent read-only audit agents (Sonnet 5, no memory of the deep-plan session), each comparing ONE spec section range against its corresponding plan section file, plus 1 cross-cutting agent checking spec §1-3/§11-18 (gap table, acceptance criteria, flags, persistence, skills, rollout) against the plan overview. All 9 section-specific audits plus the cross-cutting pass are summarized below; full agent outputs are in the session transcript, not reproduced here.

## Summary verdict

The deep-plan (spec.md v0.2 + 9 section files, already once internally reviewed in `self-review-round-1.md`) was substantially complete but **not spec-complete**: every audit found real, fixable gaps against the actual spec text, ranging from a genuinely dangerous bug (a miscounted required-field check that would have blocked every non-anchor shot in production) to a significant schema omission that broke the plan's own stated §10.7 requirement. **All findings below marked FIXED were resolved directly in the plan/spec files by the conductor as part of this audit round** — no further action needed before implementation starts. A handful of items are marked NEEDS PRODUCT DECISION and are intentionally left open.

## Fixed (applied directly to plan/spec files)

### Real bugs
- **Section 04**: `validateStagePayload`'s contract-presence check said "7 required fields" — the schema has 6 required + 3 optional. Left as written, an implementer would likely require the optional `anchorLine` field and reject ~2/3 of all shots (every shot without an anchor line). **Fixed**: corrected to 6, with the three optional fields named explicitly.
- **Section 07**: `spliceStoryboardShots` hardcoded "exactly 9 shots" as its integrity invariant. Nothing in spec 132 or 131 fixes shot count at 9 (it's an illustrative example; 131 §7.7's density reform allows variance). **Fixed**: invariant changed to "shot count and shot-number set unchanged from input," tests now exercise both 9-shot and non-9-shot fixtures.
- **Section 08**: `visualBibleSchema` listed only the *new* §10.2 fields and silently dropped the *existing* skill-output fields (`signature_wardrobe`, `identity_anchors`, etc.) that §10.2's own opening sentence requires persisting. This meant Section 08's own §10.7 requirement ("carry wardrobe base") had no field to read from. **Fixed**: schema now includes all 6 base fields; §10.7 binding corrected to read `visualBible.signatureWardrobe`.
- **Section 04**: `contract.newClueIds` was capped by both a zod `.max(2)` (hard schema rejection → failed chunk retry) AND a deterministic gate (repairable finding) — an unresolved double-enforcement the plan's own open questions flagged but never closed. **Fixed**: schema cap removed; the deterministic gate is now the sole enforcement point, documented as such.

### Cross-section contract mismatches
- **Section 03 ↔ Section 07**: Section 03's dependency notes claimed Section 07 "reads `affectedLedgers[]` off findings this section's checks produce," but Section 03's actual finding shape (`{kind, evidenceEpisodes, detail}`) has no such field. **Fixed**: clarified that `affectedLedgers[]` is derived by Section 07's normalizer from a fixed kind-to-ledger mapping (now pinned in Section 03's `VD_QUALITY_LEDGER_KINDS`), not carried on the finding itself.
- **Section 07**: `episode_outline` scope was routed through `applySeasonCritique` (the season-critique/cross-episode mechanism), contradicting spec §9.2's table, which groups `episode_beat` AND `episode_outline` under "existing stage-level repair (`plan_episode_script`) — unchanged." Only `cross_episode` should use `applySeasonCritique`. **Fixed**: routing corrected to split on `evidenceEpisodes.length` (1 → `episode_outline` via `plan_episode_script` stage repair; >1 → `cross_episode` via `applySeasonCritique`).
- **Section 09**: the one-anchored-character branch of the cast-contrast identity-lock logic set `requiresUserApproval: false`, contradicting spec §10.8's literal "requiring user approval **when an anchor already exists**." **Fixed**: corrected to `true` — approval is now required whenever any anchor exists in the compared pair, not only when both do.

### Missing/under-specified sub-checks
- **Section 04**: the premium deterministic gate never checked the spec-required "episode's shots collectively cover want/obstacle/choice/cost" — it was deferred to Section 06 with no concrete owner. **Fixed**: added as a fourth check in `meetsPremiumDraftContractFloor`; Section 06's Structure Pass now explicitly reuses the same function rather than re-deriving it.
- **Section 06**: `emotional_residue_reset` and "world-rule consistency" (both named in spec §8.1/§8.2 for the Continuity Pass) had no producing check function. **Fixed**: added `checkEmotionalResidueReset` and `checkWorldRuleConsistency` (the latter reusing Section 03's world-rule-ledger check, mapped to the existing `world_rules_undefined` kind).
- **Section 06**: per-deterministic-kind severity assignment was left as an open question ("finalize alongside Section 09"), but severity is load-bearing for Section 07's scope-escalation rule from day one. **Fixed**: a concrete default-severity table for all 16 finding kinds is now in Section 06 (structural: `episode_replaceable`, `hook_not_answered_in_opening`; major: 6 kinds; moderate: 7 kinds), with LLM override permitted but never unassigned.
- **Section 03**: two story-state write paths the spec names (§5.3's "written by `summarizeEpisodeToMemory` AND the deep-draft continuity sweep") and one projection (§5.1's `vertical_drama_memory_snapshots.memory.storyState`) were entirely absent from the plan — only the `summarizeEpisodeToMemory` half existed. **Fixed**: both the continuity-sweep writer and the snapshot projection are now explicit implementation steps. Also fixed: the `bible.ledgers` mirror had a read helper but no described write point (now added), and the story-state schema test said "9 fields" when spec §5.3 defines 11 (now enumerated in full).
- **Section 09**: the consistency ledger's anchor identity fields (`approvedAgeRange`, `wardrobeBase`, `colorPalette`, etc.) were declared in the schema but nothing populated them on approval — only `anchorAssetId` would ever get a real value. **Fixed**: added the explicit visualBible→anchor-field projection mapping at the `transition`-to-`approved` call site (this also resolved the separately-flagged "no data source for `hairIdentityNotes`" gap, once Section 08's fix added `hairMakeupNotes` as a base bible field).
- **Section 09**: the final hand-off step (flipping Section 06's `cast_visually_similar` stub live) never specified how the `cast` array or `hasApprovedAnchor` would actually be assembled at the call site, and didn't declare Section 06 as a hard build-order predecessor for that one step. **Fixed**: both gaps closed with explicit assembly logic and an added predecessor declaration.
- **Section 05**: the central ownership question — "this section owns the §7.1 rule text" vs. Section 01 owning the file the text would have to live in — was never resolved, leaving several §7.1 sub-rules (the ritual/dreamlike exemption, pressure-not-summary, minimal-context-per-clue, register facets, and the "deep-draft prompts" rendering target) effectively homeless. **Fixed**: Section 01 is now the confirmed sole author of the rule-text fragment (it already claimed this file in its own plan); Section 05 supplies the complete content checklist Section 01's fragment must cover, and the deep-draft-prompt rendering target is assigned to Section 02 (which already touches those exact prompt builders for premise threading).

### Systemic — criteria-module adoption (spec §11 / §16.5 / gap G24)
The prior internal review (`self-review-round-1.md`, Finding 8) believed it had closed the "unified criteria across every generate/update path" requirement by adding wiring steps to 4 sections. **This round's cross-cutting audit found that only 7 of spec §11's ~12 named consumer entry points actually had an owner** — the core story-*generation* paths (`generateStoryBible`, `generateStoryBibleDeep`, `extendStoryDraftHorizon`), episode continuation (`generateNextEpisodesViaLlm`), and manual draft edits (`updateEpisodeDraft`/`updateEpisodeDraftDialogue`) were silently unassigned, meaning §16.5's "agreement test fails if any consumer drops the criteria fragment" and gap G24 were not actually achievable as planned. **Fixed**: all 5 orphaned consumers now have owners — 3 to Section 02 (it already edits those exact prompt builders for premise threading), 1 to Section 05 (it already edits the exact manual-edit validation call site), 1 to Section 06 (episode continuation, the closest thematic fit among remaining sections). All 12 consumers now have a concrete embed-the-marker-and-flip-the-`.todo` step.

### Spec-level clarifications (spec.md bumped to v0.3)
- **§13**: documented the deliberate two-location storage split for revision plans (episode-scoped → run artifact; cross-episode → breakdown-version jsonb), which Section 07 had inferred but the spec prose implied a single location.
- **§14.2**: added `vertical-drama-character-image-qc` as a second new skill — Section 09 introduced this skill during deep-plan to keep image-QC iteration isolated from the bible-generation skill's tested contract, but spec §14 only ever listed one new skill. Now both are documented.
- **§16.1**: clarified that the `premise_drifted` finding requires BOTH F132A (produces only a synthesis-time coverage warning) and F132D (registers/detects the actual finding kind) — an earlier reading could fail a tester who enabled F132A alone expecting to see the finding fire.

## Needs product decision (intentionally left open, not silently resolved)

1. **Section 02** — the premise textarea is always rendered/sent regardless of the F132A flag (server decides whether to honor it), which diverges from spec §12's literal "F132A gates the premise field." This mirrors an existing precedent (`verticalDramaSeriesPresetMixV2`) but is a real behavioral choice: should the field itself be hidden client-side when the flag is off?
2. **Section 09** — whether villains (in addition to lead tiers) should be gated on the `audience_appeal` QC dimension. Spec §10.6 says "adult lead tiers" only; §10.2's field-population list is broader ("lead/villain tiers"). Section 09 currently assumes the broader reading; flagging for confirmation since it changes gate behavior for an entire character tier.
3. **Section 08** — three low-risk implementation-time judgment calls the plan already surfaces as open questions and this audit did not find reason to override: best-sheet role-priority placement (`expression_set` ranked after both turnaround and full — is "after turnaround" in spec meant to rank it ahead of full instead?), the assumption that "age" has no distinct prompt block and folds into `description`, and the exact algorithm for matching `contract.emotionalBeat` to the nearest `emotionalRangeNeeded` label.
