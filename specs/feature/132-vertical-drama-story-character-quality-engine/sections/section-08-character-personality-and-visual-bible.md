# Section 08: Character Personality & Persisted Visual Bible (F132F personality + F132G bible/expression)

## Goal
Give every vertical-drama character a structured, typed `personality` block and a **persisted** Character Visual Bible instead of a per-call, discarded LLM output — so (a) `extractCharacterDescription` and every image-prompt builder read stable, versioned identity data rather than re-deriving it every render, (b) `buildUserPrompt`'s block order matches the spec's priority (identity → age → face/hair/body/wardrobe → personality/emotional identity → signature cues → story-world connection → cinematic rendering → guardrails) without touching guardrail behavior, (c) a structured Expression Set (default 8 emotions) becomes a first-class asset role the best-sheet picker understands, and (d) the new `vertical-drama-ledger-planner` skill gets its personality/speech-profile-proposal output portion designed (the ledger portion is Section 03's). All additions are additive JSONB on `vertical_drama_characters.data` — zero migrations — and legacy ad-hoc keys (`data.description`, `data.personality` as a bare string, etc.) must keep rendering identically when the new typed fields are absent.

## Schema / migration notes
- No new tables, no `pnpm db:push` required — all additions are optional keys inside the existing `vertical_drama_characters.data` JSONB column (confirmed `data: jsonb("data")`, `drizzle/schema.ts:20437`).
- New asset role `"expression_set"` is a plain string value in `vertical_drama_character_assets.role`, confirmed `varchar("role", { length: 40 })` (`drizzle/schema.ts:20497`) with **no** DB-level enum/check constraint — free string, so no migration needed; only application-level constants (`CHARACTER_SHEET_ROLES` and the new comparator ranking in `verticalDramaCharacterStock.ts`) need updating.
- `visualBibleSchema` fields — **post-completeness-audit correction: the field list below now includes the BASE skill-output fields, which an earlier draft omitted entirely.** Spec §10.2's opening sentence requires persisting the skill's existing output (`visual_identity_summary`, `identity_anchors`, `signature_wardrobe`, `hair_makeup_notes`, `performance_energy`, `consistency_strategy`, plus the generated prompt strings) — NOT only the new additions. Omitting the base fields meant §10.7's "wardrobe base" binding had no source field to read from (a real, ready-to-ship bug caught by the audit). Full corrected field list:
  - Base (persisted from the existing skill output, camelCased): `visualIdentitySummary: string`, `identityAnchors: string[]`, `signatureWardrobe: string` (this IS the "wardrobe base" §10.7 binds — §10.7's implementation must read `visualBible.signatureWardrobe`, not an undefined `wardrobeBase` field), `hairMakeupNotes: string`, `performanceEnergy: string`, `consistencyStrategy: string`.
  - New additions per §10.2: `signatureVisualCues: string[]`, `colorPalette: string`, `storyWorldRelationship: string`, `forbiddenDrift: string[]`, `emotionalRangeNeeded: string[]` (default 8 applied at read time, not stored as a DB default), `ageRange: string`, and conditionally (adult lead/villain tiers only) `eraStyling: string`, `audienceAppealNotes: string`.
  - Wrapper metadata: `version: number`, `createdAt: string (ISO)`, `model: string`.
  - **Clarification (post-audit — resolves an internal ambiguity)**: `persistCharacterVisualBible` runs, and increments `version`, ONLY on a call that actually invokes the skill (fresh generation or explicit `regenerateVisualBible: true`) — a reuse-path call (stored bible present, `regenerateVisualBible` not set) never calls this helper at all, so "persist on every run" (Files to change, `generateCharacterVisualPrompts` bullet) means every run that produces a fresh `raw` skill response, not literally every function call.
- `personality` schema: `keywords: string[]`, `emotionalBaseline: string`, `want: string`, `fear: string`, `contradiction: string` — all required within the object once the object itself is present, but the object itself is optional at the parent level (legacy rows omit it entirely).

## Risk & rollback
- **Highest risk**: accidentally letting the new `eraStyling`/`audienceAppealNotes` additions leak into the `child` tier's directive or negative-terms path, or reordering `buildUserPrompt` in a way that changes guardrail TEXT (not just position). Mitigation: test #3 is a hard gate — it must pass with the exact existing child-directive string (line-for-line) and must assert zero era/audience-appeal text appears anywhere in a child-tier prompt, even adversarially (e.g. a corrupted stored bible on a child character carrying stray `eraStyling` data from a bug elsewhere — the prompt builder must ignore `visualBible.eraStyling` for the `child` tier regardless of what's stored).
- **Second risk**: character-lock instruction (`VD_CHARACTER_LOCK_INSTRUCTION`) accidentally duplicated or dropped during the block reorder. Mitigation: snapshot test #2 asserts the guardrail block set (solo-portrait + negatives + character-lock + region + preset-identity) is present exactly once, in its existing relative order, regardless of what's inserted before it.
- **Regression tests to run before merging**: full `resolveCharacterRoleTier`/`ROLE_TIER_DIRECTIVES`/`ROLE_TIER_NEGATIVE_TERMS` existing suite in `__tests__/verticalDramaCharacterImageGeneration.test.ts` (must pass unmodified — these are frozen contracts, not being changed by this section); `characterLock.ts` soften-ladder tests (untouched by this section, but verify no accidental import cycle); `extractCharacterDescription` existing tests (must pass with zero changes to legacy-path assertions).
