# Section 04: Scene Contracts (F132C)

## Goal

Add a per-shot `contract` object to the deep-draft shot schema so every shot in a deep-drafted episode carries an explicit story function, emotional beat, tension source, clue budget, and (optionally) an anchor-line marker and character decision. Thread this `contract` through generation (standard + premium deep drafts), the per-episode pipeline (`plan_episode_script`, `storyboard_shotgrid`), and `validateStagePayload`, and make sure every update/repair path preserves it instead of silently dropping it. All work is gated behind flag F132C `verticalDramaSceneContracts`; flag-off must be byte-identical to today.

## Dependencies

- **Soft dependency on Section 03 (`evidenceLedger`, F132B)**: `contract.newClueIds[]` is specified as "refs into evidenceLedger" (spec §6.1), but Section 03 may not have landed yet. Ship `newClueIds` as free-form strings (deterministic max-2 budget enforced regardless of whether they resolve to real ledger rows). When Section 03's `evidenceLedger` schema (`shared/verticalDramaSeries/qualityLedgers.ts`) exists, a follow-up can tighten validation to check `newClueIds` against `evidenceLedger[].id`, but this section must not block on that — do not add a hard foreign-key-style check here.
- **Downstream consumers of this section's interface** (do not duplicate their logic, but honor this contract shape so they don't need to re-derive it):
  - Section 07 (Targeted Revision Engine v2, F132E) — shot-scoped repair (`scope: shot_dialogue | full_shot`) reads `contract` to know what a shot must still satisfy after a splice-repair, and is expected to preserve/re-emit it. Section 07's repair prompt-composition additions should call the same "preserve contract" helper this section introduces (see Implementation steps) rather than re-implementing it.
  - Section 09 (Character Personality & Image Quality / scene-contract → visual bible binding, spec §10.7) — reads `contract.emotionalBeat` to pick the nearest entry in a character's `visualBible.emotionalRangeNeeded[]` for start-frame prompt assembly. It only needs `contract` to be present and shaped as specified here; it does not need to know how contracts are generated.
  - The Structure/Character/Evidence QC passes (multi-pass QC, Section 05/06, F132D) consume `contract` fields (`storyFunction`, `characterDecision`, `newClueIds`, `anchorLine`) to compute want/obstacle/choice/cost coverage and clue/anchor findings — this section only needs to guarantee the field is present and well-shaped; the pass logic itself lives in those sections.
- No dependency on Section 01/02 beyond the general flag-registry and criteria-module conventions already established in the codebase.

## Files to create

- None required. This section is additive/optional fields on existing schemas and existing functions; no new service files are strictly needed. (Optional, not required for this section: a small pure-function module `server/services/verticalDramaSceneContracts.ts` could host the new deterministic gate checks — `shotsHaveContracts`, `contractNewClueIdBudgetOk`, `anchorLineCadenceOk` — to keep `verticalDramaStoryBible.ts` from growing further; recommended but not mandated. If created, its exports are pure functions with no I/O, trivially unit-testable in isolation.)

## Schema / migration notes

- **No DB migration required.** `vertical_drama_series.bible` is `jsonb` (`drizzle/schema.ts:20378`) and `StoredBreakdownVersion`/`shotDrafts` live entirely inside that jsonb blob (per spec §13, confirmed against `schema.ts`). `contract` is just a new nested-optional key inside an already-jsonb-nested array of objects.
- `verticalDramaEpisodes.storyboard` (jsonb, per the `db.update(verticalDramaEpisodes).set({ storyboard: ... })` calls in `verticalDramaEpisodePipeline.ts`) is likewise jsonb — the `contract` field on storyboard shots needs no column change either.
- Both `shotDraftSchema` and `storyboardShotSchema` are `.passthrough()`, so even before any explicit `contract` key is added to the zod object shape, an LLM emitting a stray `contract` key would already survive round-tripping — the schema change here is about making the field *known/validated* (so the deterministic gates can rely on its shape), not about unlocking storage that didn't otherwise exist.
- No new database table, no `_journal.json` entry, no Alembic/Drizzle migration step in this section.

## Risk & rollback

- **Flag-off byte-identical requirement**: every prompt-builder change, schema change, and gate-check change in this section must be provably inert when `sceneContractsEnabled` is false/absent. Concretely: capture a snapshot of `buildDeepDraftPrompts`, `buildUserPrompt` (script generation), and the storyboard prompt builder's output BEFORE this section's changes for a representative fixture, and assert byte-identical output with the flag off AFTER the changes land. This is the single most important regression test in this section, since three separate prompt-builders are being touched.
- **`validateStagePayload` becoming a false-positive blocker**: since this function's failures are `repairable: true` but still surface as validation failures, a bug in the new contract checks (e.g. a wrong anchor-line-cadence math off-by-one) could block every episode's `storyboard_shotgrid` stage once the flag is on for a tenant. Mitigate by unit-testing the boundary conditions explicitly (exactly 3 shots between anchors = pass, 4 = fail) and by keeping the flag off by default (per spec §12, default `off`) until this is verified against real generated output in a lower environment.
- **Premium mode's shared `buildDeepDraftPrompts`**: because standard and premium share one prompt-builder function, a bug in the contract instruction block affects both modes simultaneously — there is no "premium-only" isolation the way `meetsPremiumDraftContractFloor` (gate-only, premium-only) has. Test both modes explicitly, not just premium.
- **Rollback**: since there's no migration, rollback is purely a flag flip (`verticalDramaSceneContracts` → off) plus a code revert if the flag-off path was somehow not fully inert. Any already-generated `contract` data sitting in existing rows' jsonb is harmless dead weight if the flag is later turned off — no cleanup needed (matches the project's additive-jsonb philosophy per spec §13).

## Acceptance criteria

Mapped to spec.md §16.2/§16.3 relevant bullets:

- Every shot in a deep-drafted episode (standard AND premium mode) has a `contract` object when `verticalDramaSceneContracts` is on; flag-off output has none, unchanged from today (§16.2 "want/obstacle/choice/cost derivable from contracts+beats" precondition; §16.5 "flag-off = current behavior").
- No shot's `contract.newClueIds` exceeds 2 entries — enforced deterministically (not merely requested in the prompt), verified by `meetsPremiumDraftContractFloor` (premium) and `validateStagePayload` (per-episode pipeline) (§16.3 "new-proper-noun budget respected").
- At least one anchor-line-marked shot (`contract.anchorLine === true`) per 3 consecutive shots within an episode's 9 shots — enforced by the same two gate points (§16.3 "Anchor-line cadence ≥1 per 3 shots").
- `plan_episode_script` and `storyboard_shotgrid` stage outputs carry `contract` through from the active breakdown's drafted shots (via `episodeDraft` hydration) without loss, verified by an integration-style test comparing input draft contracts to output shot contracts.
- Any repair (line-level via `updateEpisodeDraftDialogue`/`applyManualDialogueEdit`, or stage-level via `repairStageOutput`/`repairStage`) that changes a shot's dialogue either preserves that shot's original `contract` unchanged or emits an explicit, well-shaped replacement — never silently drops it — verified by the preservation test suite above.
