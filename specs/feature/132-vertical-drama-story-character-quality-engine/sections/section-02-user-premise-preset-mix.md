# Section 02: User Premise & Premise-Primary Preset Mix (F132A)

## Goal
Add an optional, 2,000-character free-form "โจทย์เรื่องที่อยากได้" (user premise) field to the Create Series Wizard step 0, positioned directly above the existing `เรื่องย่อ (logline)` field, and thread it end-to-end — wizard state → `create`/`synthesizeGenrePreset` tRPC inputs → preset-synthesis prompts (v1 and v2) → `bible.userPremise` (jsonb, no migration) → `generateStoryBible`/`generateStoryBibleDeep` prompts — so that when present it becomes the **primary story spine** and the 1–5 selected genre presets become supporting flavor, while an absent premise reproduces today's behavior byte-for-byte. Gated by tenant flag `verticalDramaUserPremise` (F132A), following the exact "server decides, client always sends the field" precedent already established by `verticalDramaSeriesPresetMixV2` (`CreateSeriesWizard.tsx:296-300`) so flag-off requests are provably unaffected regardless of client payload. Also wires a deterministic, warn-only `evaluatePremiseCoverage` guard and a read-only premise preview in the Deep Story Drafts panel.

## Risk & rollback
- **Primary risk**: accidentally changing the flag-off/empty-premise prompt output (breaks spec §16.1's "byte-identical to today" acceptance and could silently degrade existing series' story-bible quality).
  - Mitigation: every prompt-builder change (`buildUserPrompt`, `buildUserPromptV2`, `buildPrompts`, `buildDeepDraftPrompts`) must use the existing `.filter(Boolean).join("\n")` conditional-block idiom already used throughout these files (e.g. `speechBudgetEnabled ? ... : null` at `verticalDramaStoryBible.ts:1008-1010`) so an absent/empty `userPremise` literally never appends anything — write a snapshot/exact-string test of the current (pre-change) prompt output for each builder BEFORE editing, then re-run it after editing with `userPremise: undefined` and assert exact equality.
  - The tenant-flag gate at the router level (`verticalDramaUserPremise` off ⇒ `userPremise` forced to `undefined` before calling the service) is a second independent safety net, mirroring `verticalDramaSeriesPresetMixV2`'s proven pattern.
- **Secondary risk**: `create`'s new `bible` merge logic accidentally drops `input.bible` fields when `userPremise` is also present, or vice versa. Mitigation: the merge is a simple object spread (`{ ...(input.bible ?? {}), userPremise: input.userPremise }`) covered by an explicit "both fields present, both persist" router test (test plan item 5).
- **Rollback**: every change is additive and flag-gated; reverting is a straightforward git revert of this section's commits with zero data-loss risk (no migration, no destructive schema change, per the Database Safety Protocol's low-risk classification for "ADD COLUMN (nullable)"-equivalent jsonb-key additions).

## Acceptance criteria
Maps directly to spec.md §16.1:
- With no premise: synthesis (`buildUserPrompt`/`buildUserPromptV2`) and creation (`create`, `generateStoryBible*`) prompts and DB writes are byte-identical to pre-change behavior — verified by the exact-string regression tests in the test plan.
- With a premise + 3 presets (flag on): the synthesized draft's `logline`/`mainPlot` visibly derive from the premise (manual/LLM-response-fixture assertion in tests using a mocked LLM call that echoes premise entities); conflicting preset elements land in `draft.warnings`; a coverage-drift fixture triggers `evaluatePremiseCoverage`'s warning (the deterministic Phase-1 stand-in for the later `premise_drifted` season-critique finding kind, which is formally introduced under F132D/§8 — out of scope here, see Open Questions).
- Premise survives preset apply (`applyPreset`/`applyPresetDraft` never touch `form.userPremise`), series update (`updateSeries` accepts `bible.userPremise` via its existing wholesale-bible-replace path), deep generate and extend (`GenerateStoryBibleDeepParams.userPremise` threaded through `runGenerateStoryBibleDeepJob`/`runExtendStoryDraftHorizonJob`, both reading the same persisted `bible.userPremise`).
