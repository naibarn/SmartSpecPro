# Section 03: Ledgers & Story State (F132B)

## Goal
Add seven versioned "quality ledgers" (evidence, character activation, threat ladder, consequence, thread, world-rule, causal-chain) plus a typed per-episode "story state" object to the vertical-drama story pipeline, so long seasons can be tracked deterministically instead of relying on LLM context recall. Ledgers are built once per breakdown version (`ledger_plan` step, new skill `vertical-drama-ledger-planner`), then kept in sync deterministically (`reconcileLedgers`, no LLM) after every draft/critique/loop/replan mutation. Story state is appended to the existing append-only memory-event stream as `memoryKind: "story_state"`. This section owns: the zod schemas, the storage plumbing (`StoredBreakdownVersion.ledgers`, `bible.ledgers` mirror, memory event write/read), the `reconcileLedgers` deterministic engine, the new `ledger_plan` job phase, and the deterministic ledger-check functions (as pure functions returning `VdDramaturgyFinding[]`) that later sections wire into the multi-pass critique. Everything is gated by flag `verticalDramaQualityLedgers` (F132B); flag-off must be byte-identical to current behavior.

## Schema / migration notes
- **`vertical_drama_memory_events.memoryKind` is `varchar("memoryKind", { length: 40 }).notNull()`** (confirmed by reading `drizzle/schema.ts:20887`) — a **free-form varchar, NOT a database enum**. There is a separate `pgEnum("memory_kind", [...])` at `schema.ts:17186` (`memoryKindEnum`), but it belongs to the completely unrelated `scoped_memories` table (a general hierarchical agent-memory store, `schema.ts:17213`) — it is not referenced by `verticalDramaMemoryEvents` at all. **Conclusion: adding `"story_state"` as a new memory kind requires ZERO database migration.** It is purely a TypeScript union-type addition (`VerticalDramaMemoryKind` in `shared/verticalDramaSeries/memory.ts`) plus application-level validation; the column already accepts any string up to 40 chars (`"story_state"` is 11 chars, well within bounds).
- All other new structures (`StoredBreakdownVersion.ledgers`, `bible.ledgers` mirror, `story_state` payload contents) live in existing `jsonb` columns (`vertical_drama_series.bible`, `payload` on `vertical_drama_memory_events`) — per spec §13, **no new tables, no `pnpm db:push` needed for this section**. This matches the Database Safety Protocol's "Low risk" row for schema-additive jsonb changes; no backup step is required since no `ALTER TABLE` runs.
- Risk classification for this section's DB touch: **zero** (no migration). If a future section promotes ledgers to a dedicated table (spec §13's deferred option near `schema.ts:21039`), that is explicitly out of scope here and would need its own full Database Safety Protocol pass (backup, migrate, verify row counts) at that time.

## Risk & rollback
- **Flag-off safety**: every new code path (ledger_plan phase, reconcileLedgers calls, story_state event writes, memory-bundle `storyState` field) is gated behind `verticalDramaQualityLedgers` being resolved true for the tenant; when off, `buildEpisodeMemoryBundle` must omit the `storyState` key entirely (not `undefined`-key it) to match the existing `activeBreakdownVersion`/`standingArcDriftWarnings` byte-identical-when-off convention already established in this file.
- **`worldRuleSchema` upgrade risk**: this is the one *upgrade-in-place* (not purely additive) change in this section. Because it's `.passthrough()` and legacy bible rows may only have `{ rule, limit_or_cost }`, the new required-vs-optional fields must all default to safe values on read (e.g. `verdict` defaults to `"keep"`, `usedAgainEpisodes` defaults to `[]`) so a legacy world-rule row never fails validation. Regression test: parse an old-shape fixture (`{ rule, limit_or_cost }` only) through the upgraded schema and assert it still parses.
- **Reconcile correctness risk**: `reconcileLedgers` runs after every draft/critique/loop/replan mutation (per §5.1) — a bug here could silently corrupt ledger state across many call sites at once. Mitigate by keeping it a pure function with no DB/LLM access (fully unit-testable in isolation) and requiring idempotency (running it twice on the same input is a no-op) as a hard test invariant.
- **Rollback**: since there is no migration, rollback is a pure code revert (git revert the section's commits). No data cleanup needed — any `ledgers`/`story_state` jsonb already written is inert extra data that legacy (pre-revert) code already tolerates via `.passthrough()`/optional reads, so a revert does not need to strip written jsonb from existing rows.

## Acceptance criteria
Mapped to spec.md §16.2 ("Story quality (F132B–E, H)"):
- "Threat or consequence increases every episode (ladder check)" → covered by the threat-ladder non-escalating-stretch check in `reconcileLedgers`'s test suite.

- "Ledgers and story state update after every revision; re-score touches only revised episodes" → covered by `reconcileLedgers` idempotency + "never removes a row" tests; the "re-score touches only revised episodes" half is Section 06/07's responsibility, not this section's, but this section's `reconcileLedgers` signature must support being called with a partial (revised-only) episode subset without discarding unaffected ledger rows.
