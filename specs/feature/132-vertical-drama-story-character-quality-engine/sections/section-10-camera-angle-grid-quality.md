# Section 10: Camera Angle Set Quality (Nine-Angle Cinematic Grid) (F132I)

## Goal
Upgrade the existing, shipped "multi-angle variations" feature (the "สร้างหลายมุมกล้อง (3x3)" button) so its one 3×3 grid render — 9 different camera angles of the same shot/moment — is backed by a structured, per-angle description (9 required fields), a deterministic diversity/coverage check across the 9 angles' narrative functions, and a 6-dimension best-angle scoring pass that surfaces a "แนะนำ" (recommended) badge on the highest-scoring tile. The existing manual click-to-approve picker UX (`VerticalDramaStoryboardPanel.tsx`'s inline angle-candidate picker) is preserved unchanged — this section adds information, never replaces the user's choice. All new behavior is gated behind flag F132I `verticalDramaAngleGridQuality`; flag-off must reproduce today's exact prompt, schema, and picker behavior byte-for-byte. This section must not touch `contracts.ts`'s (or any file's) definitions belonging to the storyboard's OTHER "9" — the 9 sequential story shots (`contactSheets.ts`, `VerticalDramaContactSheetPicker.tsx`, `vertical-drama-storyboard-shotgrid` skill) — those are a distinct concept per spec §19.1 and are read-only/out-of-scope here.

**Grounded correction to the spec's own premise** (confirmed by reading the real code, not assumed): today, `generateStartFrameAngleVariations` makes **zero LLM calls**. It takes the shot's already-generated `frame.imagePrompt` (produced once, per-episode, by the `vertical-drama-shot-start-frame-render` skill's one call covering all 9 *story* shots — a genuinely different "9" again), string-concatenates a handful of fixed TS-authored sentences instructing "3x3 grid, 9 different camera angles, no on-image text" (`apps/web/server/routers/verticalDramaEpisodes.ts` lines ~7655-7666), and submits that single text prompt directly to `mediaGenerationService.generateImageAsync`. There is no intermediate structured JSON response to "parse" today (spec §19.5's phrase "parse the LLM's structured 9-candidate response" describes a step that does not yet exist). Implementing §19.2's 9-field-per-angle schema and §19.3/§19.4's deterministic/scoring checks therefore requires **adding a brand-new LLM planning call** (with its own cost) into this flow, not merely re-parsing an existing one — see Implementation steps and Risk & rollback for how this is scoped and flagged.

## Risk & rollback
- **Flag-off byte-identical requirement, with a genuinely new cost path to guard against**: unlike most other Feature 132 sections (which extend an existing prompt/schema), this section introduces a **brand-new LLM call** (`planAngleGridCandidates`, and separately `scoreAngleGridCandidates`) into a flow that previously made zero LLM calls. The single most important regression guard is confirming these two calls are NEVER invoked when `verticalDramaAngleGridQuality` is off — a bug here would silently add LLM cost/latency to every angle-grid generation for every tenant, flag or no flag. Mitigation: the flag-off test in Test-first plan item 6 explicitly asserts the mocked planning/scoring functions were never called, not just that the final `gridPrompt` string matches.
- **New credit-cost surface when the flag is ON**: today, one "multi-angle grid" costs exactly one image-render credit charge (`gridCreditCost`, priced via `calculateCreditCost(pricingModel, { numImages: 2 })`). With F132I on, two additional LLM calls (planning + scoring) run before that image charge — spec §19 does not explicitly discuss a new credit charge for these, and this section does not introduce one (LLM planning calls elsewhere in this codebase, e.g. `generateStoryBibleDeep`, are typically credit-gated separately from image renders) — flagged as an explicit open question below since it changes the feature's real-world cost profile per tenant when enabled.
- **New skill directory review-cycle risk**: a 4th "vertical-drama-*" skill directory (mirroring Section 09's precedent) means one more skill to keep in sync if the underlying `imagePrompt`/grid-instruction conventions change later — mitigated by keeping `buildAngleGridImagePromptFromCandidates`'s deterministic TS composition (not the LLM) responsible for the actual final image-generation prompt text, so the skill's job is narrowly "describe 9 distinct angles," never "write the final grid prompt."
- **Diversity/scoring warnings must never block**: per spec §19.3/§19.7, a failing diversity check produces a `warnings[]`/`diversityWarnings[]` entry, never blocks generation or spends extra credit — mirrored exactly on `checkAngleGridDiversity`'s signature (no boolean "passed" field to accidentally wire into a hard gate).
- **Rollback**: flip `verticalDramaAngleGridQuality` off — `generateStartFrameAngleVariations` skips the new planning/scoring/diversity block entirely and reverts to today's single-string `gridPrompt`; already-persisted `candidates`/`scores`/`recommendedIndex` on existing rows become inert dead JSON (harmless, matches the project's additive-jsonb philosophy); the picker's recommended-badge JSX simply never renders (no `recommendedIndex` present). No DB migration to revert. No code from any of sections 01-09 is touched, so rollback here has zero interaction with any other Feature 132 section's rollout state.
