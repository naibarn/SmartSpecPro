# Section 07: Targeted Revision Engine v2 (F132E)

## Goal

Convert every QC output — season critique findings (`critiqueSeasonDrafts` / `applySeasonCritique`, `server/services/verticalDramaStoryBible.ts`) AND per-episode quality-review issues (`runVerticalDramaEpisodeQualityReview`, `verticalDramaQualityReviewApply.ts`) — into one normalized, typed **revision plan** (spec §9.1), and execute each entry at the *narrowest* scope that fixes it. The only genuinely new execution mechanism is **shot-scoped repair** (`shot_dialogue` / `full_shot`): instead of `repairStage("storyboard_shotgrid", ...)` regenerating all 9 shots (today's only path — confirmed in `verticalDramaEpisodePipeline.ts:3227-3238`, which unconditionally calls `generateRealStoryboard` → `generateStoryboardShotgrid` for the whole episode), the repair prompt carries only the target shot(s) + adjacent context + relevant ledger slices, and the result is **spliced** back into the persisted 9-shot array, leaving every untouched shot byte-identical. `line` scope, `episode_beat`/`episode_outline` scope, and `cross_episode` scope reuse existing mechanisms unchanged. A `structural`-severity finding is the only thing allowed to widen scope, and it must go through an approval step reusing the existing retcon propose/approve/reject pattern.

## Dependencies

- **Section 03 (Ledgers & Story State, F132B)**: this section's revision-plan entries carry `affectedLedgers[]`, and every revision execution ends with a `reconcileLedgers` pass (Section 03's deterministic reconciler) — this section is a **consumer**, not the owner, of `reconcileLedgers`. Do not re-specify its internals here.
- **Section 04 (Scene Contracts, F132C)**: shot-splice repair sends the target shot's `contract` object (and, per spec §9.2, "relevant ledger slices") as prompt context, and the splice must preserve or explicitly re-emit each touched shot's `contract` (§6.2 rule: "a repair that changes a shot's dialogue must keep the contract or explicitly emit an updated one"). F132E's shot scope is flag-dependency-ordered *after* F132C (spec §12: "F132C before F132E shot scope — splice needs contracts").
- **Section 06 (Multi-Pass QC & Scorecard v3, F132D/H)**: this section is the **consumer** of Section 06's `severity` taxonomy (`minor | moderate | major | structural`) attached to every finding/issue, and of the finding/issue shapes themselves (season critique `findings[]`, episode review `issues[]`). Do not redefine severity semantics here — only branch on the value.
- Existing (unflagged) machinery this section extends rather than replaces: `classifyQualityReviewIssueLocation`, `groupQualityReviewIssuesByStageWithFlag`, `composeQualityReviewRepairInstruction`, `evaluateVerticalDramaStoryLockScriptGuard`/`...StoryboardGuard` (all `server/services/verticalDramaQualityReviewApply.ts`); `runVerticalDramaQualityLoop` (`server/services/verticalDramaQualityLoop.ts`); `repairStage` (`server/services/verticalDramaEpisodePipeline.ts:3169`); `updateEpisodeDraftDialogue` (`server/routers/verticalDramaSeries.ts:3938`, input schema `updateEpisodeDraftDialogueInput` at `:2621`); `applySeasonCritique` (`verticalDramaStoryBible.ts`, params `ApplySeasonCritiqueParams`); the retcon propose/approve/reject procedures (`server/routers/verticalDramaEpisodes.ts:6075` `proposeRetcon`, `:6127` `approveRetconProposal`, `:6156` `rejectRetconProposal`, backed by `verticalDramaSeriesMemoryService`).

Client + server both import this (client needs it for the scope-label UI, per spec §17 test item 4) — must be dependency-free of DB/LLM imports, mirroring the convention already used by `shared/verticalDramaSeries/qualityPolicy.ts`.
- `server/services/verticalDramaRevisionPlan.ts` (new, sits beside `verticalDramaQualityReviewApply.ts`) — pure, DB-free normalizer + scope-decision functions:
  - `normalizeQualityReviewIssueToRevisionPlanEntry(issue, context)` — maps one `QualityReviewIssueLike` (+ its severity, sourced from Section 06's extended issue shape) to a revision plan entry; reuses `classifyQualityReviewIssueLocation`'s stage classification as an input signal but adds a **shot-number extractor** (new — no such extractor exists in the codebase today; confirmed by grep) to populate `shot`/scope `shot_dialogue`/`full_shot` distinctly from stage-level `episode_beat`.
  - `normalizeSeasonCritiqueFindingToRevisionPlanEntry(finding, context)` — maps one season-critique finding (today's `ApplySeasonCritiqueFindingInput`-shaped kind/evidenceEpisodes/problem/fixInstruction, extended by Section 06 with `severity`) to a plan entry. **Post-completeness-audit correction**: an earlier draft of this section routed BOTH single-episode and multi-episode season-critique findings through `applySeasonCritique`'s mechanism, which contradicts spec §9.2's table (row 3 groups `episode_beat` AND `episode_outline` under "existing stage-level repair (`plan_episode_script`) — unchanged"; only row 4, `cross_episode`, is "existing `applySeasonCritique` + arc replan — unchanged"). The corrected mapping: `finding.evidenceEpisodes.length === 1` → `scope: "episode_outline"`, executed via the SAME stage-level `repairStage("plan_episode_script", ...)` mechanism as `episode_beat` (not via `applySeasonCritique`); `finding.evidenceEpisodes.length > 1` → `scope: "cross_episode"`, executed via `applySeasonCritique` + arc replan as today. Shot-granular season-critique findings (when Section 06 attaches shot-level evidence) normalize to `shot_dialogue`/`full_shot` per the same rule as episode-review issues (open question below).
  - `resolveRevisionScope(entry)` — enforces "never widen scope silently": returns the entry's stated scope unchanged unless `severity === "structural"`, in which case it returns a `{ requiresApproval: true, proposedScope }` result instead of auto-executing.
  - `spliceStoryboardShots(currentStoryboard, revisedShots)` — pure function: replaces only the shots whose `shot_number` is in `revisedShots` inside a structurally-cloned copy of `currentStoryboard.shots`, leaving every other shot reference-equal/unchanged; asserts the result's shot count and `shot_number` set are IDENTICAL to the input's (post-completeness-audit fix — an earlier draft hardcoded "exactly 9 shots," which is a brittle assumption not fixed by spec §9: shot count per episode can vary, e.g. short/teaser formats or 131 §7.7's density-reform variance; the invariant this function must actually guarantee is "same shot count and same shot-number set as the input," not a literal constant — this still mirrors `evaluateVerticalDramaStoryLockStoryboardGuard`'s own defensive count check, generalized to whatever count the input actually has).

## Schema / migration notes

- **No new tables.** Per spec §13, revision plans are additive jsonb, stored as run artifacts with new stage tags (`revision_plan`). Confirmed against `drizzle/schema.ts:20770` (`verticalDramaRunArtifacts`): the table has `episodeId` and `runId` as **NOT NULL** foreign keys — this fits episode-quality-review-sourced revision plans (always tied to one episode's pipeline run) cleanly, storing the normalized plan as a `jsonPayload` artifact with `stage: "revision_plan"` linked to that episode's active `runId`.
- Season-critique-sourced revision plan entries (which can span multiple episodes, `cross_episode` scope) do **not** fit that NOT NULL shape — mirror the existing `lastCritique` persistence pattern instead (`verticalDramaStoryBible.ts:5464-5521`, stored on `StoredBreakdownVersion`'s own jsonb metadata, mirrored to `bible.ledgers`-style read path per Section 03 §5.1). Concretely: add a sibling `revisionPlan` key alongside `lastCritique` on the active breakdown version, not a run artifact row. This is a deliberate divergence from a single uniform storage location — flagged as an explicit assumption below, not silently decided.
- All schemas additive/optional; no `contract_version` bump needed on existing scorecards (revision plan is a new, independent artifact type, not a scorecard mutation).

## Risk & rollback

- **Primary risk**: a shot-splice that leaves a touched shot's contract/continuity inconsistent with its untouched neighbors (e.g. a new prop introduced in shot 4's revision that shot 5 references as already-known, or a `source_beat_indexes` drift). Mitigations, layered:
  1. `spliceStoryboardShots` is a pure, structurally-cloned replace-by-`shot_number` — neighbors are never touched, by construction (proven by the reference-equality test above), so any contract drift can only originate from the LLM's revised shot content itself, not from the splice mechanics.
  2. The existing `evaluateVerticalDramaStoryLockStoryboardGuard` runs unmodified on the spliced (full 9-shot) result — it already rejects a shot-count change or a `source_beat_indexes` change on ANY shot, so it catches both splice bugs and story-lock violations in the revised shot itself.
  3. Per Section 04 (§6.2), the splice must carry forward or explicitly re-emit the touched shot's `contract` — a repair prompt that omits `contract` on a touched shot should be treated as invalid output (fails `validateStagePayload`'s contract-presence check, F132C flag-gated) rather than silently accepted.
  4. `reconcileLedgers` (Section 03) runs after every revision and re-derives ledger state from drafts — an orphaned clue or broken activation introduced by a shot splice surfaces on the NEXT critique pass, not silently.
- **Rollback**: F132E is fully flag-gated (`verticalDramaTargetedRevisionV2`, default off). Flag-off byte-identically preserves today's `repairStage`/`applySeasonCritique`/quality-loop behavior (no shot-splice code path is ever entered), so rollback is a flag flip with zero data migration.
- **Regression risk in the loop**: reordering `runVerticalDramaQualityLoop`'s per-round work (line → shot → stage) changes WHICH repairs happen before the round's single re-review — this could change round-count/escalation outcomes for existing fixtures. Mitigate by keeping the flag-off path calling the untouched `groupQualityReviewIssuesByStageWithFlag` exactly as today, and only routing through the new line/shot split when F132E is on.

## Acceptance criteria

Maps to spec §16.2's targeted-revision bullets:
- "A revision plan entry always names a scope" — every normalized entry has a non-null `scope` (tested in normalization unit tests).
- "A dialogue-only weak episode is fixed at shot/line scope with structure intact and continuity unbroken (verified by re-running Continuity Pass on neighbors only)" — integration test: an episode with only dialogue-flavored issues produces a plan with zero `episode_beat`/`episode_outline`/`cross_episode` entries; after applying, `plan_episode_script` and the untouched shots' storyboard content are unchanged (Story-Lock script guard sees no violation since that stage was never repaired at all), and re-scoring touches only the revised episode.
- "Never widen scope silently" — the `resolveRevisionScope` unit tests above directly assert this; a non-structural finding's scope is never auto-escalated under any severity/kind combination.
- "Ledgers and story state update after every revision; re-score touches only revised episodes" — end-to-end test asserting `reconcileLedgers` is called exactly once per revision batch and the re-review call list contains only the touched episode id(s).
- Loop status vocabulary and `maxAutoImproveRounds` remain byte-identical to pre-F132E behavior when the flag is off (snapshot/regression test against existing `verticalDramaQualityLoop.test.ts` fixtures).
