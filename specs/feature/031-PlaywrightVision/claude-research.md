## Part 1: Codebase Analysis

### 1.1 Existing Browser Automation

**Key files:**
- `python-backend/app/orchestrator/node_executors/integration_executors/browser_executor.py` (166 lines) — delegates to Python API via Node.js
- `python-backend/app/services/tools/browser_tool.py` (392 lines) — SSRF guard, concurrency, session lifecycle
- `python-backend/app/api/browser.py` (130 lines) — FastAPI endpoint
- `apps/web/server/routes/browserTool.ts` (220+ lines) — Node.js: feature flag check, credit pre-reservation, forward to Python

**Current architecture (Node.js-mediated):**
- Node.js endpoint `/api/internal/tools/browser` handles credit pre-reservation (20 credits), feature flag check (`browserAutomation`), concurrency enforcement
- Python endpoint `POST /api/browser/execute` does the actual Playwright work
- Flow: BrowserExecutor (Python orchestrator) → HTTP POST to Node.js → Node.js validates + deducts credits → forwards to Python API

**Supported actions (current):** `navigate, click, fill, screenshot, extractText, extractLinks, waitForSelector, scrollTo`

**Security model:**
- SSRF protection: 3 layers — IP blocks (RFC 1918), hostname blocks (localhost, metadata endpoints), DNS resolution check
- Concurrency: Redis semaphore — 1 per user (`browser:sem:user:{id}`), 2 per tenant (`browser:sem:tenant:{id}`)
- Output limits: 50KB text, 100KB HTML, 200 links max, 5 screenshots max
- Session timeout: 300 seconds max
- `allowed_domains` whitelist: empty list = deny all

**Note:** `browser_tool.py` currently uses stub implementations (no real Playwright calls) — the structure is ready for full integration.

**Feature 031 change:** The new `PlaywrightScriptGenerator` and `SelfHealingExecutor` will use Playwright **directly in Python** (not via the Node.js proxy path). The existing `builtin-browser` tool path stays unchanged.

### 1.7 FastAPI Endpoint Patterns

## Part 2: Web Research Findings

### 2.1 Playwright Async Python Best Practices (2025)

**Core context manager hierarchy (resource-safe):**
```python
async with async_playwright() as pw:
    browser = await pw.chromium.launch(headless=True)
    async with await browser.new_context() as context:
        async with await context.new_page() as page:
            await page.goto("https://example.com")
```

**Key production rules:**
- One shared `Browser` per worker (expensive: 150-200 MB, 1-3s startup)
- One `BrowserContext` per tenant/session (cheap: 50-100 MB, fully isolated)
- Always `await context.close()` in `finally` blocks — not just on happy path
- Call `await playwright.stop()` explicitly in long-running services — the context manager `__aexit__` can deadlock
- **Never use `ProcessPoolExecutor` with Playwright async** — causes hang on context exit. Use asyncio concurrency only.

**Concurrency guidelines:**
- 3-5 concurrent contexts: safe for development / small servers
- 10 concurrent contexts: typical production (8-16 GB RAM)
- 20+: requires dedicated high-RAM machine or cloud browser service

**Timeouts:**
```python
page.set_default_timeout(30_000)           # 30s for all actions
page.set_default_navigation_timeout(60_000) # 60s for navigations
```

Sources: [Playwright Python docs](https://playwright.dev/python/docs/browser-contexts), [GitHub issue #2132 (deadlock)](https://github.com/microsoft/playwright-python/issues/2132), [Scrapfly guide Dec 2025](https://scrapfly.io/blog/posts/web-scraping-with-playwright-and-python)

### 2.2 Vision LLM for UI Element Detection

**Core pipeline:**
```python
screenshot_b64 = await page.screenshot(encoding="base64")

response = openai_client.chat.completions.create(
    model="gpt-4o",
    response_format={"type": "json_object"},
    messages=[{
        "role": "user",
        "content": [
            {"type": "text", "text": "Find the Submit button. Return JSON: {selector, confidence, reasoning}"},
            {"type": "image_url", "image_url": {"url": f"data:image/png;base64,{screenshot_b64}"}}
        ]
    }]
)
```

**Annotated screenshot pattern (most reliable):** Inject numbered overlays `[1]...[N]` at each interactive element via JavaScript before screenshot. Assign `@eN` refs to DOM elements. Vision model identifies by number → deterministic Playwright locator. This is the approach used by production browser agents (e.g., vercel-labs/agent-browser).

**Prompt engineering principles:**
- Require JSON output with `confidence` field (0.0-1.0)
- Reject results with confidence < 0.7
- One action per prompt (one click, one fill)
- Include word "json" in prompt when using JSON mode (required by OpenAI)
- Ask for `reasoning` field to aid debugging

**Model comparison (2025 benchmarks):**
| Model | Accuracy | Notes |
|---|---|---|
| GPT-4o | 65.1% | Tends to abbreviate output |
| Claude 3 Sonnet | 70.3% | More complete output |
| Claude 3 Opus | 61.5% | Underperforms Sonnet |
| ShowUI (2B, CVPR 2025) | High | Returns `[x,y]` coordinates, no DOM needed |

**For Claude (Anthropic SDK):**
```python
{"type": "image", "source": {"type": "base64", "media_type": "image/png", "data": screenshot_b64}}
```

**Known failure modes:**
| Mode | Mitigation |
|---|---|
| Hallucinated selectors | Always validate returned selector against live DOM before using |
| Token budget exhaustion | Capture viewport only (not full page); use `clip` option |
| Ambiguous elements | Numbered overlay system eliminates ambiguity |
| Dynamic content missing | Wait for `networkidle` or specific element before screenshot |

Sources: [Bright Data guide 2026](https://brightdata.com/blog/ai/web-scraping-with-gpt-vision), [ShowUI CVPR 2025](https://www.blog.brightcoding.dev/2025/09/24/showui-the-2-billion-parameter-mini-brain-that-can-click-type-and-navigate-any-gui-like-a-human/), [vercel-labs/agent-browser](https://deepwiki.com/vercel-labs/agent-browser/5.4-skills-and-templates)

### 2.3 Self-Healing Selectors

**Selector priority hierarchy (most to least resilient):**
1. `page.get_by_role("button", name="Submit")` — ARIA role (survives redesigns)
2. `page.get_by_label("Email address")` — label text
3. `page.get_by_text("Continue")` — visible text
4. `page.get_by_test_id("submit-btn")` — `data-testid`
5. `page.locator(".submit-btn")` — CSS (fragile)
6. `page.locator("//button[1]")` — XPath (most fragile)

**Fallback array pattern:**
```python
async def click_with_fallback(page, selectors: list[str], timeout=5000):
    for selector in selectors:
        try:
            locator = page.locator(selector)
            await locator.wait_for(state="visible", timeout=timeout)
            await locator.click()
            return selector  # return winner
        except Exception:
            continue
    raise Exception("All selectors exhausted")
```

**AI healing as last resort:**
1. Capture screenshot + DOM at failure moment
2. Send to vision LLM with failed selector and intent
3. LLM returns new selector suggestion + confidence
4. Validate suggestion against live DOM
5. Cache with shorter TTL (less trust than verified selectors)

**Failure diagnosis — capture all four at failure time:**
- Screenshot at moment of failure
- DOM snapshot (`page.content()`)
- DOM diff vs last-known-good
- Accessibility tree snapshot (`page.accessibility.snapshot()`)

Sources: [BrowserStack self-heal docs](https://www.browserstack.com/docs/automate/playwright/self-healing), [BreakTheBuild AI pipeline](https://www.breakthebuild.org/stop-test-failures-in-their-tracks-build-a-self-healing-playwright-pipeline-with-ai/)

### 2.4 Browser Pool & Concurrent Session Management

**Production pattern — semaphore pool:**
```python
class BrowserPool:
    def __init__(self, max_contexts: int = 10):
        self._browser: Browser | None = None
        self._semaphore = asyncio.Semaphore(max_contexts)
        self._pw = None

    async def start(self):
        self._pw = await async_playwright().start()
        self._browser = await self._pw.chromium.launch(
            headless=True,
            args=["--no-sandbox", "--disable-dev-shm-usage"]
        )

    async def stop(self):
        if self._browser:
            await self._browser.close()
        if self._pw:
            await self._pw.stop()

    @asynccontextmanager
    async def acquire(self, **context_options):
        async with self._semaphore:
            context = await self._browser.new_context(**context_options)
            try:
                yield context
            finally:
                await context.close()
```

**Per-tenant Redis atomic counter:**
```python
async def acquire_tenant_slot(tenant_id: str, limit: int) -> bool:
    key = f"browser_pool:active:{tenant_id}"
    async with redis.pipeline() as pipe:
        pipe.incr(key)
        pipe.expire(key, 300)  # safety TTL
        results = await pipe.execute()
    count = results[0]
    if count > limit:
        await redis.decr(key)
        return False
    return True
```

**Idle reaper (run as background asyncio task):**
```python
async def reaper_loop(interval_seconds: float = 60.0):
    while True:
        await asyncio.sleep(interval_seconds)
        # close contexts idle > IDLE_TIMEOUT_SECONDS
        # reset Redis counters if count > actual processes
```

**Common pitfalls to avoid:**
| Pitfall | Fix |
|---|---|
| New browser per request | Share one browser, use contexts per request |
| Missing `finally` on `context.close()` | Always close in `finally` |
| `ProcessPoolExecutor` + async Playwright | Use asyncio only — no process pools |
| Redis counter without expiry | Always `EXPIRE` keys as safety net |
| Context reuse across tenants | Never reuse contexts across tenant boundaries |

Sources: [Crawlee BrowserPool API](https://crawlee.dev/python/api/class/BrowserPool), [Medium: Building Scalable Browser Pool](https://medium.com/@devcriston/building-a-robust-browser-pool-for-web-automation-with-playwright-2c750eb0a8e7)
