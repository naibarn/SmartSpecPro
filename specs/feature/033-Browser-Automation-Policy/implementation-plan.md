# Implementation Plan

## Objective

Implement a single browser automation policy system that governs every production browser execution path, starting with Automation Copilot and the live Playwright executor, while preventing the raw browser tool from acting as an unenforced production bypass. The plan must keep online decisions deterministic and low-latency, reuse the existing approval system for v1, store only minimal structured evidence, and introduce dedicated tenant-scoped browser policy configuration rather than extending unrelated workflow governance tables.

## Current-state impact map

The most relevant existing behavior is split across Node request orchestration, Python live browser execution, existing approval infrastructure, and tenant feature gating. `apps/web/server/routers/automationCopilot.ts`, `python-backend/app/api/automation_copilot.py`, `python-backend/app/tasks/automation_copilot_task.py`, `python-backend/app/services/playwright_script_generator.py`, and `python-backend/app/services/self_healing_executor.py` form the live browser execution path that will become the primary policy-enforced production path. `apps/web/server/routes/browserTool.ts` and `python-backend/app/api/browser.py` form a second browser path that currently cannot remain production-enabled unless it shares the same policy contract. `apps/web/server/routers/approvals.ts`, `python-backend/app/api/approvals.py`, `python-backend/app/services/approval_db_service.py`, and the existing approval UI must continue to work after browser-specific payload extensions are added. `apps/web/server/services/featureFlags.ts`, `apps/web/server/services/tenantFeatureFlagService.ts`, and `apps/web/shared/featureFlags.ts` continue to provide kill switches and rollout gates. Regression risk is highest in browser execution startup, approval round-trips, domain and navigation enforcement, and tenant isolation.

## Target architecture

The policy engine should be implemented as a shared Node.js policy module that evaluates browser actions before execution and acts as the only online decision authority for production browser automation. It should expose a single contract that receives normalized browser action input plus execution context, loads tenant browser policy configuration and applicable rules, computes page sensitivity and action class, decides whether the action should be allowed, denied, or routed to approval, emits a policy decision record, and returns an execution instruction to the caller.

This shared contract must be used immediately by the Automation Copilot execution path. The raw browser tool must not receive separate bespoke policy logic. Instead, the plan should keep the raw browser tool tenant-disabled for production until it can call the same policy contract. That preserves the user requirement that policy be always-on in production without creating two policy implementations.

The online policy engine should remain rule-based and deterministic. The codebase already shows that the critical browser path is latency-sensitive and split across services. A synchronous online LLM classifier would add cost, latency, and unpredictable failure modes. Any model-assisted analysis should be deferred to offline jobs for rule improvement or backfill review. Existing domain allowlists remain a defense-in-depth input to the final decision, not the sole policy layer.

## Production rollout and execution surfaces

The implementation should explicitly separate execution-surface readiness. The first production-ready surface is Automation Copilot and the underlying Playwright executor. The raw browser tool should remain internal-only or otherwise tenant-disabled through existing feature or availability controls until it is re-routed through the shared policy interface. The plan should include a hard launch guard that verifies the raw browser path cannot be enabled for tenant production use without the shared policy path in place.

That hard launch guard should be concrete rather than procedural. The implementation should add a startup or configuration invariant plus deployment verification that blocks tenant-facing raw browser enablement unless the shared policy contract is wired, healthy, and covered by launch checks. This guard should be directly testable so flag drift or partial deploys cannot accidentally expose the raw path.

Copilot’s approval notifications may continue using the current polling model in v1. This keeps the initial launch aligned with the user’s decision not to block Feature 033 on SSE. The polling response payloads should be extended to include browser policy approval context, while the longer-term architecture remains open to an SSE bridge once the policy engine is stable.

## Tenant-scoped configuration and rules

Introduce dedicated tenant-scoped browser policy persistence in the shared database. One table should hold tenant-level browser policy configuration such as enforcement phase, enabled state, approval TTL bounds, evidence retention preferences, rollout flags, and other defaults. A second table should hold ordered tenant-level browser policy rules or overrides, including conditions, resulting decisions, thresholds, and priority. The plan should not extend `workflow_policy_rules`, because the user explicitly chose separate browser policy ownership and the semantics differ from workflow governance.

Because the existing `system_settings` table is global by `(category, key)`, it should not be used as the primary home for browser policy. Any configuration that must be tenant-specific must be loaded from the new tenant-scoped tables. Existing feature flags can continue to act as coarse gates, but fine-grained policy state must come from the dedicated tables.

The initial seeded default set should be inserted through migrations or startup seeding so that v1 does not depend on a new tenant admin UI. The plan should define a stable seed format and a lightweight backend or API surface for inspection and future management, but tenant CRUD UI is deferred.

Regression checks should prove that browser policy resolution does not silently fall back to the existing global `tenant_automation` settings path. If any temporary compatibility bridge is needed during rollout, it should be explicitly transitional, narrowly scoped, and validated separately from the steady-state tenant-scoped read path.

The plan should explicitly keep two policy layers rather than collapsing them into one table shape. Tenant browser policy config and tenant browser policy rules establish tenant-wide defaults, deny overrides, rollout phase, and incident controls. A separate workflow entitlement layer should remain the source of truth for per-workflow allowed capabilities, forbidden capabilities, allowed data classes, approval TTL overrides, record-count and action-count limits, origin-transition limits, enable or disable state, expiry, and review cadence. Approval TTL should follow the approved bounds from the spec: default 300 seconds, minimum 60 seconds, and maximum 900 seconds unless governance changes them in a future revision. The policy engine should require both layers for authorization: tenant policy defines the ceiling and global safeguards, while workflow entitlement defines the minimum scope actually granted to a specific browser run.

This workflow entitlement layer should also own the workflow-level kill switch required by the spec. If a workflow entitlement is disabled, expired, or missing a required capability, the shared policy contract should fail closed before any live browser action executes, even if tenant-level browser policy is otherwise enabled. Seed data and future inspection APIs should therefore cover both tenant defaults and workflow entitlements so rollout, debugging, and incident response do not depend on implicit configuration.

## Shared policy evaluation flow

The shared policy pipeline should normalize each action into a stable input envelope containing tenant context, workflow context, execution context, target origin, action type, action payload summary, any candidate file or data-transfer metadata, and whatever page context the executor already has at decision time. It should classify the action into read, draft, commit, or restricted tiers and score page sensitivity using deterministic signals such as URL patterns, form field types, control labels, iframe or popup context, and precomputed capability rules. It should then resolve applicable tenant rules, workflow entitlement constraints, and rollout defaults, determine the final policy decision, and persist a minimal policy decision record before returning the result to the caller.

The decision contract should support at least the browser-specific results already reflected in the spec: allow, allow with redaction, require approval, deny, and escalate for review. This should use a dedicated browser-policy decision enum and storage representation rather than reusing `policy_action`, because browser-policy decision semantics are broader than workflow governance actions and were explicitly separated in the approved spec.

Because online policy decisions originate in Node while live browser execution and approval consumption still cross into Python-owned paths, the plan should define a versioned policy envelope and shared fixture set for the Node/Python boundary. Contract tests should verify that approval payload extensions, policy decision fields, and context fingerprints serialize consistently across both stacks before rollout.

The shared policy engine should also own approval grant verification. When an action requires approval, the same policy module should compute and store the binding material for approval validation so execution can later verify that the action, origin, page context, transfer target, and workflow entitlement context still match the approved request.

Decision evaluation should make capability and data-handling checks first-class rather than secondary annotations. The policy engine should reject actions when the workflow lacks the required capability, when the target data class exceeds workflow allowance, when a transfer crosses the allowed trust boundary, or when per-workflow bulk and rate thresholds are exceeded. This keeps least privilege enforceable at runtime instead of treating workflow metadata as documentation only.

Fallback semantics should be explicit and fail closed. Unknown or weakly classified contexts should be downgraded to read-only behavior, low-confidence non-read actions should require approval or be denied according to the configured threshold, and restricted-class detections must never degrade into permissive execution just because classification confidence is incomplete. These downgrade rules should be deterministic, visible in audit output, and covered by tests so all execution surfaces behave the same way under uncertainty.

## Approval reuse and contextual binding

The implementation should reuse the existing approval request and response flow for v1. Browser-specific policy approvals should create standard approval requests through the current approval service, but the payload and extra metadata need to be extended so users are approving a precise browser action rather than a generic task. The approval request should include normalized action description, target origin, execution ID, policy reason codes, action digest, payload preview hash, page-context fingerprint, optional screenshot hash, TTL, and enough user-visible text for the existing approval UI to explain the consequence clearly. The migration contract should remain explicit: the existing approval request model needs browser-specific fields for `action_digest`, `dom_fingerprint`, and `screenshot_hash`, while `payload_preview_hash` must be preserved in the browser approval payload contract so both Node and Python can compute and display the same approval preview semantics.

Approval validation should be stricter in v1 than the original draft spec. The user chose invalidation on any navigation, frame change, or popup change. The implementation should therefore treat these transitions as approval-context invalidators, not just major DOM drift. This should be wired into the browser execution lifecycle so a paused approval cannot later be replayed on a different page, frame, or popup surface.

The invalidation contract should call out exact event coverage and exact comparison semantics. Verification must cover top-level navigation, subframe navigation, popup creation, and redirect-driven origin changes on the live execution path, with fail-closed behavior if context continuity cannot be confirmed. At resume or immediately before action dispatch, the executor should recompute and compare a context hash derived from at least `action_digest`, `dom_fingerprint`, and `target_origin`. If the context hash no longer matches, if the action digest changes, if the origin changes, or if DOM fingerprint drift exceeds the approved threshold of more than 20 percent, the approval must be invalidated and a new approval required.

Invalidation outcomes should also be standardized in audit output. Approval invalidation due to changed execution context should emit a dedicated reason code aligned with the source spec, including `approval_context_changed`, so analytics, incident review, and replay tooling can distinguish context drift from expiry, rejection, or operator revocation.

Approval creation and policy-audit persistence should be duplicate-safe under task retries, executor reconnects, and transient transport failures. The plan should include correlation keys or idempotency semantics tying a pending approval and its decision record to one logical action attempt so retries cannot create multiple approvals or conflicting audit rows for the same paused step.

Polling-based status delivery is sufficient in v1, but the plan should ensure approval state becomes visible to the existing status responses quickly enough for the frontend polling interval to present it without additional manual refresh logic. Browser-specific payload fields should be added in a backward-compatible way so existing approval UIs render sensible summaries before any dedicated browser approval component exists.

## Execution-path integration details

The first implementation pass should attach policy enforcement to the Automation Copilot path at the point where live actions are about to execute, not only when scripts are generated. Current codebase research showed that script generation validates the initial URL and installs a route handler during planning, but execution itself does not clearly reapply the same guardrails during live navigation, redirect, frame, or popup transitions. The plan should therefore require execution-time enforcement hooks around navigation and action dispatch in the Playwright executor path. That is necessary to close the current gap between planned intent and actual browser behavior.

The raw browser tool path should not receive a shortcut. Instead, launch gating should ensure it remains disabled for tenant production use until it can call the same shared policy contract with the same rule loading, approval handling, and audit emission. This minimizes duplicated logic and matches the user’s instruction to avoid separate enforcement implementations.

Execution-time enforcement should cover more than click and form actions. Download initiation, upload selection, clipboard-style copy or transfer flows, popup creation, redirect completion, and cross-origin frame interaction should all pass through the same policy contract or a directly equivalent preflight. The implementation should treat hidden browser or OS prompts such as file pickers, permission prompts, download prompts, and certificate warnings as sensitive interaction points that fail closed unless an explicit rule and entitlement permit proceeding.

Iframe trust handling should be implemented according to the approved three-tier model rather than left to heuristic interpretation. Same-origin iframes may inherit parent policy directly. Same-site cross-origin iframes should be treated as constrained surfaces that inherit parent sensitivity but cap allowed behavior at draft-class actions, with commit-class actions requiring approval. Cross-site iframes should be treated as new untrusted contexts that are reclassified independently and capped at read-only behavior, with draft and commit actions denied by default and logged with a dedicated reason code. Sandboxed Tier 2 or Tier 3 iframes should be treated as the strictest cross-site tier.

## Data handling and exfiltration controls

The plan should translate the spec’s data-handling rules into explicit runtime controls. Downloads from sensitive contexts should be denied by default unless the workflow entitlement explicitly allows the file class and destination handling. Uploads should be denied by default, require approval for external destinations, and verify both the file source and allowed data class before dispatch. Copy and extraction flows should be constrained by row-count, record-count, and sensitivity thresholds, with redaction or masking when extracted content is forwarded to other processing components.

Bulk guardrails should be enforced through the same shared policy path rather than by best-effort logging alone. The implementation should define per-workflow thresholds for non-read actions, extracted record volume, external sends, and origin transitions, and it should store these limits in workflow entitlement configuration so operators can tune them without code changes. Existing Redis concurrency controls should be extended to support per-action-type rate limiting and aggregate threshold tracking by workflow, user, and tenant where appropriate.

Clipboard and inter-page transfer should be treated as policy-relevant actions instead of invisible browser state. The plan should explicitly deny copying data from restricted or high-sensitivity contexts into untrusted destinations and should treat transfer attempts across origins, tabs, or workflows as new policy decisions rather than implicit follow-on behavior.

## Evidence model and privacy boundary

Only minimal structured evidence should be retained by default. Policy decision records and approval payloads should store normalized action metadata, page origin and normalized route identity, action digest, DOM or page-context fingerprint, screenshot hash where needed, decision result, reason codes, and timing metadata. The plan should explicitly exclude raw DOM snippets and full screenshots from default retention. If future debugging exceptions are ever allowed, they should be modeled as a separate opt-in policy with explicit governance, not quietly introduced into v1’s default audit path.

This privacy boundary should also affect observability. Metrics and logs should use normalized or hashed fields wherever possible. Existing audit logs should continue to avoid secret disclosure, and browser-policy additions should follow the same redaction expectations already visible in `browser_tool.py`.

Verification should include explicit tests and assertions that policy audit rows, approval payloads, debug logging, and status responses exclude raw DOM snippets and full screenshot blobs under default settings. Privacy regressions in this area should be treated as release blockers.

Audit storage should also satisfy the spec’s forensic requirements rather than only serving product analytics. The plan should preserve compatibility with the existing JSONL audit stream while also writing structured database records, so operators can query browser-policy activity with the same local tooling patterns already used elsewhere in the repo. The append path should be tamper-evident through an integrity mechanism such as chained hashes, signed batches, or another verifiable append-only strategy that can be checked during incident review without exposing secret material.

The audit contract should explicitly cover linkage between policy decisions, approvals, and downstream action outcomes. Investigators should be able to reconstruct which approval authorized which action, which rule or entitlement produced the final decision, whether a revocation or invalidation occurred, and what the eventual execution result was, all without persisting raw secrets or full DOM captures.

## Data model and migration strategy

This feature is primarily additive, but it spans a shared database used by both Drizzle and SQLAlchemy code. The plan should therefore establish a clear ownership split. Node-side Drizzle should own new tenant browser policy tables and most browser-policy decision querying types. Any Python approval model changes that are necessary for browser-specific payload enrichment should be limited and coordinated so the same approval rows remain readable from both stacks.

For the high-write policy decision history, use a partitioned append-only table with monthly range partitions from the beginning. The write volume and retention expectations justify early partitioning. The partitioned parent table and maintenance configuration should be created through raw SQL migration where necessary, while query-side typing can still be represented in Drizzle schema definitions. The plan should use `pg_partman` as the primary partition lifecycle mechanism and define a fallback maintenance job if `pg_partman` is unavailable in a target environment.

The operational plan should define concrete failure detection and operator response for partition maintenance. Monitoring should detect missed future partition creation, retention drift, and failed maintenance runs. The runbook should specify how to activate the fallback maintenance path safely, how to verify new partitions are writable, and how to confirm retention behavior has not removed data outside policy.

## Regression prevention strategy

Regression prevention must focus on three failure modes: accidental browser denials that break safe workflows, missed denials or approval gates that let risky actions through, and tenant-scoping mistakes that load the wrong policy configuration. The implementation should therefore expand test coverage at multiple layers. Node tests should cover policy-rule loading, decision resolution, rollout gating, raw browser tool disablement, and approval payload generation. Python or integration tests should cover approval invalidation, execution-path enforcement during real navigation and frame or popup changes, and prevention of unenforced live browser paths. End-to-end or higher-level integration tests should prove that a Copilot action requiring approval becomes visible through the existing approval APIs and that an approval becomes invalid if navigation or frame context changes.

Regression coverage should also include duplicate-suppression and contract-verification cases. Tests should prove that retried Copilot steps do not emit duplicate approval requests for the same logical action, that policy decision writes remain idempotent under replay, and that shared Node/Python fixtures keep approval payloads and policy-decision envelopes stable across both stacks.

The rollout should include a telemetry-first phase where the policy engine computes decisions and writes audit records before broad enforcement is enabled on new tiers. Even though production enforcement is always-on for enabled surfaces, rollout phases still matter for which action classes are permitted. Read-only and draft phases should be validated against labeled decisions before commit-class approvals are turned on.

Rollout gates should carry the concrete thresholds already approved in the spec so phase changes are operationally executable rather than policy-shaped aspirations. The observe-to-read-only gate should require at least 14 calendar days and at least 10,000 policy decisions, using whichever condition takes longer, plus a reviewed sample of at least 500 enforcement-worthy decisions with precision of at least 98 percent, false-positive rate at or below 1 percent, false-negative rate at or below 2 percent on the reviewed sensitive set, at least 7 consecutive stable days, and zero P0 or P1 misses. The read-only-to-draft gate should require deny precision of at least 99 percent plus approval-UX usability signoff. The draft-to-commit gate should require zero P0 incidents over 7 days and approval abandonment under 10 percent. The commit-to-expanded gate should require zero P0 or P1 incidents over 14 days, full red-team pass rate, and complete audit coverage.

## Observability and monitoring

Observability should focus on decision quality and operational correctness rather than verbose page capture. The implementation should emit metrics for decision volume by tier, allow or deny or require-approval rates, approval creation rate, approval expiry or invalidation rate, rule-hit distribution, classifier confidence buckets, and policy evaluation latency. Rollout gates should track precision and false-positive rate on reviewed samples, with separate reporting for commit-class actions so low-risk traffic does not mask high-impact misclassification. Alerts should be defined for spikes in denials, approval invalidations, decision-write failures, partition maintenance failures, and any sign that the raw browser tool became tenant-accessible without shared enforcement.

The plan should define an explicit online latency budget and timeout posture for policy evaluation so Copilot responsiveness does not degrade silently. Metrics and alerts should distinguish successful decisions, soft timeouts, hard failures, and fallback or fail-closed outcomes, with owner review if the policy engine exceeds its budget or if timeout rates trend upward during rollout.

Ownership should be explicit. Security or platform owners should be accountable for rule seed quality, partition maintenance health, and rollout gate review, while application owners remain accountable for Copilot UX and approval integration behavior.

## Incident controls and kill switches

The implementation plan should convert incident response requirements into concrete product behavior. Global and tenant-level kill switches should continue to use the existing feature-flag stack, while workflow-level disable should be enforced through workflow entitlement state. High-priority domain or category deny overrides should be represented as top-priority tenant policy rules so operators can block a newly risky destination or page category immediately without waiting for a full rule redeploy.

Approval revocation should be treated as an active control, not a passive state change. The plan should include a way to revoke pending or recently granted browser approvals, propagate that state to polling clients, and ensure executors fail closed if they observe revocation during resume or just before action dispatch. Incident handling should also cover suspicious prompt injection, suspicious bulk extraction, unintended external send, automation on restricted pages, approval-flow misuse, and cross-tenant or cross-session mix-ups, with owner-visible alerts and a short operator runbook for each class.

## Data safety strategy

Risk classification for database changes is low, because the expected schema work is additive: new tenant browser policy tables, new browser-policy decision storage, optional approval payload metadata extensions, and associated indexes and partitions. No destructive column removal or in-place semantic migration is required for v1.

Because the risk is not none, the plan should still include a pre-migration backup and verification step appropriate to the deployment environment before running production schema changes. The migration approach should remain non-destructive and expansion-first: create new tables, enums, indexes, and partition management configuration; seed defaults; deploy application reads and writes to the new objects; verify correctness; and only then enable enforcement phases. No contract or removal phase is required in v1 because existing systems remain in place.

Rollback should be defined at two levels. Application rollback should first disable tenant-facing access using feature flags or raw-surface disablement and return Copilot to the previous browser execution availability mode if policy integration proves unstable. Database rollback should avoid dropping newly created policy data during the initial incident response window; instead, leave additive tables in place, stop writing or reading them, and verify that approval and browser flows recover under the prior application version. Post-rollback verification should confirm that Copilot execution, approval listing, approval submission, and tenant feature gating still work as expected, and that no tenant can access the raw browser tool as a bypass.

## Compatibility notes

Backward compatibility depends on preserving the existing approval interface, existing feature-flag behavior, and current browser feature availability semantics. The approval system should continue to work for non-browser use cases without requiring UI changes. Browser-specific payload additions must therefore be additive and optional. Existing domain allowlist logic should remain active as a supporting control. Existing raw browser route behavior should only change in one deliberate way: it must remain disabled for tenant production use until it shares the new policy enforcement path. That compatibility choice is intentional and safer than exposing a known bypass.

Observe-only or telemetry-first rollout must not be interpreted as a permissive bypass mode. On tenant-facing production surfaces, observe mode should still keep restricted actions blocked, keep raw-browser bypasses disabled, and avoid granting new write capabilities that the fully enforced path would later deny. The safest interpretation for v1 is that observe mode either runs on internal evaluation traffic only or behaves as read-only plus shadow scoring for higher-risk classes, so no production tenant surface gains an unenforced commit path.

## Implementation phases

Begin by adding the tenant browser policy config and rule tables, the workflow entitlement table and lookup path, the append-only browser policy decision storage, and the necessary seed data and rollout controls. In the same phase, define the shared policy contract in Node and establish the integration seam that the Copilot path will call before execution. That foundation should also include the audit append path, integrity mechanism, workflow-level disable semantics, and the data contract shared across Node and Python boundaries. Next, integrate the Copilot path with the shared policy evaluation and approval request generation, including execution-time navigation, frame, popup, redirect, download, upload, and transfer invalidation handling. Then extend polling status responses and existing approval UIs with the browser-specific metadata needed for v1 approvals and approval revocation. In parallel with these changes, harden launch guards so the raw browser tool remains production-disabled until the same shared policy integration is complete. Finish by adding data-handling guardrails, bulk and rate limits, observability, rollout metrics, incident controls, and operational maintenance for partitioned audit storage.

## Testing and verification approach

Testing should mirror the implementation phases. Start with deterministic unit coverage for rule evaluation, action classification, sensitivity scoring, workflow-entitlement lookup, capability enforcement, data-class handling, rollout phase resolution, and approval binding. Add service-level tests for approval creation, revocation, invalidation, policy decision persistence, audit integrity verification, and launch guards that prevent raw-browser production enablement without shared enforcement. Extend integration tests around the Copilot path so a planned risky action produces a pending approval, polling surfaces that approval, approval submission resumes the right action only if context still matches, and any navigation, frame, popup, redirect, download, upload, or destination change invalidates the pending approval or triggers re-evaluation as intended.

Verification should also include abuse-driven scenarios, not only happy-path regression. Tests should cover prompt-injection and deceptive-label pages, hidden auth prompts in iframes, popup origin changes, mass extraction attempts, external-send thresholds, clipboard or cross-origin transfer attempts, denied downloads from sensitive pages, upload approval on external destinations, and workflow-disable or domain-override incidents. Finally, add operational verification for partition creation and maintenance health, rollout-dashboard checks for decision latency, precision review, false-positive thresholds, and explicit checks that observe-mode behavior never exposes an unenforced write path.
