## Relevant schema and behavior observed

- `users` is the existing account authority. It has integer `id`, `email`, `normalizedEmail`, nullable `password`, `loginMethod`, `currentTenantId`, disabled-state fields, `twoFactorEnabled`, encrypted `twoFactorSecret`, hashed recovery codes, and `sessionRevokedAt`. No account data or hash values were read.
- `tenant_users` binds `tenant_id` and `user_id` with role and active state. `tenants` contains `primaryDomain` and `domains`; current Legacy middleware resolves a hostname to a customer tenant through those fields. The table also contains both snake-case and camel-case generations of several legacy fields, so adapters must map the live schema exactly.
- The canonical shared tables `worker_jobs`, `worker_job_events`, `worker_job_outbox`, `credit_transactions` and `billing_subscriptions` exist. `worker_jobs` has customer `tenantId` and requester identity fields, but no explicit environment-tenant column. No environment-tenant mapping was found in `users`, `tenants`, `tenant_users` or `worker_jobs`.
- The current email/password login verifies bcrypt hashes, enforces disabled-account and 2FA behavior, and issues a host-scoped cookie. Device direct-login code also handles Argon2 hashes. Existing cookie validation checks the user's `sessionRevokedAt` fence; the separate hashed-JTI revocation store is used by bearer-token validation. Preserve and explicitly test the session behavior before claiming per-session revocation parity.
