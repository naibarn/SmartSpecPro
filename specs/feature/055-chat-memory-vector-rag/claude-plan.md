# Implementation Plan — Feature 055: Chat Memory Vector RAG

## 1. Overview

### What We're Building

A 2-level vector RAG memory system for SmartSpecPro's chat interface that replaces the current "full dump + keyword rank" approach with semantic retrieval. The system:

- **Archives** raw messages to encrypted JSONL files (per-record AES-256-GCM)
- **Extracts** key facts into `scoped_memories` with 1536-dim pgvector embeddings (Level 1)
- **Chunks** raw messages into `message_chunks` with pgvector embeddings (Level 2 fallback)
- **Retrieves** via hybrid search (BM25 + cosine similarity + recency decay)
- **Summarizes** only safe content — decisions, rules, and code are preserved as facts, never lossy-compressed

### Why This Approach

The current system (`memoryService.ts:buildChatContext`) dumps up to 50 entity memories into context using keyword ranking, consuming ~40% of the budget on often-irrelevant facts. Summaries take another ~60%, leaving only ~35% for actual recent conversation.

The new system uses vector search to pull only the most relevant memories (10-15 records vs 60), freeing budget so recent messages get **65-70%** of context. A JSONL archive + Level 2 chunks guarantee zero data loss even when the LLM fact extractor misses something.

### Key Context

- **Primary modification target:** `apps/web/server/services/memoryService.ts` — `buildChatContext()` (line 1677) and `processConversationMemory()` (line 2087)
- **Secondary (no change needed):** `apps/web/server/services/executors/contextBuilder.ts` already uses scoped memory for agency flows
- **pgvector:** Already installed and used by `scoped_memories` (1536-dim) and `multimodal_memory_vectors` (768-dim)
- **Latest migration:** 0110 — new migration will be 0111
- **BullMQ pattern:** Lazy init + `redis.duplicate()` per connection, workers in same Node.js process

## 2. Database Schema

### 2.1 New Table: `message_chunks`

Stores ~500-token segments of raw conversation for Level 2 vector search.

```typescript
messageChunks: pgTable("message_chunks", {
  id: text PK (UUID),
  tenantId: varchar(36) NOT NULL,
  userId: integer NOT NULL → users.id CASCADE,
  conversationId: integer NOT NULL → conversations.id CASCADE,
  messageRangeStart: integer NOT NULL,
  messageRangeEnd: integer NOT NULL,
  chunkIndex: integer NOT NULL,
  content: text NOT NULL,
  tokenCount: integer NOT NULL,
  embedding: vector(1536) NULLABLE,  // async via BullMQ
  projectId: varchar(100) NULLABLE,  // for cross-conversation search
  personaId: varchar(36) NULLABLE,
  createdAt: timestamptz DEFAULT now(),
})
```

**Indexes:**
- `UNIQUE (conversationId, chunkIndex)` — idempotency
- `(tenantId, userId)` — user-scoped queries
- `(createdAt)` — retention cleanup
- `HNSW (embedding vector_cosine_ops) WHERE embedding IS NOT NULL` — ef_construction=64 (write-heavy)
- `GIN to_tsvector('english', content)` — keyword fallback
- `(tenantId, projectId)` — cross-conversation search within project

### 2.2 New Table: `memory_archive_metadata`

Tracks encrypted JSONL archive files on disk.

```typescript
memoryArchiveMetadata: pgTable("memory_archive_metadata", {
  id: serial PK,
  tenantId: varchar(36) NOT NULL,
  userId: integer NOT NULL → users.id CASCADE,
  conversationId: integer NOT NULL → conversations.id CASCADE,
  archiveDate: date NOT NULL,
  filePath: text NOT NULL,
  messageCount: integer DEFAULT 0,
  fileSizeBytes: integer DEFAULT 0,
  encryptionVersion: integer DEFAULT 1,
  createdAt: timestamptz DEFAULT now(),
})
```

**Indexes:**
- `UNIQUE (conversationId, archiveDate)` — one file per day per conversation

### 2.3 Alter Table: `conversation_summaries`

Add four nullable columns (metadata-only ALTER, no table rewrite):

- `skippedRiskyCount: integer DEFAULT 0` — risky messages NOT summarized
- `extractedFactIds: text[]` — soft reference to scoped_memories IDs
- `hasRawArchive: boolean DEFAULT false`
- `classificationStats: jsonb` — `{ safe: N, risky: N }`

### 2.4 New Indexes on Existing Tables

```sql
CREATE EXTENSION IF NOT EXISTS vector;  -- idempotent safety

-- L1 facts: high-quality HNSW for small, stable dataset
CREATE INDEX CONCURRENTLY scoped_memories_embedding_hnsw_idx
  ON scoped_memories USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 200) WHERE embedding IS NOT NULL;

-- BM25 keyword search on scoped_memories
CREATE INDEX CONCURRENTLY scoped_memories_content_tsvector_idx
  ON scoped_memories USING gin (to_tsvector('english', content || ' ' || title));

-- Hot path: chunker reads messages by conversation
CREATE INDEX CONCURRENTLY idx_messages_conversation_id
  ON messages ("conversationId", "createdAt");
```

### 2.5 Migration: `drizzle/0111_chat_memory_vector.sql`

Generated by `pnpm db:push`. Must use `CREATE INDEX CONCURRENTLY` (cannot run inside transaction — Drizzle handles this). Post-migration: verify all indexes show `indisvalid = true`.

## 3. File-Based Memory Archive

### 3.1 Storage Design

**Location:** `data/memory-archives/` at monorepo root (outside `apps/web/` to prevent accidental static serving).

**Path construction:** `{base}/{sanitizedTenantId}/{userId}/conv-{conversationId}-{YYYY-MM-DD}.jsonl`

Every path segment is sanitized (alphanumeric + hyphen + underscore only) and the resolved path is verified to start with the base directory (prevents path traversal).

### 3.2 Encryption Model

Per-record encryption — each JSONL line is independently encrypted:

```
{12-byte-iv-hex}:{16-byte-authTag-hex}:{ciphertext-hex}\n
```

Uses existing `encrypt()` / `decrypt()` from `crypto.ts` (AES-256-GCM with `LLM_ENCRYPTION_KEY`). Each line gets a fresh random IV. Lines can be read/decrypted independently — corruption of one line doesn't affect others.

### 3.3 Service: `memoryArchiveService.ts`

**Responsibilities:**
- `archiveMessage(record)` — encrypt + append to JSONL (fire-and-forget, non-blocking)
- `readArchive(tenantId, userId, conversationId, dateRange)` — decrypt + parse lines
- `searchArchive(tenantId, userId, conversationId, query, limit)` — keyword search in decrypted content
- `cleanupExpiredArchives(tenantId, retentionDays)` — per-tenant, minimum 7-day floor
- `deleteUserArchives(tenantId, userId)` — for GDPR/account deletion

**Archive metadata** tracked in `memory_archive_metadata` table — `messageCount` and `fileSizeBytes` updated via upsert on each append. Verified on read for integrity.

### 3.4 Deletion Policy

When user deletes a conversation:
1. DB records cascade-deleted immediately (FK CASCADE)
2. Archive files marked for deletion (soft delete, 7-day grace period)
3. Daily cleanup task hard-deletes files past grace period

When user deletes account:
1. DB records cascade-deleted (FK CASCADE)
2. Archive directory deleted from disk synchronously (`fs.rm` recursive)

## 4. Fact Extraction Pipeline (Level 1)

### 4.1 Trigger

Runs after **every message pair** (user + assistant response). Invoked from `processConversationMemory()` when `chat_fact_extraction_enabled` flag is ON.

### 4.2 Flow

1. Take the latest message pair (user + assistant)
2. Call LLM with extraction system prompt + conversation in `HumanMessage` role
3. Parse JSON response through Zod schema validation
4. Filter out injection patterns (`/OVERRIDE|INJECTION|SYSTEM:|RULE:/i`)
5. Cap importance at 8 (only user-confirmed facts can reach 9-10)
6. For each extracted fact: check cosine similarity against existing memories (threshold 0.92)
   - If duplicate: reinforce (bump count + importance)
   - If new: insert into `scoped_memories` + queue embedding via BullMQ
7. Store with `sourceType: "auto"`, `ownerType: "user"`, `ownerId: String(userId)`

### 4.3 Category Mapping

| Extraction Category | memoryKindEnum |
|---------------------|---------------|
| decision | decision |
| rule | rule |
| fact | fact |
| preference | preference |
| checklist | checklist |
| artifact_note | artifact_note |
| note | note |

### 4.4 Embedding Generation

Facts are embedded asynchronously via BullMQ `"memory-embedding"` queue:
- Job payload: `{ type: "scoped_memory", recordId: uuid, text: "title content" }`
- Worker calls Python `/api/internal/embeddings` with `X-Internal-Token` header
- Validates embedding is 1536-dim array of finite numbers before DB update
- 3 retries with exponential backoff; dead jobs reconciled by daily task

## 5. Message Chunk Indexer (Level 2)

### 5.1 Trigger

Runs after **every message pair**, independent of summarization. Invoked from `processConversationMemory()` when `chat_chunk_index_enabled` flag is ON.

### 5.2 Chunking Strategy

- **Window size:** ~500 tokens (language-aware: Thai ~1.5 chars/token, English ~4)
- **Overlap:** 50 tokens between consecutive chunks (prevents context loss at boundaries)
- **Message boundaries:** Don't split mid-message if message < 500 tokens
- **Role prefix:** Each chunk includes `USER:` / `ASSISTANT:` role markers
- **System messages:** Stripped (not useful for retrieval)

### 5.3 Service: `messageChunkerService.ts`

**Core function:** `chunkMessages(messages)` → `ChunkResult { chunks[] }`

**Indexing function:** `indexMessageChunks(tenantId, userId, conversationId, messages, projectId?, personaId?)`
1. Chunk the messages
2. For each chunk: INSERT with `ON CONFLICT (conversationId, chunkIndex) DO NOTHING`
3. Queue embedding via BullMQ: `{ type: "message_chunk", recordId: uuid, text: content }`
4. PII handling: embed from `detectAndRedactPII(content)` sanitized text

### 5.4 Cross-Conversation Search

Per interview decision: chunks are searchable across conversations within the same project. The `projectId` column + tenant isolation enables this. `searchMessageChunks()` accepts optional `conversationId` — when omitted, searches all user's chunks in the project.

## 6. Smart Summarization Gate

### 6.1 Trigger

Replaces the existing inline LLM summarization when `chat_smart_summarize_enabled` flag is ON. Falls back to existing behavior when OFF.

### 6.2 Classification

LLM classifies message segments as SAFE or RISKY:
- **SAFE:** casual chat, Q&A, brainstorming, small talk → summarize normally
- **RISKY:** decisions, rules, constraints, debugging, config, action items, code > 10 lines → skip summarization (facts already extracted + archived)

Same prompt injection defense as fact extraction: `HumanMessage` role + Zod validation on output.

### 6.3 Flow Within `processConversationMemory()`

```
1. [always]     Archive messages → JSONL
2. [always]     Chunk messages → message_chunks + embed queue
3. [if summarize triggered] Extract facts → scoped_memories + embed queue
4. [if summarize triggered + smart gate ON]
     Classify segments → summarize SAFE only
   [else if summarize triggered + smart gate OFF]
     Use existing generateSummaryPrompt() → summarize all (legacy)
5. [always]     Legacy entity extraction (kept until Phase 2 stable)
```

## 7. 2-Level Chat Context Retrieval

### 7.1 Modification Target

**Only** `memoryService.ts:buildChatContext()` (line 1677). The secondary `contextBuilder.ts:buildChatContext()` already has scoped memory for agency flows — no change needed.

### 7.2 New Flow (replaces entity memory full dump)

When `chat_vector_memory_enabled` flag is ON and `memoryMode === "full"`:

1. **Generate query embedding** — call Python `/api/internal/embeddings` via `queryEmbeddingService.ts` (Redis-cached 5min, SHA-256 hash key)

2. **Level 1 search** — `searchMemories()` with scopes `[{ type: "user", id: String(userId) }]` + optional project/persona scopes. Top-10, hybrid BM25 + vector.

3. **Level 2 search** (conditional) — only if L1 returns < 3 results. `searchMessageChunks()` with top-5, cross-conversation within project. Pre-validates conversation ownership.

4. **Rules** — always fetched separately (`WHERE memoryKind = 'rule'`), never vector-filtered, never trimmed.

5. **Merge + dedup** — priority: Rules > L1 facts > L2 chunks > legacy entities. Dedup by record ID (not content prefix).

### 7.3 Budget Allocation

All percentages are **caps** (not fixed). Buffer gets all unused budget.

| Section | Cap | Notes |
|---------|-----|-------|
| System prompt | uncapped | Never trimmed |
| Rules | uncapped | Always included |
| L1 facts | max 20% | Primary vector search |
| L2 chunks | max 10% | 0% when L1 sufficient |
| Safe summaries | max 15% | Reduced from 60% |
| Buffer messages | remainder | Gets 65-70% typically |
| Visual memory | max 5% | When applicable |

Hard ceiling: MAX_MEMORY_TOKENS_IN_CONTEXT = 4000

### 7.4 Fallback

When flags are OFF: identical to current behavior (entity full dump + keyword rank + 60% summaries). Zero behavioral change for tenants without the feature enabled.

## 8. Embedding Pipeline

### 8.1 Python Endpoint: `/api/internal/embeddings`

**File:** `python-backend/app/api/internal/embeddings.py`

Two endpoints:
- `POST /api/internal/embeddings` — single text → 1536-dim embedding
- `POST /api/internal/embeddings/batch` — up to 100 texts → 1536-dim embeddings

**Auth:** `verify_internal_token` dependency (constant-time comparison of `X-Internal-Token` header against `SMARTSPEC_WEB_GATEWAY_TOKEN`).

**Import:** `from app.orchestrator.vector_store.embedding_service import EmbeddingService` (async, OpenAI text-embedding-3-small, 1536-dim). NOT `app.services.embedding_service` (sync, 384-dim local model).

**Text limit:** Max 32000 chars per text (~8000 tokens).

### 8.2 BullMQ Queue: `memory-embedding`

**Definition:** `server/queues/embeddingQueue.ts`
- Queue name: `"memory-embedding"`
- Lazy init pattern (matching `deliveryQueue.ts`)
- Default: 3 attempts, exponential backoff from 1s
- Concurrency: 3 workers
- DLQ: `"memory-embedding-dlq"` for permanent failures

**Job schema (Zod):**
```typescript
{ type: "scoped_memory" | "message_chunk", recordId: string (UUID), text: string (1-32000 chars) }
```

**Worker:** Validates job payload → calls Python embedding API with auth token → validates embedding array (all finite numbers) → UPDATE record in DB. Registered in main web server process (same as existing BullMQ workers).

### 8.3 Query Embedding Service: `queryEmbeddingService.ts`

Generates embeddings for user queries at search time. Redis-cached (5min TTL, SHA-256 hash key). Falls back gracefully — if Python backend is down, returns `undefined` and search degrades to keyword-only.

## 9. Background Tasks

### 9.1 Archive Cleanup (BullMQ repeatable)

- **Schedule:** Daily 03:00 UTC
- **Logic:** Iterate tenants, read per-tenant retention from `system_settings`, delete expired files
- **Safety:** Minimum 7-day retention floor (hardcoded)

### 9.2 Chunk Cleanup (BullMQ repeatable)

- **Schedule:** Daily 03:30 UTC
- **Logic:** Per-tenant: read retention from `system_settings` (default 90 days), delete expired chunks

### 9.3 Orphaned Embedding Reconciliation (BullMQ repeatable)

- **Schedule:** Daily 04:00 UTC
- **Logic:** Find chunks/memories with NULL embedding created > 1 hour ago; re-queue for embedding (batch of 200)
- **Alert:** If orphan count > 50/day, indicates embedding service degradation

### 9.4 HNSW Index Rebuild (Celery beat)

- **Schedule:** Weekly Sunday 04:00 UTC
- **Logic:** `REINDEX INDEX CONCURRENTLY` on both HNSW indexes
- **Post-check:** Verify `indisvalid = true` for all indexes

### 9.5 Memory Eviction (BullMQ repeatable)

- **Schedule:** Daily 05:00 UTC
- **Logic:** Per-user: expire → decay (importance < 3, unreinforced, 30+ days stale) → compact (cosine > 0.95) → warn if still over 500 limit

## 13. Security Checklist

| Concern | Mitigation |
|---------|-----------|
| Path traversal | `sanitizePathSegment()` + `path.resolve()` containment |
| Embedding API exposure | `/api/internal/` path + `verify_internal_token` + Nginx deny |
| Per-record encryption | Unique IV per JSONL line; AES-256-GCM via `crypto.ts` |
| Prompt injection | `HumanMessage` role + Zod validation + importance cap 8 + regex filter |
| Cross-user IDOR | Conversation ownership check before chunk search |
| BullMQ job poisoning | Zod schema on all job payloads; text length limit 32KB |
| GDPR deletion | 7-day soft delete + synchronous archive file removal on account delete |
| Embedding array injection | Validate `isFinite()` on every element before SQL |
| PII in chunks | Embed from PII-redacted text; raw content for keyword search only |
