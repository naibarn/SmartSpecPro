# Section 04: Database Schema and Migration

## Overview

This section adds the `userLlmApiKeys` table to the Drizzle ORM schema. This table stores user-provided LLM API keys encrypted with AES-256-GCM, using the same `crypto.ts` encryption functions already used by `llmProviders.apiKeyEncrypted` and `channelCredentials.credentialsEncrypted`. The table enforces a unique constraint on `(userId, provider)` so each user can store at most one key per LLM provider.

This section has no dependencies on other sections and can be implemented in parallel with Phase 1 work. It blocks section-05 (API key service) and section-06 (tRPC router), which depend on this table existing.

## Implementation Details

### Table Definition

Add the following table to the end of `/home/dev/projects/SmartSpecPro/apps/web/drizzle/schema.ts`. The imports needed (`serial`, `integer`, `varchar`, `text`, `timestamp`, `pgTable`, `uniqueIndex`, `index`) are all already imported on line 1 of the file.

```typescript
/**
 * User LLM API Keys — encrypted storage for user-provided LLM provider keys.
 * Keys are encrypted with AES-256-GCM via crypto.ts (same as llmProviders.apiKeyEncrypted).
 * One key per provider per user, enforced by unique index.
 */
export const userLlmApiKeys = pgTable("user_llm_api_keys", {
  id: serial("id").primaryKey(),
  userId: integer("userId").notNull().references(() => users.id, { onDelete: "cascade" }),
  tenantId: varchar("tenantId", { length: 36 }),
  provider: varchar("provider", { length: 50 }).notNull(),
  apiKeyEncrypted: text("apiKeyEncrypted").notNull(),
  keyHint: varchar("keyHint", { length: 8 }),
  createdAt: timestamp("createdAt", { withTimezone: true }).defaultNow(),
  updatedAt: timestamp("updatedAt", { withTimezone: true }).defaultNow(),
}, (t) => [
  uniqueIndex("user_llm_api_keys_user_provider_idx").on(t.userId, t.provider),
  index("user_llm_api_keys_user_idx").on(t.userId),
]);
```

### Column Rationale

- **`id`**: Auto-incrementing primary key. Follows the pattern of all other user-related tables (`userGroups`, `userCreditBudgets`, `userSkillVisibility`, etc.).
- **`userId`**: Foreign key to `users.id` with `onDelete: "cascade"`. When a user is deleted, their API keys are automatically removed. This matches the pattern used by `userSkillVisibility`, `userCreditBudgets`, and `userOrchestratorProfiles`.
- **`tenantId`**: Optional `varchar(36)` for multi-tenant isolation. Not a foreign key in this definition (consistent with some other tables in the schema). Allows filtering keys by tenant when needed.
- **`provider`**: `varchar(50)` storing the provider identifier string (e.g., `"openai"`, `"anthropic"`, `"deepseek"`, `"google"`, `"openrouter"`). The allowed values are enforced at the tRPC layer via Zod enum (section-06), not at the database level.
- **`apiKeyEncrypted`**: `text` column storing the AES-256-GCM ciphertext in `iv:authTag:ciphertext` hex format, produced by `encrypt()` from `/home/dev/projects/SmartSpecPro/apps/web/server/services/crypto.ts`. Uses `LLM_ENCRYPTION_KEY` environment variable.
- **`keyHint`**: `varchar(8)` storing the last 4 characters of the plaintext API key for UI display (e.g., user sees `sk-...abcd`). Stored in plaintext. This is safe because the last 4 characters of an API key are not sufficient to reconstruct or use the key.
- **`createdAt`** / **`updatedAt`**: Timestamps with timezone, defaulting to `NOW()`. The `updatedAt` field should be updated on upsert operations (handled in the service layer, section-05).

### Indexes

- **`user_llm_api_keys_user_provider_idx`**: Unique composite index on `(userId, provider)`. Enforces the business rule that each user can have at most one key per provider. Also serves as the primary lookup path for the service layer's upsert and delete operations.
- **`user_llm_api_keys_user_idx`**: Non-unique index on `userId` alone. Supports the `getUserApiKeys(userId)` query that lists all keys for a user.

### Risk Assessment

This is a **Low risk** operation (ADD TABLE -- no existing data affected):

- No existing tables are modified
- No data migration needed (user API keys in sessionStorage were never active in production)
- The `onDelete: "cascade"` on `userId` is safe since the table starts empty
- Rollback is trivial: `DROP TABLE user_llm_api_keys;`

Per the project's Database Safety Protocol, this is an ADD operation that requires only a row count check (which will be 0 since the table is new). No backup of existing tables is needed since no existing tables are altered.
