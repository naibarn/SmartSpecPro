================================================================================

1. CURRENT PROBLEM (Security Risk)
   ─────────────────────────────────
   • 2 Celery tasks pass user JWT tokens as arguments:
     - Agency Creator: create_agency_discover_task(), create_agency_design_task()
     - Automation Copilot: automation_analyze_task(), automation_execute_task()

   • JWT stored in plaintext in Redis queue (severe security issue)
   • Tokens accessible via:
     - Celery monitoring tools (Flower)
     - Worker logs
     - Task history/replay
     - Redis snapshots

   • Exposure window: 2-10+ minutes per task


2. HTTP ENDPOINTS RECEIVING JWT
   ────────────────────────────────

   Agency Creator (USES JWT):
   • POST /v1/chat/completions (Node.js LLM gateway)
     - 3x in discover phase (system prompt analysis)
     - 2x in design phase (spec generation)
     - 1x in document phase (usage guide)

   • POST /api/internal/agency/create (Node.js agency endpoint)
     - 1x after spec validation

   Automation Copilot (JWT UNUSED):
   • No HTTP calls use the JWT passed as argument
   • Uses LLMGatewayClient which uses X-Internal-Token (different auth)
   • Contains TODO comments: "Replace user_jwt with user_id + internal service token"


3. EXISTING INTERNAL TOKEN INFRASTRUCTURE
   ───────────────────────────────────────

   ✓ LLMGatewayClient (production-proven):
     - Header: X-Internal-Token (env var: SMARTSPEC_WEB_GATEWAY_TOKEN)
     - Context: X-User-Id, X-Tenant-Id
     - Used by: Automation Copilot (correctly)
     - File: python-backend/app/services/llm_gateway_client.py:65-82

   ✓ Token verification (Node.js):
     - Function: verifyInternalToken() with timing-safe comparison
     - File: apps/web/server/_core/llmRoutes.ts:1219-1232

   ✓ Short-lived token generation (Node.js):
     - Function: createInternalTokenFromAuth() — 15-min expiry
     - File: apps/web/server/_core/tokens.ts:127-145

   → These patterns can be reused for Agency Creator


4. JWT CLAIM STRUCTURE (for reference)
   ──────────────────────────────────────

   {
     "sub": "12345",        // User ID as string
     "type": "access",      // Token type
     "scopes": ["..."],     // Permission array
     "jti": "unique_id",    // JWT ID (one per token)
     "exp": 1234567890,     // Expiration timestamp (seconds)
     "iat": 1234567800      // Issued-at timestamp
   }


5. DATA FLOW ANALYSIS
   ──────────────────

   AGENCY CREATOR:
   Browser (JWT)
     → Node.js tRPC (extract: ctx.userToken)
     → Python FastAPI (body: user_jwt from credentials)
     → Celery Queue (task arg: user_jwt — PROBLEM)
     → Worker (use for 4x HTTP calls)

   AUTOMATION COPILOT:
   Browser (JWT)
     → Node.js tRPC (extract: ctx.userToken)
     → Python FastAPI (auth: X-Internal-Token; body: user_jwt — UNUSED)
     → Celery Queue (task arg: user_jwt — NOT USED)
     → Worker (ignores JWT, uses LLMGatewayClient instead)


6. RECOMMENDED SOLUTION (Option A: Preferred)
   ───────────────────────────────────────────

   Replace user JWT with existing internal service token pattern:

   REMOVE from task arguments:
     • user_jwt: str

   KEEP in task arguments:
     • user_id: int
     • tenant_id: str (add if missing)

   AT TASK RUNTIME:
     • Use LLMGatewayClient() with user_id + tenant_id headers
     • Or extend Node.js endpoints to accept X-Internal-Token + X-User-Id

   BENEFITS:
     ✓ No JWT in Redis queue
     ✓ Uses proven production pattern (LLMGatewayClient)
     ✓ Internal token never expires (monolithic)
     ✓ Minimal code changes

   ALTERNATIVE (Option B):
     • Generate fresh 15-min bearer token at task runtime
     • Requires exporting signBearerToken from Node.js to Python
     • More granular per-user, short-lived
