# SPEC-224 Runner snapshot wait and Goal recovery

- **Root cause:** the browser's immediate `availableWorkspaces.refetch()` reads the persisted Runner capability projection; it does not trigger a Runner workspace rescan. Runner workspace facts are published with its capability snapshot, normally on an approximately 120-second cycle. The earlier recovery therefore refreshed the same stale projection and stopped before the next snapshot arrived.
- **UI recovery:** after `EXECUTION_SOURCE_CHANGED`, Task Control keeps the original Goal blocked, prevents duplicate submission, explains that it is waiting for the Runner snapshot, and polls the existing workspace query. Once a newer snapshot is observed, the UI rebinds the same authorized workspace and prepares a fresh plan. It does not submit the Goal automatically. A manual check action and a timeout message are available if the snapshot does not advance.
