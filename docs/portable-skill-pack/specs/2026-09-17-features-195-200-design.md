# Features 195–200 Unified Implementation Design

Date: 2026-09-17  
Status: Approved by user for execution  
Source specifications: `specs/feature/195/spec.md` through `specs/feature/200-universal-coding-agent-control-plane/spec.md`

## Goal

Implement the six target specifications as one dependency-ordered platform evolution while preserving the current SmartSpecPro architecture and preventing duplicate execution, capability, Runner, context, asset, approval, billing or audit systems.

## Architecture

The platform has one control flow: Chat/Assistant (Feature 198) expresses intent through Feature 196 Goal/Plan/Command semantics; authorized capabilities are routed to either the Feature 199 External MCP gateway or Feature 200 External Agent runtime; all durable work enters Feature 195 `worker_jobs` and outbox; local execution is mediated by the Feature 197 Runner; results return to Feature 198. Realtime transport is never treated as durable truth.

Existing code is partial. Implementation must extend current `worker_jobs`, MCP, agent-runtime, Runner and Chat foundations rather than assuming target tables/routes exist. Every schema/API/UI addition requires tenant authority, idempotency, migration, rollback, observability and focused regression coverage.

## Dependency order

1. Feature 195: durable Job/outbox/lease/fencing contract and shared execution primitives.
2. Feature 196: Goal/Plan/Capability/Command normalization and orchestration services over 195.
3. Feature 197: Runner identity, capability snapshots, local execution and durable control channel over 195/196.
4. Feature 198: Chat/Assistant control surfaces, request lifecycle and evolution over 195/196/197.
5. Feature 199: External MCP upstream lifecycle, policy, quarantine and governed invocation over shared 195–198 boundaries.
6. Feature 200: provider-independent External Agent Task/session/runtime adapters over 195–199.

Within each feature: contracts and types → persistence/migration → domain services → API/router → UI → integration and recovery tests → acceptance evidence.

## Ownership boundaries

- Feature 195 owns durable `worker_jobs`, outbox, attempts, leases, fencing and lifecycle truth.
- Feature 196 owns Goal/Plan, capability resolution, command semantics and orchestration decisions.
- Feature 197 owns Runner/device identity, local resolution, execution control and reconnect/replay.
- Feature 198 owns Chat, Universal Assistant UI, user-facing plan/approval/task states and learning/evaluation semantics.
- Feature 199 owns external MCP upstream management, protocol/OAuth, schema/risk/quarantine and MCP invocation.
- Feature 200 owns external-agent provider adapters, sessions, normalized events/results and Agent Runtime Core.

## UI contract

The primary user entry point remains `/chat` and the Universal Assistant Side Panel. Feature 199 adds role-scoped MCP Center/Connected Apps surfaces using existing MCP admin/settings foundations. Feature 197 uses the existing Runner connection surface. Feature 200 adds Agent Panel/live task/approval/result states within the Chat/Assistant experience. No UI may expose upstream credentials, bypass tenant policy or imply that target functionality is implemented before its backend gate is ready.

## Failure and security model

Admission is durable before publication. Queue/runtime readiness cannot prevent a valid canonical Job write. Retries are bounded and idempotent; leases and fencing prevent stale side effects. Disconnect, restart, provider outage, malformed input, revoked credentials, stale capability snapshots and partial result delivery are explicit states. Client, hostname, queue and external-agent input never supplies tenant authority. Retired Agency, work request/workpack, `/workflows`, OpenSandbox, `sandbox_jobs` and Docker/OpenSandbox dispatch remain prohibited.

## Verification policy

Each feature ends with focused tests for changed paths, route/schema contract checks, `git diff --check`, and a cross-spec ownership check. Do not run whole-repository TypeScript typecheck. After Feature 200, run at least ten independent consistency rounds across all six specs, source anchors, schema ownership, routes, UI surfaces, prohibited paths, retry/idempotency and implementation blockers; fix high-confidence gaps immediately and record unresolved environment-only proof separately.
