# Long-running Job Completion Alerts

## Goal

Notify the owner of a long-running job when it reaches a terminal state. The
notification must identify the job, explain success or failure briefly, and
provide a safe internal link to the result screen. Notifications must be
scoped to the owning user and must not change the normal episode-generation
flow.

## Existing evidence

- `user_notifications` already stores structured action URLs, labels, metadata,
  and deduplication keys.
- `notificationService` already persists notifications and publishes a
  user-scoped Redis event consumed by `/api/notifications/stream`.
- `GlobalAlerts` currently invalidates notification queries on SSE receipt but
  does not show an immediate toast from the event payload.
- Vertical Drama story jobs already notify on terminal state. Interactive
  Vertical Drama jobs persist terminal Redis records but do not notify.
- Worker callback notifications are explicit and idempotent; generic terminal
  worker notification must not duplicate that callback path.

## Design

### Server

Use one best-effort terminal-notification helper with structured metadata:

- `source: "job_completion"` and a job-specific source name.
- terminal status, job kind/type, trace/job id, duration, retry information,
  and bounded error details where available.
- a stable `groupKey` per owner and job so retries or duplicate terminal
  callbacks update one notification instead of spamming the user.
- an internal relative `actionUrl` and action label whenever the result route
  is known; never trust arbitrary external URLs.

Call the helper after durable terminal state is written for Vertical Drama
interactive jobs and for opted-in worker job types. Keep the existing story
job notifier behavior compatible, or route it through the helper without
creating a second notification. Notification errors are logged and swallowed
after the job result has been persisted.

### Client

Extend the existing SSE hook to pass the event payload while preserving
backward compatibility for existing listeners. `GlobalAlerts` will:

1. invalidate the existing bell/urgent-reminder queries;
2. parse only valid notification payloads;
3. show an in-app success/error toast for job-completion notifications with an
   action that navigates to the safe internal result URL;
4. deduplicate toast display by notification id and terminal event key;
5. retain notification-bell history as the fallback when SSE is unavailable.

The toast is deliberately limited to notifications tagged as job completion,
so unrelated alert behavior is unchanged.

### Ownership and security

The server creates the notification using the persisted job owner (`userId` or
`requestedByUserId`). The Redis channel is already user-scoped. URLs are
relative application routes generated by trusted server code and remain subject
to the destination route's normal tenant/owner authorization.

### Failure handling and observability

Every terminal notification attempt logs a structured event containing owner,
tenant, job type/kind, job id, trace id, terminal status, dedup result, action
URL presence, and any notification error. The notification path cannot change a
successful or failed job outcome. SSE failure falls back to the existing
polling/bell path; repeated delivery cannot produce repeated toasts.

## Testing

- unit-test notification payload construction, ownership, safe action URLs,
  dedup keys, and swallowed notification errors;
- test interactive-job success/failure terminal paths;
- test worker opt-in and callback dedup boundaries;
- test SSE payload forwarding and GlobalAlerts toast/navigation behavior;
- run focused existing notification, SSE, Vertical Drama, and worker tests;
- run `git diff --check` and report unrelated baseline failures separately.

## Migration and rollout

No database migration is expected. Existing notification columns and metadata
are sufficient. Roll out additively: normal episode/story behavior remains on
its current path, and only terminal notification delivery is shared.
