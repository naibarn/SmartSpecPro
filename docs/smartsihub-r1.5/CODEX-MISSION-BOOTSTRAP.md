# SmartAIHub implementation bootstrap mission (R1.6 owner clarification)

## Objective

Implement the new SmartAIHub Modular SaaS Core first on the `aimarkethubs.com` Debian development/test target, then prepare its separately authorized Cloudflare Workers/Hono production target at `smartsihub.com`. Both applications use the existing canonical PostgreSQL `smartspec` database and existing user accounts; existing users can sign in with their current accounts. Keep development and production environment tenants, runtime credentials and release authorities separate. The current task package is SPEC/ADR/documentation only; this bootstrap is for a later implementation mission. Do not interpret a spec, domain registration, optimized build or account membership as evidence of a live product or release authority.

## Binding architecture

1. Build a usable new Core identity/action boundary, then Chat plus durable Agent identity and jobs, then complex Task/Mission surfaces and Mini Apps. `smartaihub.app` remains the Legacy application. New-platform development may proceed directly with Codex/Claude in the canonical source repository, or through existing SPEC-224 facilities on `smartaihub.app`; SPEC-224 is optional. Preserve truthful evidence for the path used. Full Legacy repair or cutover is not a global prerequisite.
2. Use Hono/TypeScript for the small Core API on local Debian/workerd and Cloudflare Workers. Do not add Express or import the Legacy Express runtime. Use private Service Bindings with caller verification, Durable Objects/Agents SDK for Agent identity/state and wakeups, Workflows for recoverable multi-step work, Queues for asynchronous transport, and suitable data bindings. Workers/DOs are event-driven and may hibernate or be evicted. Never require a resident cloud model, browser, Container or native supervisor.
3. Use the same canonical PostgreSQL `smartspec` database and existing identity, customer-tenant, entitlement, ledger and `worker_jobs`/outbox authority across `smartaihub.app`, `aimarkethubs.com` and `smartsihub.com`. Bind the modular development/test hostname to a distinct development environment tenant and the Cloudflare hostname to a separate production environment tenant. Keep customer tenant IDs and existing authorized canonical data shared under verified membership and role policy; keep development-only data and effects scoped to development. Use separate least-privilege runtime DB credentials and release identities per environment. Do not create a second identity, ledger, job authority or database copy.
4. Make Chat the primary signed-in workspace. Web Chat, headless HTTPS/MCP and the desktop Companion share the same typed action registry and frontend components/state. Closing a UI hides it; it does not cancel authorized durable work.
5. Use the three credential tiers: Tier A per-Worker/environment Secret bindings with required-secret preflight; Tier B only selected, scoped Secrets Store credentials after checking current product suitability; Tier C application-side AES-256-GCM tenant vault with wrapped DEKs behind a Credential Broker and external AWS KMS. No raw secret in prompts, memory, queues, browser storage or default logs. Device private keys remain local.
6. Enrolled Windows/Linux devices run a minimal Core Connector service at OS boot. The Connector uses outbound authenticated WSS, TLS validation, device-key proof and short-lived grants. Shell/browser/GPU/GUI Executor processes start only per bounded authorized task. No incoming control port, arbitrary command IPC, browser cookie borrowing or silent re-pairing.
7. Release each module and Runner package independently with least-privilege identities, target assertions, source/artifact provenance, signing or verifiable hashes, rollback and compatibility policy. Do not force a GitHub-only path.

## Target checks and execution boundary

Resolve `legacy-debian-dev`, `modular-debian-dev` and `modular-cloudflare-prod` through `apps/web/scripts/deployment-targets.json` before any build intended for release. Preserve current `smartaihub.app` Legacy service and the healthy `aimarkethubs.com` port-3100 service. `aimarkethubs.com` is currently unavailable for Modular application traffic until its replacement is healthy and handover is intentional. `smartsihub.com` is not activated and retains separate production release authority. The target map's shared `smartspec` mapping is not proof of live DB readiness. A later mission must verify exact runtime, application, service, port, database endpoint and separately scoped credential, environment-tenant binding, target ID and deployment identity before publishing or changing traffic.

Do not activate remote Runner execution until SPEC-325's non-production tests cover one-time enrollment, device proof-of-possession, signed effect-bound job envelope, reconnect/replay/fencing, live revoke, tenant isolation, OS boot, service recovery, locked-session limits, safe updates, shared Companion state and artifact redaction. Ordinary bounded autonomous work under a valid Goal grant must not introduce recurring approval prompts.

## Status reporting

Keep `SPECIFIED`, `IMPLEMENTED` and `DEPLOYED` separate. Report source SHA, focused checks, exact target identity and actual runtime evidence for each claimed state. A local Worker/DO simulation, CLI success or this mission text does not prove production readiness.
