# R0.7 — Owner correction, impact and consistency review

## Owner directive

A Mini App subscription includes only a Skill newly written for that Mini App and not shared with another system. Using any shared Skill requires credit billing for every distinct invocation, independent of subscription.

## R0.6 defects corrected

1. SPEC-321's broad phrase "covered Skill entitlement set" allowed pre-existing shared Skills into the subscription.
2. SPEC-321's generic periodic Skill-owner royalty pool could let shared Skills be used without the per-invocation charge explicitly required by owner.
3. SPEC-318 described all subscription-covered Skills as free and funded by a Skill-owner pool; it omitted nested shared billable calls.
4. SPEC-320 offered subscription with all covered skills free but did not distinguish App-exclusive from shared in public listings/checkout.
5. CODEX-MISSION-M0, README, work packages, and economy ADR repeated the broader R0.6 interpretation.
6. SPEC-313/314/319 lacked explicit exclusive-skill proof, billing inheritance prohibition and identical headless/WebMCP enforcement.

## New canonical decisions

- `APP_EXCLUSIVE_SKILL`: newly authored, App-scoped, verified provenance, not shared = subscription-included.
- `SHARED_BILLABLE_SKILL`: central/marketplace/other-App/third-party/reused = credits per distinct invocation.
- No wrapping/rebranding/unmodified fork bypass; no nested Skill billing bypass.
- Retry/double delivery not a new charge. Unproven classification never receives inclusion exemption.
- Contractual App-exclusive royalties can come from subscription proceeds; shared Skill royalties come from their own invocation revenue.
- No surprise charge if an exclusive Skill turns shared; present quote/authorize the affected action.
- Do not create a new credit ledger, orchestration authority or whole-platform UAT gate.

## File changes

SPEC-313, 314, 318, 319, 320, 321; README; WORK-PACKAGES; CODEX-MISSION; MARKETPLACE-ECONOMY-ADR; newly added MINIAPP-EXCLUSIVE-SKILL-SUBSCRIPTION-ADR and this review.

## Limits

Documents are proposed target policy only, not live runtime changes. Actual shared skill provenance and billing data must be discovered from existing Skill Registry/credit/ledger authorities during implementation.
