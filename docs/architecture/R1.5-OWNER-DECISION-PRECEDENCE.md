## Environment and database reconciliation

The checked-in target map currently names smartspec as the database contract for modular-cloudflare-prod and records a separate production application credential, but the target is not deployable and the entry does not establish an active database connection or shared host. R1.5 requires strong isolation from Legacy and development. Before future production provisioning, verify whether the target's logical database mapping points to an isolated production database and update its deployment mapping if needed. Do not infer or change live data, credentials or resources as part of this documentation revision.

For cross-product continuity, the bridge must identify the source authority, destination authority, permitted fields, actor/audience, direction, idempotency key, reconciliation process, revocation/deletion semantics and audit retention. No dual-write or silent credential reuse is allowed.

## Official product facts checked 2026-11-02

- Cloudflare Agents SDK Agents run on Durable Objects; persistent state and schedules survive hibernation/restarts, but in-memory state, timers and in-flight requests do not. An idle DO is evicted, and active work can stop on deploy/crash. See [Agents SDK runtime](https://developers.cloudflare.com/agents/runtime/), [long-running agents](https://developers.cloudflare.com/agents/concepts/agentic-patterns/long-running-agents/) and [schedule tasks](https://developers.cloudflare.com/agents/agent-class/schedule-tasks/).
- [Cloudflare Workflows](https://developers.cloudflare.com/workflows/get-started/guide/) persist multi-step state and support retries/sleep. Retryable steps still require idempotent external effects; they do not replace the platform job/settlement authority.
- [Durable Object WebSocket hibernation](https://developers.cloudflare.com/durable-objects/best-practices/websockets/) keeps server-side clients connected while an idle DO sleeps, but volatile in-memory state is reset on reactivation. This is not an always-running process guarantee.
- [Cloudflare Secrets Store](https://developers.cloudflare.com/secrets-store/) is open beta as of this date; it is currently compatible with Workers and AI Gateway. Current official docs state one store and up to 100 secrets per account. Role permissions and per-secret service scopes are required; treat this as a small shared-service tier, not a per-tenant credential database. Recheck status/limits at implementation time.
- Wrangler's [secrets.required](https://developers.cloudflare.com/workers/configuration/secrets/) property validates named required secrets on deploy/version upload. Local dev emits missing-secret warnings; the application startup/readiness check must therefore fail closed where required platform credentials are absent.
- [Service Bindings](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/) create private Worker-to-Worker calls, but Cloudflare Access context does not propagate through a Service Binding.
- Cloudflare [Worker-level Access does not support WebSocket connections](https://developers.cloudflare.com/workers/configuration/cloudflare-access/); a WebSocket service using Access must use a hostname-based Access application and independently verify application-level device proof.
- Cloudflare Access [mTLS Service Auth](https://developers.cloudflare.com/cloudflare-one/access-controls/service-credentials/mutual-tls-authentication/) has account-plan requirements; do not make it the only device-authentication path without verifying the target plan.
- [AWS KMS data keys](https://docs.aws.amazon.com/kms/latest/developerguide/data-keys.html) can return plaintext and wrapped data keys; plaintext must be used transiently and removed from memory. [AWS KMS key rotation](https://docs.aws.amazon.com/kms/latest/developerguide/rotate-keys.html) retains historical key material to decrypt existing ciphertext; rotation does not itself re-encrypt data keys. SPEC-325 selects AWS KMS behind a narrowly scoped broker as a proposed external KEK service, not as an existing deployed resource.

Provider facts are dated and linked. Design choices are normative proposals. Account-specific availability, quotas, region, pricing, cross-cloud latency and live resource state remain unverified.
