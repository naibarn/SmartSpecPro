## R1.6 — Owner clarification: shared database, separate environment tenants and selectable development path

The existing PostgreSQL `smartspec` database is the one canonical Core control plane for `smartaihub.app`, `aimarkethubs.com` and `smartsihub.com`. Reuse its existing user IDs, password/hash and revocation semantics, customer tenant IDs and memberships, credit ledger, subscriptions, App registry and `worker_jobs`/outbox authority. A user with a valid existing account can sign in to the modular application with that account; do not clone users, create an alternate identity store, copy the database or introduce a second ledger/job authority. New Mini App business data remains in its app-owned data plane under SPEC-323. The new Core uses Hono/TypeScript and Worker-compatible handlers; do not add Express or import the Legacy Express runtime.

Treat the database, customer tenant and environment tenant as separate concepts. `aimarkethubs.com` binds to the modular development/test environment tenant; `smartsihub.com` binds to a distinct modular production environment tenant. `smartaihub.app` retains its Legacy application context. Existing customer tenant IDs and authorized shared Core records remain canonical across those surfaces. Resolve every customer tenant from verified identity and membership; a hostname, environment tenant or request-supplied ID never grants access. Development-only records and effects remain scoped to the development tenant. Cross-environment reads or writes are allowed only for canonical records and operations authorized by the existing tenant, role and financial policy.

All three runtimes connect to the same canonical database authority. Use separately scoped runtime DB credentials, deployment identities, Worker bindings and secrets where supported; separate credentials do not mean separate databases. Preserve current schema semantics and default to zero DDL. Do not reuse a broad Legacy credential in a new runtime, and do not claim that a database role alone provides customer-tenant isolation without verifying the existing schema and authorization checks.

The normal development path may be direct Codex or Claude work in the canonical source repository, with scoped review, focused verification and source/commit receipts. The owner may instead route a task through the existing SPEC-224 Job/Run, Runner, Workspace and Harness facilities on `smartaihub.app`. Neither route is mandatory for every task; never claim SPEC-224 Run evidence for a direct session, and do not create a replacement in-house orchestration system.

The target registry already maps modular development and production to the logical `smartspec` database contract. Keep `aimarkethubs.com` unavailable and preserve the current port-3100 service until its replacement is healthy. Keep `smartsihub.com` registered but inactive until its separate production release authority is provisioned. This clarification changes no live database, credential, DNS, Worker or service.

## Environment and database reconciliation

The checked-in target map records `smartspec` for both modular targets and a distinct production application credential. That is the intended shared database contract, not evidence of a live connection or runtime readiness. Before a release, verify the exact target, database endpoint, scoped credential and environment-tenant binding. The application shares canonical records under existing authorization; dev-only data and production-only effects remain tenant-scoped. No database copy or continuity bridge is needed for records already in the canonical database. Any future replicated or external data bridge must identify authority, permitted fields, direction, idempotency, reconciliation, revocation/deletion and audit retention. No dual-write or silent credential reuse is allowed.

## Official product facts checked 2026-11-02

- Cloudflare Agents SDK Agents run on Durable Objects; persistent state and schedules survive hibernation/restarts, but in-memory state, timers and in-flight requests do not. An idle DO is evicted, and active work can stop on deploy/crash. See [Agents SDK runtime](https://developers.cloudflare.com/agents/runtime/), [long-running agents](https://developers.cloudflare.com/agents/concepts/agentic-patterns/long-running-agents/) and [schedule tasks](https://developers.cloudflare.com/agents/agent-class/schedule-tasks/).
- [Cloudflare Workflows](https://developers.cloudflare.com/workflows/get-started/guide/) persist multi-step state and support retries/sleep. Retryable steps still require idempotent external effects; they do not replace the platform job/settlement authority.
- [Durable Object WebSocket hibernation](https://developers.cloudflare.com/durable-objects/best-practices/websockets/) keeps server-side clients connected while an idle DO sleeps, but volatile in-memory state is reset on reactivation. This is not an always-running process guarantee.
- [Cloudflare Secrets Store](https://developers.cloudflare.com/secrets-store/) is open beta as of this date; it is currently compatible with Workers and AI Gateway. Current official docs state one store and up to 100 secrets per account. Role permissions and per-secret service scopes are required; treat this as a small shared-service tier, not a per-tenant credential database. Recheck status/limits at implementation time.
- Wrangler's [secrets.required](https://developers.cloudflare.com/workers/configuration/secrets/) property validates named required secrets on deploy/version upload. Local dev emits missing-secret warnings; the application startup/readiness check must therefore fail closed where required platform credentials are absent.
- [Service Bindings](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/) create private Worker-to-Worker calls, but Cloudflare Access context does not propagate through a Service Binding.
- Cloudflare [Worker-level Access does not support WebSocket connections](https://developers.cloudflare.com/workers/configuration/cloudflare-access/); a WebSocket service using Access must use a hostname-based Access application and independently verify application-level device proof.
- Cloudflare Access [mTLS Service Auth](https://developers.cloudflare.com/cloudflare-one/access-controls/service-credentials/mutual-tls-authentication/) has account-plan requirements; do not make it the only device-authentication path without verifying the target plan.
- [AWS KMS data keys](https://docs.aws.amazon.com/kms/latest/developerguide/data-keys.html) can return plaintext and wrapped data keys; plaintext must be used transiently and removed from memory. [AWS KMS key rotation](https://docs.aws.amazon.com/kms/latest/developerguide/rotate-keys.html) retains historical key material to decrypt existing ciphertext; rotation does not itself re-encrypt data keys. SPEC-325 selects AWS KMS behind a narrowly scoped broker as a proposed external KEK service, not as an existing deployed resource.

Provider facts are dated and linked. Design choices are normative proposals. Account-specific availability, quotas, region, pricing, cross-cloud latency and live resource state remain unverified.
