# Test Design — Provider Boundary Revalidation

| Requirement | Observable behavior | Level and test | RED target | Residual boundary |
|---|---|---|---|---|
| Team room authority is checked at provider boundary | A valid captured binding is revalidated after model/provider candidate resolution and immediately before each outbound provider request | Unit/integration seam: `unifiedOrchestrator.test.ts` and `llmRouter.providerAuthorization.test.ts` | Current executor input has no provider-attempt guard; revocation after context construction is not observable by the fetch boundary | Does not make DB check and remote provider acceptance atomic |
| Revoked/mismatched binding fails closed | Guard rejection propagates; no provider fetch and no alternate-provider fallback occurs | Deterministic provider-boundary test with at least two candidates and mocked `fetch` | Current router catches request-path failures as network errors and may continue fallback | Does not prove external provider behavior after request acceptance |
| Guard is repeated for each fallback attempt | Each candidate attempt has a fresh authority read before dispatch | `llmRouter.providerAuthorization.test.ts` counts guard calls across a failed provider and its fallback | Existing router has no callback parameter | Test does not exercise a live external provider |
| Direct media execution is guarded | Team-room image/video/audio paths call the binding guard before handing context-derived prompt data to the media service | `imageExecutor.test.ts`, `audioExecutor.test.ts`, and `videoExecutor.test.ts` prove guard rejection propagates and the media service is not called | Existing executors do not receive an authorization callback | Does not validate the media backend's later durable job authorization |
| Worker-local dispatch is guarded | A project-bound worker-local request is revalidated before durable queue persistence | `llmRouter.providerAuthorization.test.ts` proves guard rejection leaves the worker queue untouched | Existing worker-local branch bypasses HTTP provider attempts | Does not prove later worker execution's independent authorization |
| Non-team behavior remains compatible | Chat requests without a verified project binding do not run the team guard and retain global-only memory behavior | Existing focused context/orchestrator suites | Guard is optional and absent on chat | No live user/provider acceptance |
| Mini App routing honors stable App identity | Only canonical Research Notes and Project Wiki IDs select their reference UI; an unrelated active App gets an unsupported-runtime state | `MiniAppRoute.test.tsx`, plus the existing Research Notes and Project Wiki page suites | Any resolved App other than Project Wiki defaults to Research Notes | Does not verify a registered production route, arbitrary App hosting, migration, or deployment |
| Team-room message capture cannot persist personal entity facts before provenance acceptance | `captureUserMemoryFromTeamMessage` returns zero without extraction or entity upsert while the shared policy is disabled | Unit: `teamRoomMemoryService.test.ts` | Previous path extracted user message entities and called `upsertEntityMemory` with `source=team_room` | Does not disable explicit, permission-checked manual scoped-memory CRUD |
| Team-room assistant output and rolling summaries cannot persist before isolation acceptance | `recordAssistantTurnScopedMemories` and `refreshRollingSummaryMemories` return empty results without memory writes, room-history reads, or summarization | Unit: `teamRoomMemoryService.test.ts` | Previous paths persisted run/room/team episodes and read history for rolling summaries | Team-room execution context still uses authorized live room history; only persistent memory writes are disabled |
| Team-room provenance cannot be erased by merging into an existing entity | If a team-room fact is merged into an existing entity row, its source remains `team_room`, even when the prior source was `auto` | Unit with a deterministic existing-row update mock: `memoryServiceTeamRoomProvenance.test.ts` | Existing update merged facts but left the previous source unchanged | Historical mixed rows written before this guard cannot be reliably reconstructed from row-level provenance |
| Persistent team-room memories are excluded from prompt context | Prompt retrieval removes room/team/run scopes and room/team graph joins, excludes rows with prior room/team/run promotion audit records, rejects returned projections with room provenance, filters direct Chat facts and promoted user rules, and excludes entity rows tagged `team_room` | Service contracts: `scopedMemoryTeamRoomPromptPolicy.test.ts`, `teamRoomMemoryPolicy.test.ts`, `memoryPersonaRouting.test.ts`, `memoryServiceTeamRoomProvenance.test.ts` | Existing graph retrieval could query source-room rows; user-scope Chat retrieval and rule retrieval could return promoted room-derived rows; run-owned rows without `sourceRoomId` were not excluded | SQL-shape and unit tests do not establish production database contents or team-room App-switch acceptance; historical mixed entity facts in rows whose source remains `auto`/null are unidentifiable |
| Historical room promotions cannot bypass the graph exclusion via another related match | The promotion `NOT EXISTS` predicate is applied outside the complete graph-match `OR`, so project, assistant, or run metadata matches cannot re-include a promoted row with `sourceRoomId = NULL` | SQL-shape regression in `scopedMemoryTeamRoomPromptPolicy.test.ts` checks the exclusion follows the final graph alternative | The original exclusion lived only in the scoped-owner branch of the `OR` | This proves query construction, not the contents of a production database |
