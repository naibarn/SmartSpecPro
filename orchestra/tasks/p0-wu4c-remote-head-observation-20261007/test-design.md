# P0-WU-4C Fresh Remote Head Observation Test Design

| Requirement | Observable behavior | Test level and location | RED evidence | GREEN evidence | Residual boundary |
|---|---|---|---|---|---|
| Push state comes from a fresh authoritative remote ref | Distinguishes one local commit beyond an upstream head from commits already pushed; `git ls-remote` does not mutate cached refs | Unit/integration: `scripts/development-lifecycle/test_workspace_authority.py::test_project_mission_control_uses_fresh_remote_heads_for_push_and_integration_state` | Before change, Mission Control reported local SHA `1a307224…` while current remote main was `851e4c02…`; push state remained hard-coded `UNKNOWN` | Local bare remote proves unpushed 1, pushed/unintegrated 2, then integrated after canonical advance; remote tracking refs unchanged | Does not prove provider-side PR state on hosts lacking an upstream binding |
| Stale or unavailable remote evidence stays unknown | Expired/future/unavailable observation never falls back to a local SHA as current canonical truth | Unit: `test_project_mission_control_does_not_fall_back_to_local_sha_when_remote_is_unavailable`; TS projection test below | Pre-change canonical SHA came from local registry and could appear current despite remote divergence | Unavailable remote returns `canonical_sha: null`, `REMOTE_HEAD_UNAVAILABLE`, and unknown workspace parity; stale snapshot remains unknown | Live remote failure modes beyond Git's `ls-remote` error contract are not exercised |
| Integration distinguishes merged, patch-equivalent, and unintegrated facts | Current remote upstream tip is compared with current canonical head; patch equivalence is labeled explicitly | Unit: `test_project_mission_control_marks_patch_equivalent_remote_head_explicitly` and push/integration test | Existing implementation emitted no integration classification | Tests prove exact integrated head and `PATCH_EQUIVALENT` via `git cherry` patch IDs | Patch ID is content equivalence evidence, not product-level semantic equivalence |
| Cached evidence expires before Mission Control projection | Expired canonical, push, integration, and user-workspace parity facts become `STALE` with counts removed | Unit: `apps/web/server/services/workspaceAuthorityProjectReadModel.test.ts::downgrades expired remote push and canonical facts to STALE` | Existing projection accepted any audit younger than 15 minutes even when nested remote evidence had a shorter TTL | Focused Vitest projection suite passes with explicit 60-second expiry assertions | Does not prove scheduler cadence or remote API availability in production |
| CLI binds the configured canonical remote | Local Mission Control command returns fresh canonical remote SHA and sanitized observation metadata | CLI integration: `test_mission_control_cli_returns_success_for_authority_snapshot` | Before change, CLI did not observe remote refs | Local bare remote CLI fixture passes; live local run observed canonical `851e4c02…` and 81 remote heads without returning ref inventory | External runtime verification remains separate |
| Same-session local owner and Runner facts are merged without dropping task/provider identity | Unknown local provider retains a fresh Runner provider, runner binding, task assignment, host, and lease state; conflicting known provider facts return UNKNOWN | Unit: `apps/web/server/services/workspaceAuthorityProjectReadModel.test.ts::merges registered owner task facts with trusted Runner provider facts for the same live session` and `does not choose between conflicting confirmed session providers` | New tests failed 2/13: local owner row overwrote the Runner row and conflicting provider claims selected `claude` | Focused projection suite passes 13/13 after field-aware merge | No provider is inferred when both sources lack an explicit value; multi-Runner production ingestion remains external |
| RunnerGateway revocation tests remain isolated while preserving real revoke checks | Revocation, ephemeral, and dedupe state are in-memory per suite and cleared after each test; a revoked token remains rejected | Focused and combined unit suites: `runnerGateway.test.ts`, `runnerControl.test.ts`, `computerUseFeature195Gateway.test.ts` | Original brief reported 13 failures from pre-existing revoked-token state; fix was already present in this integrated baseline, so only the current behavior was rechecked | `JWT_SECRET=<test-only>` focused suite passes 17/17; combined three-file suite passes 43/43 | Does not reproduce the historical shared database state or prove PostgreSQL rollback behavior; the suite mocks the backing stores by design |
