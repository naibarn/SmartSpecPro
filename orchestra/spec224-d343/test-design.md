# D3.43 Durable Runner Continuation — Test Design

| Requirement | Observable behavior | Level / target | RED evidence | GREEN evidence | Residual boundary |
|---|---|---|---|---|---|
| Persist receipt and continuation intent atomically with stable identity | A committed terminal Spec 224 Runner receipt has exactly one pending operation ID derived from run/job/attempt/receipt; rollback leaves neither | Unit + PostgreSQL: `jobControlPlane.test.ts`, new `spec224RunnerContinuationPostgres.integration.test.ts` | Inject transaction failure after receipt insert; verify no receipt or intent | Retry commits one receipt and one intent | Real process restart tested only by PG integration fixture; no Runner provider |
| Complete/fail settlement is restartable and idempotent | Persisted receipt can recover canonical worker status after process restart; replay creates no duplicate terminal event | PostgreSQL + child process | Child exits between receipt persistence and settlement | restarted reconciler settles once; duplicate receipt is exact duplicate | No external provider billing/settlement certification |
| DevelopmentRun continuation is durable and idempotent | Pending intent reconciles terminal worker job into one owner-scoped DevelopmentRun event/projection | PostgreSQL + child process | Persist intent, terminate process before calling reconcile | restarted existing reconciler updates state once | It advances canonical projection only; next-phase job admission still requires existing policy/approval path |
| Crash after continuation commit before ACK does not repeat effects | Reconcile, terminate before ACK marker/response, restart and scan again | PostgreSQL + child process | crash after projection tx commit | event, dispatch/outbox, settlement and audit counts stay unchanged on replay | WSS-level live ACK timing is not tested without registered Runner |
| Concurrent reconcilers do not duplicate transitions | Two independent processes handle the same operation simultaneously | PostgreSQL + child processes | launch two against one pending op | one phase/decision event; no duplicate terminal/outbox/settlement | No multi-host failure-domain test |
| Unknown outcome is fail-closed | `UNKNOWN_OUTCOME` produces operator review, not automatic repair/retry | Unit + PostgreSQL | baseline currently maps failed job to repairable state | DevelopmentRun enters `WAITING_HUMAN_DECISION`; no next-job outbox | Operator UI action remains separate |
| Tenant/session/attempt/fence/capability mismatch rejects continuation | No DevelopmentRun transition or new outbox is created | Unit + PostgreSQL negatives | mismatch payload/current projection | ignored or operator-review state with audit; canonical counts unchanged | Runner process authentication is not certified |
| Cancellation race and duplicate/conflicting receipt | Cancellation wins by canonical status CAS; exact duplicate is idempotent; conflicting payload is rejected and audited | Unit + PostgreSQL | race/alter receipt scenarios | no double completion; conflict audit once per content digest | Live network partition not tested |

Focused test commands will run after the test-only RED cases are added. PostgreSQL must be a dedicated loopback-only disposable PostgreSQL 15.17 instance with isolated database and credentials. TypeScript typecheck remains `SKIPPED_POLICY`.
