# Test Design — Worker App and Chrome Extension Recovery

| Requirement | Observable behavior | Level / location | RED evidence | GREEN proof | Residual boundary |
|---|---|---|---|---|---|
| Resolve encrypted DB keyring without exposing bytes | Pairing store can encrypt/decrypt a round trip from persisted system setting; admin status returns only IDs/source/status | Unit: new Worker keyring service test | Existing implementation rejects absent env keyring; no UI-backed store | Focused service test covers valid, missing, malformed, and failed decrypt cases | Does not prove all production Web instances share the same LLM root key |
| Preserve previous Worker session format | Keyless AES-GCM envelope encrypted with prior SHA-256(JWT_SECRET) derivation can be read and re-encrypted | Unit: ephemeral authorization store tests | Existing code rejects envelopes without `keyId` | Legacy fixture decrypts; resulting row has active key ID and same payload | Needs Production inventory to know if any legacy rows exist |
| Safe key initialization | Admin action creates random 32-byte key server-side and only returns a configured status | Router/service test | No keyring initialization procedure exists | Test checks ciphertext persisted, no raw key returned, non-admin denied | DB test does not prove browser account authorization in Production |
| Rotation and rollback | New writes use new key; old keys still decrypt; rollback changes active key; pruning is blocked while live sessions reference a key | Unit/integration: key service + PostgreSQL integration tests | Current active key is env-only and has no UI lifecycle | Tests cover batch rotation, rollback, non-expired references, and safe prune | Cross-instance propagation/cache behavior requires multi-process smoke |
| Crypto encoding compatibility | Existing Node AES-GCM envelope is consumed by WebCrypto using same raw key/12-byte IV and separated 16-byte auth tag | Unit: crypto compatibility test | No Node/WebCrypto interoperability test | Exact known-plaintext round trip in both directions, hex settings envelope remains stable | WebCrypto test does not prove a deployed Cloudflare Worker uses the key |
| Worker connection route recovers | Connect start/status/approve/token handshake reaches its normal state transitions with DB keyring | Contract: `workerRuntime.test.ts` or focused route test | Existing route returns mapped 503 when store cannot load keyring | Focused mocked route asserts statuses and no secret leakage | Does not prove public domain routing/deployed DB readiness |
| Chrome extension stays independent and functional | Extension connect page issues a device-bound token and Companion receives it without rendering credential; Worker routes reject extension token | Existing UI tests plus focused auth contract | Existing UI delivery test is baseline; add token-use isolation regression if absent | `MarketplaceCaptureConnect.test.tsx`, extension auth test, and Worker rejection test pass | Browser Store installation/extension ID and user-account policy require manual target test |
| Admin instructions/readiness | Admin sees exact blocked/ready state, supported actions, and localized setup/rotation guide | UI test: new Worker pairing settings component | No Worker keyring status/action surface | Tests assert Thai/English labels, no key bytes, disabled unsafe actions | No authenticated browser screenshot available without login session |
