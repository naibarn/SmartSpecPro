Verdict: APPROVE_WITH_FIXES (2026-03-24)

2 CRITICAL, 5 HIGH, 7 MEDIUM, 4 LOW findings.

**Why:** Spec covers the happy path of provider registration and media pipeline well, but has critical gaps in the Python media generation dispatch layer, API key sourcing, `_upload_and_return_url` helper, and TTS pipeline wiring.

**How to apply:** Sections 01-03 need significant hardening before Batches 2-3 can begin safely. The generation_service.py integration path and config.py env var addition must be planned explicitly.

Key findings:
- **CRITICAL-1 — generation_service.py integration path entirely absent**: The existing media dispatch chain goes through `generation_service.py` → `kie_provider` → Celery. KNPLabs bypasses this entirely; no section describes how `media_generation.py` API endpoint routes a `provider=knplabai` request to the new Celery task. Section 05 defines the Celery task but nothing wires it in.
- **CRITICAL-2 — `_upload_and_return_url` helper undefined**: The spec uses this method throughout Sections 04, 06, 07 (Gemini base64→S3, TTS binary→S3) but it is not defined in the provider class skeleton and does not exist in fal_ai_provider.py or kie_ai_provider.py. The upload pattern is in `media_pipeline.py` / `r2_storage.py` — the spec never maps this dependency.
- **HIGH-1 — `KNPLABAI_API_KEY` not added to config.py Settings**: Python backend reads API keys from `app/core/config.py` (pydantic BaseSettings). No section adds `KNPLABAI_API_KEY: str = ""` to this file. Provider will raise AttributeError at instantiation.
- **HIGH-2 — Factory.py integration uses wrong pattern**: Spec shows `elif provider_type == "knplabai": return KNPLabAIProvider(settings)` but `factory.py` handles LLM providers (OpenAI-compatible), not media providers. KNPLabAIProvider is a media provider — it must be instantiated by the media generation dispatch layer, not the LLM ProviderFactory. These are separate registries.
- **HIGH-3 — VEO multipart/form-data not detailed**: VEO text-to-video uses `multipart/form-data` (not JSON). The spec mentions this in the endpoint matrix but the Section 05 implementation sketch only shows polling, not the form-data submission. httpx requires `files=` kwarg, not `json=`.
- **HIGH-4 — Credit cost column mismatch**: Spec seed SQL shows `creditCost` as int (e.g., 5, 6) but the conversion formula gives fractional values (GPT Image 1.5: 0.156 KNP × 69 = 10.764 → 11 SSP credits). The spec shows both "0.156 cr/req" and "5" as creditCost in the same table. The DB column type and rounding rule must be stated unambiguously.
- **HIGH-5 — Section 08 embeddings breaks existing pgvector integration**: Section 08 modifies `embedding_service.py` to add KNPLabs fallback. The existing system uses this service for chat memory (spec 055) and agency memory (spec 056) — both of which depend on a specific embedding dimension. KNPLabs offers 3,072 (3-large) and 1,536 (3-small/ada) dimensions. Adding a fallback with a different dimension will corrupt existing vector comparisons if the primary provider used 1,536 and KNPLabs falls back to 3,072. No dimension guard is specified.
- **MEDIUM-1 — Gemini API key sent as both Bearer header AND ?key= query param**: Spec shows this (Section F2.1) but does not note that the API key appears in server logs as a URL query param. The spec should explicitly note that the key must be redacted from logs and that `follow_redirects=False` must apply to this call too.
- **MEDIUM-2 — TBD credit costs for 7 out of 10 video models**: The spec marks video i2v and all Grok video models as "TBD". Section 09 (Cost Tracking) cannot be implemented correctly without these values. This blocks accurate `mediaModels` seeding.
- **MEDIUM-3 — TBD credit costs for all 3 TTS models**: Same issue — Section 07 and Section 09 cannot complete.
- **MEDIUM-4 — Polling timeout strategy incomplete**: The spec says "max 10 minutes" but does not specify what Celery task state to set on timeout (FAILURE vs a custom state), nor does it specify whether the `mediaCallbackEvents` row should be tombstoned or left for retry. This must match the existing kie_ai polling pattern.
- **MEDIUM-5 — Section dependency graph omits `generation_service.py`**: Section 05 correctly depends on 01 and 03, but the section that wires the new task into the existing API endpoint (`media_generation.py`) is entirely absent from the manifest. This is effectively a missing section.
- **MEDIUM-6 — No migration for `media_providers` seed**: The spec claims "no schema migration required" (§6.1), but the `media_providers` table has a `providerType` column backed by the `media_provider_type` enum. The enum already contains `"multimodal"` so this is fine — but the claim should be verified explicitly against the current enum values, which the spec does not do.
- **MEDIUM-7 — `llmProviders.providerType` column is varchar(32), not enum**: The spec inserts `providerType = 'secondary'` in the SQL example. The column is `varchar("providerType", { length: 32 }).default("primary")` — not an enum. This is compatible, but the spec should list valid values (primary/secondary/fallback) and confirm the circuit breaker code handles 'secondary'.
- **LOW-1 — Section 11 dependency on Section 06 is asymmetric**: The index says Section 11 (Security) blocks Section 06 (Image-to-Video). But Section 11 can be written stand-alone; the SSRF utility should be written in Section 11 and imported in Section 06, not the other way. The dependency direction is wrong — Section 06 should depend on 11, not vice versa. (The table does show this correctly; the prose "Batch 3 — Depends on Video + Security" is correct. Minor spec clarity issue.)
- **LOW-2 — Section 10 Admin Dashboard has no concrete file list**: Section summary says `Admin*.tsx` — there are multiple admin pages. The section spec should name the exact component(s) to modify.
- **LOW-3 — LLM seed script creates `llmModels` records but spec does not mention this table**: `modelProviderMap` needs a `modelId` FK. Some model IDs (qwen-3.5, kimi-k.25, etc.) may not exist in `llmModels` table yet. If there is a FK constraint, the seed will fail. Spec should verify and seed `llmModels` first.
- **LOW-4 — httpx client lifecycle not specified for KNPLabAIProvider**: fal_ai_provider.py implements `aclose()`, `__aenter__`, `__aexit__`. The spec's class skeleton omits these. kie_ai_provider.py also has no `aclose` — it uses a persistent `httpx.AsyncClient(timeout=600.0)` that is never closed. The spec should specify whether to follow fal.ai's lifecycle pattern or kie.ai's pattern.
