CURRENT STATE: DUAL ARCHITECTURE
================================================================================

PRODUCTION (BROWSER):
  Cookie: app_session_id (HS256 JWT, httpOnly, 30-day expiry) ✅ SECURE
  Transmission: Automatic via browser (credentials: 'include')
  Verification: HS256 HMAC with env.cookieSecret
  Revocation: Redis + in-memory JTI denylist
  User lookup: Database (openId) on each request

FALLBACK (TAURI DESKTOP):
  Primary: Tauri secure store (native Rust keychain)
  Fallback: localStorage ("smartspec_auth_token", "smartspec_user_data")
  Risk: localStorage is XSS-vulnerable if Tauri unavailable

USER DATA:
  Storage: localStorage ("smartspec_user_data") — cached JSON
  Risk: XSS-vulnerable; plaintext user object

API KEYS (USER-PROVIDED):
  Storage: sessionStorage ("smartspec_apikey_{provider}") — CRITICAL TODO
  Providers: openrouter, openai, anthropic, deepseek, google
  Risk: ⚠️⚠️ CRITICAL XSS VULNERABILITY — All LLM keys exposed if XSS
  Status: TODO at authService.ts:272 to move to encrypted DB store

================================================================================
LOGIN FLOW
================================================================================

1. User submits email + password
   ↓
2. Server verifies credentials + creates HS256 JWT:
   - Payload: { openId, appId, name, jti (for revocation), exp }
   - Secret: env.cookieSecret → SHA-256
   ↓
3. JWT set as httpOnly cookie with options:
   - httpOnly: true (prevents JS access)
   - secure: true (HTTPS only in prod)
   - sameSite: "none" (prod HTTPS) / "lax" (dev HTTP)
   - domain: ".smartspec.pro" (allows subdomain sharing)
   - maxAge: 30 days
   ↓
4. Browser auto-includes cookie in tRPC requests (credentials: 'include')
   ↓
5. Server extracts from request (context.ts):
   - Check Authorization: Bearer header first
   - Fall back to "app_session_id" cookie
   ↓
6. Verify JWT signature + check JTI not revoked
   ↓
7. Look up user by openId in database
   ↓
8. Return authenticated user context

================================================================================
SECURITY ASSESSMENT
================================================================================

STRONG POINTS ✅
- httpOnly cookies prevent JavaScript access (XSS protection)
- HS256 HMAC with server-side secret (not vulnerable to tampering)
- SameSite=none with secure=true for HTTPS (CSRF protection)
- Revocation system (JTI-based logout + Redis caching)
- Password hashing with bcrypt (12 rounds)
- Email verification before account activation
- 2FA support (with backup codes)

WEAK POINTS ⚠️
- localStorage fallback for Tauri (exposes token if XSS on desktop app)
- sessionStorage API keys (CRITICAL XSS risk for all LLM credentials)
- Unclear if JTI revocation is checked in verifySession()
- No token rotation (same JWT valid for entire 30-day window)
- No refresh token rotation (requires new login after 30 days)
- Client-side token expiry check (at isTokenExpired(), not enforced server-side)

MIGRATION DECISION TREE
================================================================================

Q: Keep localStorage JWT fallback?
A: NO. Remove entirely; Tauri should have native secure store only.
   Reason: Creates attack surface for XSS if Tauri unavailable.

Q: Keep httpOnly session cookies?
A: YES. Already correct; no changes needed.
   Reason: Browser-managed; no JavaScript access.

Q: Migrate API keys to encrypted DB table?
A: YES. BLOCKING ISSUE. sessionStorage is XSS-vulnerable.
   Timeline: Phase 1 (1-2 weeks)

Q: Add token rotation?
A: OPTIONAL. Not required for Phase 1 launch.
   Timeline: Phase 3 (future iteration)

Q: Switch to refresh token pattern?
A: OPTIONAL. Only if 30-day session duration becomes a pain point.
   Timeline: Phase 3 (future iteration)
